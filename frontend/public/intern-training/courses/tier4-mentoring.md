# Tier 4：指導他人

學到這個階段，你已經有足夠的能力帶新人了。這一課講的是「怎麼有效地幫助別人學習」，而不只是「幫別人解決問題」。

---

## 指導的目標

幫助對方「學會解決這類問題」，而不只是「解決這一個問題」。

區別在哪裡？

```
幫他解決：
「你的問題在第 23 行，改成這樣就好了。」
（對方今天修好了，明天遇到類似問題還是卡住）

教他學會：
「你覺得問題可能在哪裡？Console 有什麼錯誤訊息？
Network tab 的請求是 200 還是 4xx？」
（對方今天多花了 10 分鐘，但學到了 debug 的方法）
```

> 💡 提示：給魚不如教釣魚。但「教釣魚」需要耐心，因為對方學習的過程中你要忍住「直接告訴他答案」的衝動。

---

## Pair Programming

兩個人面對同一個螢幕、同一個問題一起工作。有兩個角色：

**Driver（司機）**：負責打字，把思路轉換成程式碼。

**Navigator（領航員）**：負責思考，說「往這個方向走」，不急著打字。

```
實際操作：
- 兩個人坐在一起（或視訊）
- Driver 分享螢幕
- Navigator 說「我們先看看 Console 有什麼錯誤」
- Driver 打開 DevTools → Console
- Navigator 說「那個 TypeError 的 stack trace 指向哪個檔案？」
- Driver 點進去看
- ...繼續，每 20-30 分鐘可以換一下角色
```

**重點**：Navigator 不是坐在旁邊看，而是積極地思考和引導方向。

## 引導提問法

不要直接給答案。用問題引導對方自己找到答案。

### 定位問題

```
不好：「你的問題在 fetchStory 那裡，你沒有處理 error。」

好的引導：
「你能描述一下 bug 是怎麼發生的嗎？使用者做了什麼，然後發生什麼？」
「你試著手動重現過嗎？每次都會發生還是偶爾？」
「Console 有紅色錯誤訊息嗎？」
「Network tab 裡那個請求的 status code 是什麼？」
```

### 尋找解法

```
不好：「用 try/catch 就好了。」

好的引導：
「如果 API 請求失敗了，現在的程式碼會怎麼樣？」
「你覺得怎樣的使用者體驗是好的？（想像你自己是學生）」
「你有沒有看過 ComprehensionChat 是怎麼處理 API 錯誤的？可以參考那裡的寫法。」
```

### 驗證解法

```
不好：「改完 push 上去就好了。」

好的引導：
「你怎麼知道改好了？你測試過哪些情況？」
「如果 API 真的回傳錯誤，使用者會看到什麼？你測過這個路徑嗎？」
```

## 解釋技巧

當你需要解釋一個概念，用對方已經知道的東西來類比。

```
解釋 useState：
「你有沒有用過 Excel？想像 React 的 state 是試算表裡的一格，
你改了那格的值，所有參照到它的公式都會自動更新。
useState 就是那格，setXxx 就是改那格的值。」

解釋 useEffect：
「就像你設定一個提醒：『每次我改變城市後，更新天氣預報』。
useEffect 就是『每次 [城市] 改變，就去做 [更新天氣] 這件事』。」

解釋 API：
「餐廳點餐的過程：你說我要點 A 和 B（request），
廚房做好了送出來（response）。你不需要知道廚房怎麼做的，
只需要知道怎麼點餐（API 格式）和餐點長什麼樣（response 格式）。」
```

> 💡 提示：如果對方聽了還是不懂，不是他太笨，是你的比喻不夠好。換一個角度再試一次。

## 帶新人完成第一個 Bug Fix

**你的角色**：Navigator + 教練，不是代勞。

```
流程：

1. 一起看 Issue 描述，確認理解問題
   → 問：「你覺得這個 bug 是在前端還是後端？」

2. 一起重現 bug
   → 問：「你能穩定重現嗎？重現的步驟是什麼？」

3. 引導使用 DevTools
   → 說：「先打開 Console，看看有沒有錯誤訊息」
   → 不要：代替他操作 DevTools

4. 引導定位問題
   → 問：「你覺得是哪個函式出問題？」
   → 可以提示：「試試在 handleSend 裡加個 console.log，看資料對不對」

5. 讓他自己寫修復
   → 可以說：「你覺得怎麼改比較好？」
   → 可以說：「有沒有看過類似的處理方式在其他地方？」
   → 不要：直接寫程式碼

6. 一起驗證修復
   → 問：「你要怎麼確認這個 fix 有效？」
   → 問：「有沒有其他的邊界條件要測試？」

7. 一起開 PR
   → 讓他自己寫 PR 說明，你給 review 意見
```

---

## 反思：教學讓你更了解自己

教別人的過程中，你會發現自己哪些地方其實不夠熟：

「我以為我懂 useEffect 的 cleanup，但要解釋給靖杭的時候我說不清楚為什麼需要 cleanup...」

這是正常的。能說清楚一個概念，才是真的懂了。

## 練習

**任務**：帶一個更新的實習生（如果有的話）完成他的第一個 bug fix

如果目前只有你一個實習生，這個練習改為：

**選一個你之前解過的 bug**，用文字寫出「如果你要教別人解決這個 bug，你會問哪些引導問題？」

格式：

```markdown
## Bug 教學腳本：#XXX [bug 名稱]

### 我會先問的問題（引導重現）
1. ...
2. ...

### 我會引導他看的地方
- DevTools 的哪個 tab？
- 哪個函式？

### 我不會直接告訴他的（讓他自己發現）
- ...

### 當他卡住時，我會給的提示
- 第一層提示：「試著...」
- 第二層提示（如果還卡住）：「看看 [具體位置]」

### 我學到的（教學讓我重新理解的東西）
- 原來我對 X 的理解有點模糊，因為要解釋時說不清楚...
```

把這份腳本給 Young 看，他會給你回饋。
