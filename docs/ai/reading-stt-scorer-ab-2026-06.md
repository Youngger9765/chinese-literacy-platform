# 朗讀評分可信度驗證計畫（2026-06）

> Issue: #2266（根因 B）/ 相關 #2253（根因 A）
> 狀態：plan 定稿；階段 A 進行中
> 慣例對齊：`docs/ai/llm-model-ab-2026-05.md`

## 0. 一句話：我們到底要驗證什麼

**「系統打出來的正確率 = 老師/人耳會給的分數，而且穩定。」**
這是朗讀從以前到現在一直做不好的核心——分數不可信（方大哥幾乎全對卻 58%、且 39~58% 浮動）。延遲、成本、哪個 STT 引擎都是**次要**。

## 1. 為何之前一直做不好（根因）

把「逐字比對」這種**確定性**工作丟給 LLM 逐字吐 token → 截斷(58%)+ 浮動 + forgiven=0。詳見 #2266 定案。

## 2. 信心從哪來（關鍵思路）

分數可信 = 兩件事，**信心來源不同**：

| 要驗證 | 信心來源 | 需要測試集？ |
|--------|---------|------------|
| **評分邏輯**（文字→分數合理）| **確定性，像驗函數一樣驗** | ❌ 不需要 |
| **STT 品質**（音檔→文字準）| 真實人聲 | 需要（但見下）|

**關鍵洞察**：同音容忍**吸收大部分 STT 錯誤**（食指浩繁→十指好帆 全 forgive）→ **STT 不必完美，分數就可信**。所以「分數可信」主要靠**評分器**，不是靠 STT 完美、也不是靠大測試集。

## 3. 兩階段（不要混在一起）

### 階段 A — 沒測試集也能 tune 一版「敢上線、有信心」的（現在）
信心**不來自 100-200 樣本**，來自：
1. **評分器確定性 + 少數「已知正解」案例鎖死**（unit test，見 §4）。地基。
2. **自錄 5-10 段真音 sanity**（你/我/實習生：全對版 + 故意錯版）→ 肉眼確認「分數 == 我的判斷」。pre-test-set 的信心橋樑。
3. **守「不確定就寬鬆」**：STT 聽錯寧可 forgive，不冤枉扣分。

産出：一版 LiveTutor+FullReading 共用、確定性、穩定、分數合理的評分，敢給方大哥/教授再測。

### 階段 B — 測試集建好後（之後）
- 方大哥的 100-200 人聲樣本 → 廣度 + 回歸基準
- STT 引擎優化 A/B（Gemini batch 切短 vs Azure 即時 vs …）→ 求更快/更省（見附錄）
- 這些是**優化**，不是 v1 blocker

## 4. 階段 A Rubrics（主軸：可信 + 穩定）

| # | 維度 | 量法 | 通過 | 階段 |
|---|------|------|------|------|
| R3 | **正確率準度** | \|算出 − 人判真值\| | ≤ ±5%（自錄 sanity）；unit 案例精確 | **A 主軸** |
| R5 | **確定性** | 同輸入跑 N 次 variance | = 0 | **A 主軸** |

| R2 | STT 字準(CER) | STT vs 已知文字 | 記錄 | B 優化 |
| R4 | 成本 | $/min | 記錄 | B 優化 |
| R8 | 整合成本 | 質化 | 記錄 | B |

## 5. 階段 A 具體做法

**A-1 鎖評分器（確定性 unit，不需音檔、不需 LLM）**
測 `scorer(target, spoken_text)`：
- 全對 spoken==target → 100%
- 漏 K 字 → (N−K)/N、該位置 missing
- 同音/異調（食/十、浩/好）→ forgiven
- 真錯字（足/出）→ wrong
- 字序對調（風和日麗→日麗風和）→ 記錄它怎麼判（過罰?）
- 重複字（避免 ghost-green）、漏字後 resync（不 cascade）
- >100% 不可能、長段不截斷
- 方大哥 STT 文字 → ~98%（已驗前/後端各 98.1%）

**A-2 自錄真音 sanity（少量、人判對照）**
- 自己/實習生錄 5-10 段（≥2 篇課文 × 全對 + 故意錯）
- 跑 音檔→STT→評分→看顯示分數
- 每段標「人判應得幾分」，比對系統分數，差 > ±5% 就查
- 用現成 STT（Gemini batch，已夠準）即可，先不糾結引擎

**A-3 收斂上線**
- LiveTutor + FullReading 都接同一份確定性評分（移除後端 Gemini 逐字 diff 覆蓋）
- 上一版給方大哥/教授複測

## 5.5 最終成果呈現：HTML 檢視儀表板（交付物）

實驗結果**不只給表格**，要做一份**自包含 HTML**（零依賴、可直接開或上 staging `/presentation/` 同慣例）給 Young 檢視，UI/UX 要讓非工程也一眼看懂。必含：

1. **成本效益成果**：每方案的「延遲 × 準度 × 成本」並排（卡片/長條圖），標出 CP 值贏家；用顏色區分「可信(綠)/可接受(黃)/不行(紅)」
2. **階段比較**：Before（現況 58%/26-35s/浮動）→ After（目標 ~98%/穩定/<4s）對照；以及階段 A（可信）vs 階段 B（優化）要驗什麼、各拿到什麼
3. **架構圖分拆**：現況糾纏圖 → 目標收斂圖，模組逐塊標 LIVE/死碼/重複；同音三套→一套的收斂可視化
4. **分段選技術的理由**：Phase 0-4 每段「選哪個技術 + 為什麼」決策表（STT 引擎、評分位置、同音、GCS async），含取捨一句話
5. 每個數字可溯源（hover/註腳標 證據來源：staging log / curl / unit test）

設計要求（依 `~/.claude/rules/frontend-design.md`）：先有設計決策再寫；交付前自己截圖/開圖確認視覺（字夠大、不擠、圖文對齊、行動裝置可讀）。**不是丟檔，是「我看過視覺 OK」的交付。**

## 6. Caveats
- 自錄者咬字比真實國小生清楚 → 階段 A 是「邏輯可信」不是「真實 robustness」；真實要階段 B 人聲集
- STT 有非確定性 → STT 層看區間，**評分層必須 =0（確定性）**
- 「不確定就寬鬆」是教學取捨：寧可少扣不可錯扣

## 7. 技術選型 — 用「決策價值」篩，不平鋪 4 軸

實驗只在「結果會改變我們上線的選擇」時才值得跑。用這尺度，原本列的 4 軸（①STT 引擎 ②評分 ③演算法 ④前後端送件）**價值不對等**，收斂成 3 件：

| 原軸 | 我的判斷 | 動作 |
|------|---------|------|
| ②評分（確定性 vs LLM）| **已決**：98.1% vs 39~58%，確定性勝、無懸念 | **鎖定**，寫 unit 守住（非實驗）|
| ③演算法差異 | LCS 已成熟+前後端 parity，只剩 2 個窄誤判 | **小 unit 測**：字序對調過罰?、同音遮真錯? |
| ①+④（STT 引擎 + 前/後端送件）| **其實同一決策**：「前端送」≈瀏覽器即時 STT、「後端送」≈上傳 batch | **唯一值得量的實驗 = STT 延遲 PoC** |

**引擎準度 Azure vs Gemini**：在乾淨 TTS 音檔上**比不出有意義贏家**（真差異在童音/雜訊，要人聲集）→ 引擎現階段用**延遲/成本/整合**選，不用 TTS 準度當依據。背景跑的 TTS 準度比較**只當「pipeline 跑得通」佐證**，不當選型定案。

### 真正要跑的 3 件
1. **鎖 scorer（決定+unit）**：確定性後端，unit 覆蓋誤判模式（字序/同音/重複字/漏字 resync/>100% guard/長段不截斷/方大哥案例 98%）→ 同時是 ②鎖定 + ③測試
2. **自錄 5-10 段真音 sanity（信心）**：人判對照，pre-test-set 信心橋樑
3. **STT 延遲 PoC（唯一決策量測）**：Node+Azure SDK+WAV 量「即時串流延遲」vs 後端 batch 切短(~3-4s)；引擎準度排序留人聲集

matrix 仍記錄：C1 Gemini batch 全文(基準) / C2 Gemini batch 逐段 / C3 Azure STT / C4 Gemini Live(N/A headless) / C5 Web Speech(N/A headless)，結果進 §5.5 HTML。

### Key / 臨時 token（前端 STT 安全）
前端 STT **絕不放 key**；後端發短期 token：Azure `issueToken`(10 分) / Gemini ephemeral token(30 分)。本機 PoC 用 `backend/.env` key 直連（本機、不外曝、不 commit）；production 走 ephemeral token。

## 10. 實驗結果（2026-06-18，staging + 本機）
輸入：L10 小花（360/320 字）。F1=Azure TTS 唸原文(GT 100%)、F2=TTS 唸 6 受控錯誤版(GT 88.4%)、Fang=方大哥 STT 文字(GT 98.1%)。

| Combo | STT | Scorer | R1 延遲 | R2 CER | R3 誤差 | R4 成本/次 | R5 確定性 | R6 截斷 |
|-------|-----|--------|---------|--------|---------|-----------|-----------|---------|
| **C1 ✅贏家** | Gemini batch | 確定性 fallback | 7–14s | 0–1.8% | **<0.5%** | **$0.003** | **0 variance** | 無 |
| C2 現用 ❌ | Gemini batch | LLM 逐字 diff | 15–16s | 0–1.8% | **0–100%** | $0.007 | 高 variance | **100% 觸發** |
| C3 | Azure STT(REST) | 確定性 fallback | 20–24s | 3.8–4.2% | <0.3% | $0.022(7x) | 低 | 無 |
| C4b | Fang 文字 | LLM diff | 9.5–15s | — | 46–58% | $0.004 | 高 | 100% |
| C5/6 | Web Speech | — | N/A | — | — | — | — | — |

**結論：C1（Gemini batch STT + 確定性 fallback scorer）綜合最佳**——延遲最短、誤差 <0.5% 且零 variance、成本最低、無截斷、**工程量最小（只把 scorer 從 LLM diff 換成 fallback，不動 STT 層）**。

**現用 C2 三 bug 齊發（皆非邊緣 case）**：①MAX_TOKENS 截斷 100% 觸發；②**target==spoken→Gemini 吐空陣列→0 分（完美朗讀得 0，最慘）**；③root A 分母不一致（修 B 後會 >100%）。修 C2 要 A+B 同時修且仍有 LLM variance → 不如直接走 C1。

**引擎**：Azure STT(REST batch) 7x 貴、CER 更高（Gemini 有 target 上下文自校）→ batch 場景 Gemini 勝。Azure 即時串流延遲優勢需瀏覽器 PoC 才驗（但 Gemini 逐段 6.5s + 確定性 scorer ~0 已可接受，未必需要換）。

**限制**：實驗用乾淨成人 TTS 音，CER 樂觀；真實童音 CER 兩家都會升、Gemini 優勢縮小但不消失 → 真實排名待人聲集（階段 B）。
