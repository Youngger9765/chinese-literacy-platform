# 朗讀評分可信度驗證計畫（2026-06）

> Issue: #2266（根因 B）/ 相關 #2253（根因 A）
> 狀態：plan 定稿；階段 A 進行中
> 慣例對齊：`docs/ai/llm-model-ab-2026-05.md`

## 0. 一句話：我們到底要驗證什麼

**「系統打出來的正確率 = 老師/人耳會給的分數，而且穩定。」**
這是朗讀從以前到現在一直做不好的核心——分數不可信（方大哥幾乎全對卻 58%、且 39~58% 浮動）。延遲、成本、哪個 STT 引擎都是**次要**。

## 1. 為何之前一直做不好（根因）

把「逐字比對」這種**確定性**工作丟給 LLM 逐字吐 token → 截斷(58%)+ 浮動 + forgiven=0。詳見 #2266 定案。

## 2. 信心從哪來（關鍵思路）

分數可信 = 兩件事，**信心來源不同**：

| 要驗證 | 信心來源 | 需要測試集？ |
|--------|---------|------------|
| **評分邏輯**（文字→分數合理）| **確定性，像驗函數一樣驗** | ❌ 不需要 |
| **STT 品質**（音檔→文字準）| 真實人聲 | 需要（但見下）|

**關鍵洞察**：同音容忍**吸收大部分 STT 錯誤**（食指浩繁→十指好帆 全 forgive）→ **STT 不必完美，分數就可信**。所以「分數可信」主要靠**評分器**，不是靠 STT 完美、也不是靠大測試集。

## 3. 兩階段（不要混在一起）

### 階段 A — 沒測試集也能 tune 一版「敢上線、有信心」的（現在）
信心**不來自 100-200 樣本**，來自：
1. **評分器確定性 + 少數「已知正解」案例鎖死**（unit test，見 §4）。地基。
2. **自錄 5-10 段真音 sanity**（你/我/實習生：全對版 + 故意錯版）→ 肉眼確認「分數 == 我的判斷」。pre-test-set 的信心橋樑。
3. **守「不確定就寬鬆」**：STT 聽錯寧可 forgive，不冤枉扣分。

産出：一版 LiveTutor+FullReading 共用、確定性、穩定、分數合理的評分，敢給方大哥/教授再測。

### 階段 B — 測試集建好後（之後）
- 方大哥的 100-200 人聲樣本 → 廣度 + 回歸基準
- STT 引擎優化 A/B（Gemini batch 切短 vs Azure 即時 vs …）→ 求更快/更省（見附錄）
- 這些是**優化**，不是 v1 blocker

## 4. 階段 A Rubrics（主軸：可信 + 穩定）

| # | 維度 | 量法 | 通過 | 階段 |
|---|------|------|------|------|
| R3 | **正確率準度** | \|算出 − 人判真值\| | ≤ ±5%（自錄 sanity）；unit 案例精確 | **A 主軸** |
| R5 | **確定性** | 同輸入跑 N 次 variance | = 0 | **A 主軸** |
| R7 | **誤判模式** | 字序對調過罰？同音遮真錯？ | 記錄+設規則 | **A** |
| R6 | Robustness | 360 字長段不截斷/失敗 | 不截斷 | **A** |
| R1 | 延遲 | audio→分數 (s) | < 4s 可接受 | B 優化 |
| R2 | STT 字準(CER) | STT vs 已知文字 | 記錄 | B 優化 |
| R4 | 成本 | $/min | 記錄 | B 優化 |
| R8 | 整合成本 | 質化 | 記錄 | B |

## 5. 階段 A 具體做法

**A-1 鎖評分器（確定性 unit，不需音檔、不需 LLM）**
測 `scorer(target, spoken_text)`：
- 全對 spoken==target → 100%
- 漏 K 字 → (N−K)/N、該位置 missing
- 同音/異調（食/十、浩/好）→ forgiven
- 真錯字（足/出）→ wrong
- 字序對調（風和日麗→日麗風和）→ 記錄它怎麼判（過罰?）
- 重複字（避免 ghost-green）、漏字後 resync（不 cascade）
- >100% 不可能、長段不截斷
- 方大哥 STT 文字 → ~98%（已驗前/後端各 98.1%）

**A-2 自錄真音 sanity（少量、人判對照）**
- 自己/實習生錄 5-10 段（≥2 篇課文 × 全對 + 故意錯）
- 跑 音檔→STT→評分→看顯示分數
- 每段標「人判應得幾分」，比對系統分數，差 > ±5% 就查
- 用現成 STT（Gemini batch，已夠準）即可，先不糾結引擎

**A-3 收斂上線**
- LiveTutor + FullReading 都接同一份確定性評分（移除後端 Gemini 逐字 diff 覆蓋）
- 上一版給方大哥/教授複測

## 6. Caveats
- 自錄者咬字比真實國小生清楚 → 階段 A 是「邏輯可信」不是「真實 robustness」；真實要階段 B 人聲集
- STT 有非確定性 → STT 層看區間，**評分層必須 =0（確定性）**
- 「不確定就寬鬆」是教學取捨：寧可少扣不可錯扣

## 7. 技術選型 A/B — 4 個比較軸（**現在就能測，與階段 A 並行，不擋 v1**）

技術選型不必等階段 B。以下每軸標：✅ 現在跑得動 / ⚠️ 需小瀏覽器 PoC / 📐 設計決策（非單純量測）。固定其他軸、一次只變一軸才比得乾淨。

### 軸 1：STT 引擎/品牌 — Azure vs Gemini（vs Web Speech）
- **引擎準度/成本（✅ 現在）**：Azure STT(REST/本機 key) vs Gemini batch(staging) 餵同一 TTS 音檔 → R2 字準 / R4 成本 / R1 延遲。背景實驗進行中。
- **前端即時延遲（⚠️ 需小 PoC）**：Azure 瀏覽器 SDK / Gemini Live 的「邊讀邊轉 ~0 等待」要一個瀏覽器 PoC 驗（headless 跑不了）。先用引擎準度數據 + 單價，延遲用一支 PoC 補。
- 候選：Gemini batch（現用）/ Azure 即時 / Gemini Live / Web Speech。

### 軸 2：評分引擎 — 確定性 LCS+同音 vs LLM 逐字 diff（✅ 現在）
- 已有：確定性 = 98.1%（穩定）；LLM 逐字 diff = 39~58%（截斷+浮動）。**這軸結論最明確：確定性勝**。補 R5 確定性(variance=0 vs LLM 浮動)、R6 robustness(長段不截斷)。

### 軸 3：其他演算法差異（✅ 現在，unit）
- 同音寬鬆度（嚴格同音 vs 含異調 vs 近音）、normalize 選擇（數字/標點/注音）、LCS tie-break、字序對調處理 → 用已知案例 unit 測，看 R3 準度 + R7 誤判（過罰/遮真錯）。

### 軸 4：前端送件 vs 後端送件（📐 設計 + ⚠️ 延遲量測）
- 不是單一量測，是架構取捨：**前端送**（瀏覽器即時 STT/評分，~0 延遲、但分數客戶端算可能漂移/被改）vs **後端送**（上傳 audio→後端 STT+評分，單一真相可稽核、+round-trip~200ms+STT）。
- 可量：後端 round-trip 延遲（✅）；前端即時延遲（⚠️ PoC）。可決：單一真相要不要（📐，#2266 已傾向後端評分）。

### 呈現
4 軸結果 → §5.5 HTML 儀表板：每軸一個比較區塊（選項 × R1-R8），標「現在數據 / PoC 待補 / 設計決策」，並給「這段該選哪個 + 為什麼」。
matrix 落地：C1 Gemini batch 全文(基準) / C2 Gemini batch 逐段 / C3 Azure STT / C4 Gemini Live(N/A headless) / C5 Web Speech(N/A headless)。
