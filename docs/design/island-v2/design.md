## 1. 2.5D RPG 模式（PRD §2）

### 1.1 參考了哪些既有遊戲，以及誠實的查核結果

Young 點名要參考「寶可夢、動森、ZELDA 系列的俯視段」。查證後**不是每一個都如外界想像的是嚴格的等角投影**，誠實列出：

| 參考對象 | 查核結果 | 來源 |
|---|---|---|
| **經典 2D 薩爾達傳說**（超任《眾神的三角力量》、GB《織夢島》等，時之笛之前） | ✅ **依據，官方一手來源**——任天堂官方訪談中，系列製作人青沼英二明確說明這些作品用的是「俯視＋斜角」（overhead, diagonal angle view），**不是**正俯視；後來的《眾神的三角力量 2》才刻意改成「正俯視」（direct overhead），專門為了讓牆面合體機制可行 | 任天堂官方 Iwata Asks，已驗證可連線：<https://www.nintendo.com/en-gb/Iwata-Asks/Iwata-Asks-The-Legend-of-Zelda-A-Link-Between-Worlds/The-Legend-of-Zelda-A-Link-Between-Worlds/3-Direct-Top-down-View/3-Direct-Top-down-View-831979.html> |
| 同一系列的鏡頭分析 | ⚠️ 推論／二手，但方向一致——有分析文章提出「薩爾達視角」一詞，指出嚴格來說《眾神的三角力量》**沒有單一數學透視**，是物件各自用最清楚的角度拼出來的（地板俯視、牆面側視混合） | 遊戲設計分析部落格，已驗證可連線：<https://andrew-strickland-qnec.squarespace.com/blog/2011/3/29/a-link-to-some-perspective.html> |
| **寶可夢**（Gen 1-5 2D 時代） | ⚠️ **待查**——沒有找到官方逐字文件說這是「等角投影」。社群技術討論描述成「俯視角，精靈圖用約 45 度角模擬深度」的**視覺錯覺**，不是嚴格的等角相機數學；中文/英文維基的「等角電玩圖學」條目**沒有**把寶可夢列為案例 | 社群討論串（證據強度中等）：<https://www.pokecommunity.com/threads/pokemon-classics-gen-1-4-camera-view.455978/> |
| 寶可夢（3D 時代，劍盾） | ✅ 依據——官方描述是「固定鏡頭、第三人稱視角，部分區域允許自由轉動鏡頭」，**不是**等角 | 維基百科條目（有外部引用佐證）：<https://en.wikipedia.org/wiki/Pok%C3%A9mon_Sword_and_Shield> |
| **動物森友會**（集合啦！動物森友會） | ⚠️ **待查**——沒有找到官方把鏡頭定義為「dimetric/isometric」的聲明。媒體報導描述成「固定角度的 3D 鏡頭，有限的垂直傾斜/側移」，並提供一個「GameCube 視角」切換選項讓畫面更接近早期作品的俯視感，但沒有任何一份是官方技術文件 | 媒體報導（已驗證可連線）：<https://www.destructoid.com/animal-crossing-new-horizons-has-an-option-for-the-gamecube-camera-view/> |

**結論（依據＋推論）**：喝采島 v2 的「斜俯視固定鏡頭」最站得住腳的真實先例是**經典 2D 薩爾達系列的「俯視＋斜角」**（官方一手來源確認），不是寶可夢或動森（兩者都沒有查到官方逐字定義鏡頭數學）。技術實作上，three.js 做這種「斜俯視固定鏡頭」是業界常見手法——用 `PerspectiveCamera`（不是真的 `OrthographicCamera` 等角）固定在一個高仰角＋固定距離，跟著角色水平位移但角度不變，這個做法沒有單一官方出處可引，屬於**業界常識性技術手法（推論）**。

**給 Young 的白話版**：不用糾結「這是不是真的等角」，薩爾達 1986-2013 那一整條線（時之玉前）走的都是「鏡頭斜斜往下看，但不是從正上方看」——這正是 PRD 要的感覺，而且是三者裡唯一有官方親口證實的。

### 1.2 鏡頭角度（技術規格）

| 參數 | 建議值 | 理由 |
|---|---|---|
| 相機類型 | `THREE.PerspectiveCamera`（沿用既有單課島的相機類型，不換成 Orthographic） | 既有程式碼（`createIslandWorld.ts`）整個地形、建築、陰影系統都是為透視相機調的光影參數，換成正交相機要重新調整整批材質與陰影範圍，成本不對等；斜俯視的「感覺」主要來自角度與距離，不是嚴格等角 |
| 俯角（pitch） | 固定 **50°–60°**（從水平線往下算） | 比既有第一人稱出生仰角 15°（`SPAWN_PITCH`）陡很多——2.5D 模式要看到路徑與建築頂部的相對關係，不是看向遠方地標；薩爾達式「斜角俯視」落在這個區間（推論，依常見同類作品截圖反推，無單一引用） |
| 水平旋轉 | 固定（不可由玩家旋轉），建議跟現有 `ZONE_PATHS` 的主要延展方向對齊，讓路徑在畫面上盡量呈現左下→右上的對角線構圖 | 對角線構圖比正南北/正東西更容易同時看到「目前站」與「下一站」兩個節點，是常見的關卡地圖排版手法（推論） |
| 鏡頭跟隨 | 角色移動時鏡頭保持固定的相對位移（距離、角度都不變，只有位置跟著平移），用既有 `threejs-game-scene` 建議的指數平滑 `t = 1 - exp(-rate * dt)`，不要用固定 `lerp` 係數 | 依據：`gamedev-camera-systems`（已驗證的通用技巧），固定係數在不同裝置幀率下手感不一致 |
| 縮放 | 不開放，固定焦距——跟第一人稱模式不同，2.5D 模式的賣點是「永遠看得到路徑全貌」，開放縮放會讓低年級學生意外縮到看不懂畫面 | 推論，呼應 `ref-nielsen-norman-children-ux` 的「兒童對意外狀態的容忍度低」原則 |

### 1.3 路徑怎麼畫（重用既有資料，不重新發明）

**關鍵發現（依據，已讀程式碼確認）**：單課島的「既定路徑」**已經存在**，不需要新建——`islandTemplate.ts` 的 `ZONE_PATHS`（三段區域的控制點陣列）跟 `createIslandWorld.ts` 用同一組控制點組出 `THREE.CatmullRomCurve3`，並沿著這條曲線鋪出一整排石板路（`paths.forEach(...)` 那段，見 `createIslandWorld.ts:127-137`）。這條路**在第一人稱模式裡本來就看得到**，只是沒有被當作「2.5D 模式的移動載體」使用。

v2 的路徑設計：

1. **沿用同一條 `CatmullRomCurve3`**，不另外畫一條新路——兩個視角模式共用同一份地形資料，保證「第一人稱模式走過的路」跟「2.5D 模式看到的路」是同一條，不會因為維護兩份路徑資料而互相漂移
2. **2.5D 模式新增的視覺層**：在既有石板路上疊一條「已完成路段 vs 未完成路段」的材質差異——已走過的路段用飽和色（配合該區域的解鎖狀態），未走過的路段用霧化/半透明材質，讓玩家一眼看出「我走到哪裡、還剩多少」
3. **「下一站」的路段**額外加一層動態材質（例如沿路徑流動的光紋，複用既有 `gold` 材質常數的 emissive 做法，見 `islandBuildingShapes.ts` 的 `gold = material(0xe7bb6b, { emissive: 0xc98626, emissiveIntensity: 0.12 })`），比終點建築本身的發光更早被注意到——這是把「地標優先於 UI 箭頭」的原則（見下一節）用在路徑本身，而不是疊加一個額外的 UI 剪頭精靈

### 1.4「下一站」怎麼提示：地標優先、UI 箭頭只能當輔助

**核心原則（依據，`ref-zelda-landmark-design`，已讀原文）**：
《上古捲軸 V》的指南針是反面教訓——玩家只盯著箭頭走，世界設計的意義因此被架空。《曠野之息》靠「大地標遠望可見」解決同一個問題，UI 指引只能當輔助不能當主力。

落地到喝采島 2.5D 模式的具體設計：

| 優先序 | 做法 | 對應原則 |
|---|---|---|
| ① 最優先：建築本身的輪廓與高度差 | 延用既有「港口燈塔」最高、其餘建築依序遞減的佈局（`buildingTopY` 已經算出每種建築的真實高度），2.5D 固定鏡頭下，下一站建築應該**在畫面構圖裡明顯比周遭元素突出**（高度或體積），不靠任何文字/圖示就看得出「那裡是個目的地」 | 三層地標法 |
| ② 次要：路徑本身的視覺差異（見 1.3） | 已走過/未走過/下一段的材質差異，玩家順著路看過去自然找到下一站 | 地標優先於 UI 箭頭 |
| ③ 輔助：一個很小的 HUD 指示（例如畫面角落一句話「下一站：字源館」+ 建築縮圖），**永遠不用動態箭頭指向**（箭頭正是天際指南針被批評的那種設計） | 文字說明可以幫識字中的國小生確認，但不能取代①② | 同上，UI 只能輔助 |
| ④ 刻意保留的「好奇心」設計 | 下下一站（再下一站）**不要**一開始就完全可見，用既有地形的小丘／建築遮一部分視線（三角形遮擋視線原則），讓玩家有「往前走會看到什麼」的期待，而不是一次把全部路徑攤開變成「要走完的清單」 | 三角形遮擋視線 |

⚠️ **這條直接回應 PRD §1 的第 4 點「每座島長得差不多沒有劇情」背後更深一層的風險**：如果只是把現有路徑從側面搬到上方看，整座島仍然可能只是「要走完的清單」——根因不是視角不夠酷，是**地標密度與路徑蜿蜒程度**（見 `ref-zelda-landmark-design` 的核心主張）。2.5D 視角上線時應該同時檢查：① 密度（建築之間有沒有讓人想多看一眼的細節，交界處細節檢查法）② 路徑是不是刻意蜿蜒而非直線。這兩件事視角模式本身解決不了，需要在美術/關卡佈局階段一起做。

### 1.5 站與站之間的過場

**開場**（進入整座島）：套用既有 `game-cinematic-opening` 的冷開場原則——先給一個有張力的畫面（例如島嶼甦醒的光點聚集），標題字卡晚一點出現，不要「黑畫面 → Logo → 選單」。

**站與站之間**（點擊下一站 → 角色走過去 → 抵達）：

1. **走路本身**：角色沿 `CatmullRomCurve3` 用時間參數 `t` 遞增（`curve.getPointAt(t)`，比既有 `pointOnPolyline` 的分段線性插值更平滑，因為是沿真實曲線而非折線），移動時鏡頭保持 1.2 節的固定相對位移跟隨；角色朝向用曲線在該點的切線方向（`curve.getTangentAt(t)`）
2. **進入建築（室內場館，見 §2）的轉場**：**不要**用「黑底 + 發光」收尾——這正是本次哈維材料已經點名的反模式。改用「世界裡本來就有的物件在做轉場動作」：
   - 依據（已驗證來源）：`gamedeveloper.com`〈Resident Evil - Loading Screens and Doors〉<https://www.gamedeveloper.com/design/resident-evil---loading-screens-and-doors> ——loading 不是抽象黑畫面，是世界裡本來就有的物件（開門、翻書）在做動作
   - 落地：每種建築類型配一個對應的「進入動作」——書卷長廊＝翻開一本攤開的書、回音劇場＝布幕拉開、字源館/工匠作坊/知識實驗室＝推開一扇門、推理事務所＝百葉窗拉下再拉起（偵探事務所的經典意象）。這些動作本身**就是**轉場的全部內容，不疊加額外的黑幕
3. **完成一站、碰到下一個未解鎖地標**：沿用既有 `game-juice-motion` 的分級——完成一個小站用中分級回饋（2-3 個通道），完成整座島（最後一站）用大分級（4-8 個通道疊加），不要每一站都放最大的特效（分級錯了會讓真正的里程碑時刻被稀釋，見 `game-juice-motion` 的 Milestone Unlock 段落）

### 1.6 架構提案：`views/` 模組，跟 `themes/` 同一套哲學

PRD §2 提到「視角模式是……的新擴充點（`views/<id>.ts`）」。經檢視現有程式碼，**單課島引擎目前沒有這個抽象層**——第一人稱的相機/移動邏輯直接寫死在 `createIslandWorld.ts` 裡。建議：

```
frontend/src/pages/lab/island/
├── views/
│   ├── firstPerson.ts     ← 現有邏輯搬過來（WASD、spawnPoint.ts 整套、碰撞）
│   ├── isometric.ts       ← 本文件 §1 的 2.5D 邏輯（固定鏡頭、沿曲線走、點擊觸發）
│   └── index.ts           ← VIEWS 登錄表，`IslandView` 介面
```

`IslandView` 契約草案（呼應 `archipelago-module` 的 `ArchipelagoTheme` 寫法）：

```ts
interface IslandView {
  id: 'first-person' | 'isometric';
  createCamera(ctx: SceneCtx): THREE.Camera;
  updateCamera(ctx: SceneCtx, dt: number, player: PlayerState): void;
  handleMoveInput(ctx: SceneCtx, input: InputState, dt: number): PlayerState;
  // 2.5D 模式用：點擊「下一站」觸發沿路徑移動；第一人稱模式這個函式可以是 no-op
  travelToStop(ctx: SceneCtx, stop: IslandStop): Promise<void>;
  renderPathHint(ctx: SceneCtx, stops: IslandStop[], unlockedIndex: number): void;
}
```

這跟 `archipelago-module` 的「骨架不變、換皮膚」是同一個精神，差別是這裡換的是**操控與鏡頭**，不是視覺皮膚——兩者可以共存：將來某個主題皮膚（天空島／海底）疊加在任一個 `view` 上都要成立，`view` 決定「怎麼操控」，`theme`（如果將來單課島也要换皮膚）決定「長什麼樣子」，互相正交。

**不建議做的事**：不要為了 2.5D 模式新開一條平行的「視角模式只服務單課島」的資料流——`IslandStop` / `STEP_BUILDING_META` / `buildingTopY` 這些既有資料結構兩個 view 都要能讀，`views/` 底下的檔案只處理「鏡頭與移動」，不複製一份地形/建築資料。

## 2. 室內場館（PRD §3）

### 2.1 哪些站該做成室內，判準與結果

**判準（推論，依既有 15 種站的性質分類）**：這一站的學習活動是「安靜坐下來做一件事」（標注、朗讀、查字源、造句、解謎、查資料）→ 室內；這一站本身需要被遠處看見當地標，或帶有戶外/公共場所的意象（牧場、碑林、擂台、瞭望台）→ 保留戶外，維持它在 `ref-zelda-landmark-design` 地標系統裡的功能。

| 站 id | 現名 | 室內/戶外 | 室內新名（若改） | 理由 |
|---|---|---|---|---|
| `lesson-intro` | 港口燈塔 | 戶外 | — | 全島最高地標，`spawnPoint.ts` 已有一整組幾何計算綁定它的高度，不能動 |

### 2.2 工程邊界（重要：把風險鎖在最小範圍）

**室內化不改動既有的外觀定位與觸發半徑系統**——這 6 種建築的「外殼」（地基座標、觸發範圍、`buildingTopY` 高度資料）完全不變，玩家從外面看到的仍然是同一棟建築、同一個觸發點。室內化**只新增**一個「進入後切換到室內子場景」的行為，入口＝既有的「發現新去處」觸發卡點「進入」按鈕。這樣兩個視角模式（第一人稱／2.5D）都能直接受益，不需要各自重做一次。

### 2.3 室內格局（參考 PRD 描述的「斜俯視辦公室」調性）

每個室內場館共用一個「殼」（parallel to `buildStationGroup`，可以叫 `buildVenueInterior`）：

```
地板：木地板材質（淺色，呼應既有 `wood` 材質常數 0x80634d）
分區地毯：一塊顏色跟該能力家族（見 §3）對應的地毯，標出「活動區」範圍
牆面看板：一面可以放置圖文的看板（內容依站點類型客製，見下表）
光源：單一吊燈/立燈（不要用即時陰影光源，沿用 `threejs-game-scene` 的 iPad 效能建議，用貼圖假陰影）
```

| 場館 | 核心家具/裝飾 | 可互動物件（點擊有回饋，不一定要改變任何資料狀態） |

### 2.5 室內的鏡頭怎麼處理（兩個視角模式各自的做法）

- **2.5D 模式**：沿用同一顆固定角度相機，只是把距離拉近、範圍縮小成室內尺度；靠近鏡頭的那一側牆面做半透明/隱藏處理（業界常見的「近牆剔除」手法，多數俯視角 RPG 採用，無單一引用來源，標推論）
- **第一人稱模式**：室內是一個尺度縮小的獨立場景，直接沿用既有 `computeSpawnFacingLighthouse` 同一套「依建築真實 bounding box 算出生距離」的邏輯，只是套用在室內家具的 bounding box 上，不需要另外發明一套算法

### 3.2 三階命名規則

**規則（推論，延續 v1 白名單精神並加一條新規則）**：

1. 每個能力選 **2-3 個「語意本身就是該能力具體動作」的既有詞彙/成語**，由淺入深排成基礎/中階/進階，讓學生看到名字就約略猜到這個能力在做什麼——這是 v1「白名單：物品/自然/動作/正向品質」精神的延伸，新增一條篩選：**詞彙必須跟該能力的認知動作直接相關**，不能只是泛用正向詞
2. 三階語意要呈現「同一能力由淺入深」的脈絡（例如：拼湊線索 → 抽絲剝繭 → 洞察先機），不是三個不相干的詞彙硬湊
3. 一律套用 v1 既有黑名單（死亡/暴力/負面情緒字）與機制性規則（2-4 字）—— 完整名單見 `docs/design/word-babies/design.md` §9
4. 進階階名字優先選**更書面/更高級感的成語**，呼應常見進化鏈「最終型態辨識度最高」的命名慣例（推論，依常見同類遊戲觀察，無單一官方出處）

### 3.3 遷移設計：不動既有 100 隻，加法不減法

**約束（來自 PRD）**：不能讓學生已經擁有的寶貝消失。延伸出一個更嚴格的隱藏約束：**也不能讓已擁有的寶貝突然餵不飽**（如果把舊的「閱讀理解」口味拆成 9 個細項卻沒接相容層，舊寶貝的飲食會找不到對應碎片）。

**遷移方案（依據既有 schema 設計，純加法）**：

1. `babies.json` 既有 100 筆（id/name/rarity/diet_flavors/stages）**完全不動**
2. `fragments.json` 的 `flavor_families` 從 5 個擴充為 **5 個舊口味（相容保留）＋ 11 個新細項口味（給 v2 新物種用）**；「文言文」這個舊口味字串直接沿用（新的「文言解碼力」剛好對應同一組 classical 站，不用另開新 key）
3. **相容層（服務層聚合函式，不改資料表結構）**：任何時候要判斷「這個學生的碎片庫存夠不夠餵一隻要求『閱讀理解』飲食的舊寶貝」，改成把 9 個新細項口味（A/B/C/D/E/F/G/H/I 對應的碎片，不含文言解碼力，因為它沿用舊「文言文」key）的庫存**加總**當作「閱讀理解」庫存——玩家餵食介面上，舊寶貝顯示「閱讀理解」這個籠統選項，背後可以用任何一種細項碎片扣款
4. `StudentStationRewardLog` 判定完成 `comprehension`/`keypoints-table`/`spotlight` 站時：改成先查該課的 `reading_strategy` → 查表 3.1 → 得到一個具體能力（如「推論力」）→ 這次掉落的碎片 `fragment_flavor` 寫**具體值**（如「推論策略」），不再寫籠統的「閱讀理解」
5. 後端已有的 2 課 `reading_strategy` 空值 → fallback 寫回舊的籠統「閱讀理解」（走相容層，不特別配到任何細項），等課程資料補值後再重分類，不是永久例外
6. v2 新增物種的 `diet_flavors` 直接寫具體細項值（如「推論策略」），讓新寶貝有「我專精某個能力」的精準感——**不需要一次做滿 14×3=42 隻**，可以先每個能力做 1 隻（14 隻）起步，之後再補滿三階

**正式接線前的必查清單**：① 新 14 個名字（§3.2 表）要再跑一次跟既有 100 隻的字面查重 ② 相容層聚合函式要有單元測試，覆蓋「舊寶貝用任一種新細項碎片都餵得動」③ `StudentFragmentWallet` 的 `flavor` 欄位目前是 `String(20)` 不是 ENUM（見 `word_baby.py` 註解，刻意設計成這樣方便擴充），新增 9 個字串值不需要 migration，但要在應用層驗證清單裡加上去

| 三階造型差異 | 基礎階＝體型最小、造型最簡化（呼應幼體意象）；中階＝加入 1-2 個代表該能力的道具/配件；進階＝完整造型＋發光/特效細節，跟現有「傳說寶」級的視覺規格（`babies.json` 裡 `legendary` 稀有度那幾隻）同一個等級 |
| 命名標籤同步 | 每張圖檔名建議 `{ability_id}_{tier}.png`（如 `inference_tier2.png`），方便美術資產跟 `ability_id` 直接對應，不需要額外一張對照表 |

### 4.2 參觀同學島的方式

1. 入口：從既有的班級名單頁（教室/班級既有資料結構已經是 classroom-scoped，不新建跨班機制）選一位同班同學 → 進入該同學的「我的島」**唯讀模式**
2. 唯讀模式下可以：走動、看裝飾、看寶貝圖鑑、看徽章展示

4. 範圍限制：**只能參觀同一個班級**的同學（沿用既有 team-arena/PK 等功能的班級邊界慣例），不開放跨班或全校

### 4.3 未成年隱私邊界

| 內容 | 預設可見範圍 | 開放條件 |
|---|---|---|
| 裝飾、徽章、寶貝圖鑑 | 同班同學可見（成就型內容，鼓勵良性比較） | 一律開放，無需額外設定 |

## 5. 我的島：裝飾與上傳筆記（PRD §7）

### 5.1 新概念：獨立的「我的島」（home island）

PRD §7 描述的是「累積成就、可以裝飾、可以放筆記」的個人空間，這**不等於**任何一座單課島（每座單課島綁定一篇課文），也不等於群島地圖（`archipelago` 看的是課程清單）。建議新增**第三種場景類型**：

```
單課島（per-lesson）  —— 一篇課文一座，學完就留在那裡
群島地圖（archipelago）—— 看「我有哪些課程島」的總覽地圖
我的島（home）         —— 學生唯一一座，放成就/裝飾/筆記，不綁定任何單一課文（新）
```

「我的島」的地景可以直接重用 `archipelago-module` 的某個主題皮膚當底（例如預設用「海島」主題的地面/海洋/光照），只是上面擺的不是課程小島，而是裝飾物件。

### 5.2 裝飾規則

- 擺放範圍：「我的島」上劃定一塊可裝飾區域（避免學生把裝飾物蓋住既有的成就展示牆）
- 擺放方式：網格吸附（grid-snapped），避免學生把物件疊得亂七八糟導致畫面雜亂或效能問題
- 可擺放的物件 = §4 表格裡已解鎖的所有裝飾／地標，無上限（但畫面可能需要分頁/分區呈現，若物件數量成長到一定量）

### 5.3 上傳筆記呈現

- 文字筆記：顯示在「筆記看板」裝飾（§4 筆耕力中階解鎖）上，類似便利貼／卡片牆
- 照片筆記：顯示為掛在看板上的一張小照片，點擊放大
- 老師視角：可以看到自己班上所有學生的筆記（不受分享開關限制），並有一個「標記分享」的按鈕

## 6. 劇情模板（PRD §8）

### 6.1 五種骨架

| 劇情類型 | 開場 | 每完成一站推進 | 結局 |
|---|---|---|---|
| **修復** | 島上一個地標（例如中央雕像/鐘樓）出現裂痕，旁白說明「這裡本來不是這樣的」 | 對應裂痕視覺減少一格（貼圖從裂痕→修補→完工），伴隨呼應該站主題的一句肯定語 | 地標完全修復並發光，旁白總結「你修復了……」|
| **魔王** | 島上出現一團擬人化的「困境影子」（迷霧巨影，**非暴力造型**，代表課文裡的某種困難或誤解，不是邪惡怪物）| 影子縮小/弱化/透光一點，顯示「你看穿了一個謎團」| 影子消散或變回友善的樣子（化解而非打倒），給予握手/擁抱動畫 |
| **尋寶** | 一張古地圖/卷軸攤開，標示「藏著一件失落的智慧寶物」| 解鎖地圖上一個藏寶點，拾獲一枚「智慧勳章」碎片 | 所有勳章拼成完整寶物（例如發光的古書），寶物開啟顯示這堂課的核心金句 |
| **偵探** | 島上出現一個待解的謎團，玩家化身偵探接案 | 收集到一條線索（釘上案情看板），旁白給出階段性推論 | 線索串起真相大白，案情看板呈現完整因果關係 |
| **比賽** | 介紹一場即將到來的「島嶼競賽」，主角報名參加 | 累積「訓練點數」，角色裝備視覺升級一次 | 結果揭曉——刻意不強調名次，呼應「全力以赴比輸贏更重要」的價值，給予「喝采」動畫 |

**兒童情緒安全檢查（呼應既有 `~/.claude/skills/game-academy/test-list.json` 標 red 的缺口，本文件先用常識把關，正式上線前仍建議找兒童心理專業複核）**：「魔王」刻意避開暴力擊倒框架，改用「化解心結」；「比賽」刻意不強調輸贏，呼應 PRD 開場範例課文〈贏得喝采的輸家〉本身的核心價值——這兩處是本學院目前對兒童情緒安全缺口（`test-list.json` 標 red：「輸了會不會對國小學生造成過大的挫折感」）能做的最大努力，不等於已經過兒童心理專業驗證，正式上線前建議補一次專業複核。

### 6.2 指派規則：依 grade/category，優先序分層，覆蓋全部 179 課

```
① grade == "文言文"（12 課）        → 尋寶
② grade == "品格教育"（15 課）      → 修復
③ 其餘 152 課，依 category：
   category == "Science"（71 課）   → 偵探
   category == "Fable"（56 課）     → 魔王
   category == "History"（16 課）   → 比賽
   category == "Daily"（5 課）      → 尋寶
   category 與 genre 皆空值（4 課）  → 比賽（預設，理由見下）
```

**為什麼是這個優先序**：①②先處理有「特殊年級標籤」的課（文言文、品格教育），這兩組課的內容性質跟一般單元課文差異最大，優先給它們最貼合的劇情；剩下的課才看 `category`（內容類別，比 `genre` 文體更貼近「故事感」）。`category` 皆空值的 4 課（如「牧羊少年的逆轉勝」）語意本身多半偏勵志/逆境主題，比賽骨架（資格賽→晉級→結果）最適合套用在不特定文體的勵志故事上作為通用殼，故設為 fallback 預設值。

**分布結果（覆蓋全部 179 課，無遺漏無重複）**：

| 劇情類型 | 課數 | 組成 |
|---|---|---|
| 修復 | 15 | 品格教育 15 |
| 尋寶 | 17 | 文言文 12 ＋ Daily 5 |
| 偵探 | 71 | Science 71 |
| 魔王 | 56 | Fable 56（remaining pool）|
| 比賽 | 20 | History 16（remaining pool）＋ 空值 fallback 4 |
| **合計** | **179** | ✓ |

### 6.3 五個真實課程的套用示範

**修復 — 體-L1〈心，也要一起練〉**（品格教育，`reading_strategy`＝品格力──自我覺察）

> 開場：「歡呼廣場上的那座『勇氣鐘』出現了裂痕，鐘聲變得沙啞——因為好久沒有人好好練習『覺察自己的心』了。」
> 推進：完成每一站後鐘的裂痕修補一點，旁白：「你剛剛練習了一次自我覺察，鐘聲回來了一點點。」
> 結局：「勇氣鐘完全修好了，敲響的瞬間，全島都聽到了——原來心也要像運動一樣，一起練。」

**魔王 — G4-L1〈贏得喝采的輸家〉**（Fable，記敘文，描寫戴資穎輸球仍贏得掌聲）

> 開場：「回音劇場後方，籠罩著一團『自我懷疑的迷霧巨影』——它低語著『你輸了，你不夠好』。」
> 推進：讀完全文（書卷長廊）→ 巨影變小一圈；朗讀關鍵段（回音劇場）→ 巨影開始透出光；查完詞彙/重點（字源館/地圖塔）→ 巨影輪廓越來越清晰；完成理解題（推理事務所）→ 看懂巨影其實是自己的倒影
> 結局：「原來那團迷霧不是怪物，是你自己。她輸了比賽，卻贏得了全場喝采——因為她沒有被那團迷霧擊倒。你也一樣。」

**尋寶 — 文-L2〈文言文怎麼讀？以鞭虎救弟記為例〉**（文言文，`reading_strategy`＝文言文閱讀策略──如何讀懂文言文）

> 開場：「原文閣深處藏著一捲古老卷軸，上面只寫著『讀懂文言文的智慧，藏在這座島上』。」
> 推進：每完成一站（讀原文／對句配對／字牌換說法／自我挑戰）→ 解鎖地圖上一個藏寶點，拾獲一枚「智慧勳章」
> 結局：「四枚勳章拼成一本發光的《鞭虎救弟記》，翻開第一頁——你已經能讀懂古人的句子了。」

**偵探 — G4-L5〈這是什麼「意思」？〉**（Science，說明文，`reading_strategy`＝推論策略──推論代名詞）

> 開場：「島上的字典館出了一樁怪案——好幾個詞的『意思』不翼而飛，只留下一堆看起來很像的句子。」
> 推進：每完成一站找到一條線索（釘上案情看板），旁白逐步推理「這個詞在這裡的意思，應該是……」
> 結局：「案情看板串起所有線索——原來同一個字，在不同句子裡，『意思』真的不一樣。案子結了，你是個很棒的偵探。」

**比賽 — G5-L17〈牧羊少年的逆轉勝〉**（category/genre 皆空值，`reading_strategy`＝品格力──認識自我，fallback 規則命中）

> 開場：「喝采島今年要辦一場『逆轉賽』，牧羊少年在海報前猶豫了很久，最後還是報名了。」
> 推進：每完成一站累積一枚訓練勳章，角色裝備（牧羊杖/披風）逐漸升級
> 結局：「比賽結果不是重點——牧羊少年看見自己從『猶豫』走到『報名』、從『報名』走到『完賽』，看台上的掌聲，是為了這段逆轉喝采。」

### 6.4 跟既有「開場白」系統的接線（低工程量的關鍵）

**依據（已讀程式碼）**：`islandTemplate.ts` 已經有 `buildOpeningForTitle(title)` 產生通用開場白，`islandData.ts` 的 `OPENING_20011` 是手刻範例。建議：擴充 `buildOpeningForTitle` 成 `buildOpeningForStory(title, storyType)`，依 `storyType` 套用 §6.1 骨架的開場句型模板（模板裡嵌入課名，不需要為 179 課各自手寫），**每完成一站的推進旁白**同理，掛在既有的完成站回呼（`notifyIslandStepDone` 之後）插入一句依 `storyType` 查表產生的句子。這是**純資料+模板**的工作，不需要新美術資源，是 §7 批次建議把它排在第二批（僅次於 2.5D 模式本身）的原因。

## 7. 實作分批建議

**排序原則**：第一批固定（PRD 已驗收）；其餘依「學生最有感、工程量最小」排序，且考慮相依關係（例如「賦能解鎖」必須在「裝飾擺放系統」之後）。

### 批次 1（固定）：2.5D 模式 + 即時回饋

對應 PRD §9 的驗收，照抄：

1. Given 學生進入一座課程島，Then 預設是 2.5D 斜俯視、固定鏡頭，畫面上清楚標出「下一站」
2. When 點下一站，Then 角色沿路徑自動走過去並進入該站；無法走到路徑以外
3. Given 在學習頁完成一個站，Then 當頁就跳出碎片／寶貝提示，不必回島
4. 1280 與 390 寬：0 頁面錯誤、無水平捲動
5. 第一人稱模式仍可從設定切換，且行為不變

### 批次 2：劇情模板文字層

**理由**：純資料＋模板，不需要新美術資源，重用既有 `buildOpeningForTitle` 架構（§6.4），學生感受到的變化是「每座島都有不一樣的故事」——PRD §1 第 5 點點名的核心問題，用最低成本解決。

- Given 一座課程島依 §6.2 規則判定出劇情類型，When 學生進入該島，Then 開場白內容對應該劇情類型的骨架且包含課名
- Given 學生完成任一站，When 回到島上，Then 看到一句對應該劇情類型與完成進度的推進旁白
- Given 全部 179 課各自跑過劇情指派規則，Then 每課恰好得到 1 種劇情類型，加總等於 179（回歸測試鎖住這個不變量）

### 批次 3：能力寶貝 v2 判定邏輯

**理由**：中等工程量（後端判定邏輯改動＋相容層），但直接提升每次「遇到寶貝」的教育意義——這是 PRD 提到小莊「現在看不出來我養的東西長什麼樣」痛點背後更深一層的「看不出跟學習的關係」。

- Given 學生完成一個理解類站（comprehension/keypoints-table/spotlight），When 該課有 `reading_strategy` 值，Then 掉落的碎片 flavor 對應到 §3.1 查表結果，不是籠統的「閱讀理解」
- Given 一隻舊版（v1）寶貝要求「閱讀理解」飲食，When 玩家用任一種新細項碎片餵食，Then 扣款成功，升級邏輯不受影響（回歸鎖：既有 100 隻寶貝全部可餵食）
- Given `reading_strategy` 為空值的課，Then 掉落碎片 fallback 為舊的「閱讀理解」

### 批次 4：室內場館（共用殼）

**理由**：先做 6 種場館共用的室內殼模板（木地板＋地毯分區＋單一光源），驗證「進入建築→室內子場景→離開」整條轉場邏輯可行，不急著做逐站客製家具（那是批次 7）。

- Given 玩家點擊 6 種室內站之一的「進入」，When 轉場觸發，Then 依該站類型播放對應的「世界內物件轉場動作」（翻書/拉幕/開門），不是黑底淡出
- Given 玩家在室內場景操作完成，When 點擊離開，Then 回到外部場景時角色位置與朝向跟進入前一致
- iPad 實機：室內場景的 draw call 數不超過既有戶外場景的預算（沿用 `threejs-game-scene` 效能檢查清單）

### 批次 5：我的島骨架 + 裝飾擺放

**理由**：新場景類型，中高工程量（新頁面/新場景/新資料表），是後續賦能解鎖與上傳筆記的地基，必須先做。

- Given 學生首次進入「我的島」，Then 看到一塊可裝飾的空地與既有成就展示（佔領紀錄、徽章）
- Given 學生已解鎖至少 1 項裝飾，When 嘗試擺放，Then 可以用網格吸附方式放置、旋轉、移除
- Given 裝飾擺放後重新整理頁面，Then 擺放狀態持久化（對應 §5.4 資料表）

### 批次 6：賦能解鎖串接

**理由**：建立在批次 3（能力判定）與批次 5（裝飾系統）之上，增量工程量低。

- Given 某能力達到中階，When 完成判定當下，Then 對應裝飾立即出現在「我的島」可擺放清單
- Given 某能力達到進階，Then 對應地標級裝飾出現，且視覺上明顯跟中階裝飾有差異（體積/發光）

### 批次 7：室內場館客製化

**理由**：在批次 4 的共用殼基礎上疊加逐站專屬家具與互動物件（§2.4 表），是美術與細節打磨階段，不影響核心玩法，排在功能性批次之後。

- Given 6 種室內場館，Then 各自至少有 §2.4 表列出的核心家具與 1 項可互動裝飾
- G7 逐畫面審查：桌機+手機，6 種室內場館各自截圖，核對「交界處細節」檢查法（`ref-zelda-landmark-design`）

### 批次 8：上傳筆記

**理由**：涉及檔案上傳、隱私開關、潛在的內容安全審核，工程與合規考量都比裝飾系統重，排在後面。

- Given 學生上傳一則文字筆記，Then 筆記出現在自己「我的島」的筆記看板，預設僅本人與老師可見
- Given 老師將某筆記標記為可分享，When 同班同學參觀該學生的島，Then 該則筆記可見；未標記的筆記不可見
- Given 學生嘗試上傳照片，Then 系統不保留地理位置等 metadata（工程落地時確認）

### 批次 9：參觀同學島

**理由**：依賴批次 5（我的島要先存在）與批次 8（筆記隱私規則要先生效），且是加分的社交功能，不是核心學習路徑，排最後。

- Given 學生 A 從班級名單選擇同班同學 B，When 進入 B 的「我的島」，Then 以唯讀模式呈現，無法編輯/留言
- Given A 在唯讀模式瀏覽，Then 只看得到 B 已公開的成就/裝飾，筆記只在 B 的老師標記分享後才可見
- Given 學生嘗試跨班查看他人島嶼，Then 系統拒絕（班級邊界檢查）
