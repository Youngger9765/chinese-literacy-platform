## 1. 一課一隻寶貝：遇見、命名、造型

### 1.1 遇見（Encounter）—— 進入那一課的當下，不是抽到的

**設計決策（推論，直接回應「不要點數升級跟點擊」）**：v1 的「遇到新寶貝」是**機率事件**（`_roll_encounter` 用 CSPRNG 擲骰，依稀有度分層抽，見 `word_baby_service.py:176-222`）——這套機制是「抽卡」，正好是 Young 要避免的「花時間在點數跟點擊上」的那種焦慮來源（抽不到會想再刷一次）。

閱讀寶貝反過來：**species 跟課是固定的 1:1 關係，沒有抽卡**。「遇見」的意思是「這隻寶貝一直都在那裡等你，你進入這堂課的瞬間就看到牠」，不是「運氣好才遇到」。

| 時機 | 行為 | 依據 |
|---|---|---|
| 學生第一次進入某課的 `lesson-intro` 站 | 立刻顯示「遇見」動畫 + 寶貝基礎型態現身（不需要任何作答，進入即可見）| 呼應 Amy Jo Kim「第一次互動就要有正向回饋」—— 讓最沒有門檻的第一步（進入課程）就看得到寶貝，不是要先答對題目才看得到 |
| 同一課重複進入 | 直接顯示目前的進化階段，不重播遇見動畫 | 冪等，沿用 v1 唯一鍵精神，寫進 §7 全新成長紀錄表（不是 v1 的表本身，v1 已整套移除）|

**跟 lesson-intro 既有特例完全對齊**：`learning_step_progress.py:293-298` 已經把 `lesson-intro` 定義為「這一課有任何一次 step_progress 儲存就算完成」的特例（不要求學生在那個步驟做出「完成」動作）——閱讀寶貝的「遇見」就掛在同一個觸發點上，不需要新的判斷邏輯，是既有邏輯的直接複用。

### 1.2 命名——名字從「那一課自己的生詞」長出來，不是套用通用詞

**方法（推論，重用 v1 已驗證的白名單流程，`docs/design/word-babies/design.md` §9，只是把候選池從「全平台」縮小成「這一課」）**：

v1 的做法是：撈全平台 1,365 個生詞候選 → 白名單篩（物品/自然用單字、正向品質/動作用完整詞）→ 黑名單排除死亡/暴力/負面情緒字 → 人工複閱 → 選 100 個。這套篩選邏輯（`generate_config.py` 的 `NATURE_CHARS`／`OBJECT_CHARS`／`QUALITY_CHARS`／`QUALITY_WORDS`／`ACTION_WORDS` + 黑名單）**可以原封不動重用**，差別只在候選池範圍：

```
v1：   全平台 1,365 個候選 → 篩出 100 隻「通用寶貝」的名字（跟課無關）
閱讀寶貝：單一課的 vocab_definitions 生詞表（約 8-15 個/課）→ 用同一套篩選 → 這隻寶貝的候選詞
```

**具體規則**：
1. 取該課 `vocab_definitions.*.yml` 的生詞表（跟 v1 同一個資料來源，只是不跨課聚合）
2. 跑同一套白名單/黑名單篩選，若篩出的候選 < 3 個（短課、生詞少的課），往上一層取該課的「重點表」關鍵詞（`keypoints-table` 的資料）補足候選池
3. 三階各選一個，語意遞進（依 v1 的命名規則：基礎 → 中階 → 進階，由淺入深，同一能力脈絡）——因為候選詞來自同一課，天然就有「同一課的語感」，不需要額外設計脈絡規則
4. **候選真的不足 3 個的課（待查，需實測確認有多少課會落入這個情況）**：fallback 使用該課所屬 §6 劇情類型（修復/魔王/尋寶/偵探/比賽，見 `island-v2/design.md` §6.2 的分類結果，已覆蓋全部 179 課）對應的一組**劇情向通用詞**（例如「偵探」型課用「追問／抽絲剝繭／真相大白」這類跟偵探劇情呼應的詞），確保每一課都能三階命名

**為什麼不沿用 v1 的 100 個現成名字**：v1 已整套移除（見 §0.2.1／§5），即使保留也沒有對象可用——v1 的名字是跟「寶貝本身」綁定的設計，閱讀寶貝需要的是跟「這一課內容」綁定的名字，兩者命名目的本來就不同，重用的是**方法**，不是**成品**。

**查重**（沿用 `island-v2/design.md` §3.3 原本第 1 點的提醒，對象改為彼此）：179×3=537 個名字跑完生成後，必須彼此之間做一次字面查重，避免同名——不再需要跟 v1 查重，因為 v1 不存在了。

### 1.3 造型——家族×變體公式，不必手畫 179 張圖

**現狀查核（依據，已讀程式碼與資料；v1 本身已整套移除，這裡只借它的「做法」當參考，不是繼承它的美術資產）**：v1 原本的規劃是「這次先沿用現有 6 張通用圖循環使用（`baby_id` 取餘數對應）」（`design.md` §9），也就是說**v1 自己從來沒有做到 100 張專屬美術**，100 隻共用 6 張底圖——這個「少量底圖、靠程式規則組合差異」的精神直接可以借，不需要因為 v1 被刪除就連這個方法一起丟掉。閱讀寶貝如果要做到「179 隻看起來有差異」，不可能、也不需要一步到位做到 179 張全新原創圖——用公式組合出視覺差異比直接手繪划算，且美術資源目前還沒談成授權（`island-v2/design.md` §3.5 已標註小莊的圖「尚未取得授權」，PRD §4 也明寫「圖像先不處理」）。

**公式（推論，三層疊加，解決「179 隻要有差異又不必手畫 179 張」）**：

```
造型 = 體型家族（5 種，依劇情類型） × 色彩變體（8 種，依年級） × 招牌小物（依課程內容決定性選出）
```

| 層 | 決定依據 | 種類數 | 理由 |
|---|---|---|---|
| **體型家族** | 該課的 §6 劇情類型（修復／魔王／尋寶／偵探／比賽，`island-v2/design.md` §6.2 已覆蓋全部 179 課，決定性規則）| 5 | 劇情類型本身已經有明確的視覺意象（偵探＝風衣/放大鏡剪影、尋寶＝卷軸/勳章剪影），體型輪廓直接呼應劇情，不需要另外發明一套分類 |
| **色彩變體** | 年級（4-9 共 6 級 + 品格教育 + 文言文，共 8 組，沿用 `archipelago-clusters-prd.md` §2.1 現成的 8 群分類）| 8 | 色彩隨年級漸變（低年級較亮、較圓潤；高年級較深、較俐落），讓同一體型家族在不同年級看起來有層次，而不是完全一樣 |
| **招牌小物** | 用 `lesson_uid` 做決定性雜湊，從一個跟該課能力指標相關的小物池裡選一件（例如「推論力」池＝放大鏡/問號燈，「摘要力」池＝濾網/精簡瓶）| 池大小依能力家族數量（§3.1 既有 14 個能力家族，每家族配 2-3 個小物圖示）| 同一能力家族底下的課，招牌小物會重複（這是刻意的——重複本身就在暗示「這兩課練的是同一種能力」，呼應老師端想看到的能力分類），但體型+色彩+小物三者疊加後，179 種組合裡**完全沒有兩隻外觀全部相同**（5×8×池內随機挑選的小物，排列組合遠大於 179）|

**決定性、不是隨機**：體型家族跟色彩變體都是查表決定（跟 `island-v2/design.md` §6.2 的劇情指派、§2.1 的年級分組一樣，純函式、同輸入同結果），招牌小物用 `lesson_uid` 雜湊決定性挑選（不用真隨機，確保同一課每次看到的都是同一隻外觀，不會重新整理就變了）。

**三階造型差異沿用既有規格**：`island-v2/design.md` §3.5 已經定義「基礎階體型最小造型最簡化／中階加 1-2 個代表道具／進階完整造型+發光特效」——這份規格本身跟 species 軸是能力還是課無關，直接沿用，不需要重寫。

**兒童情緒安全**：沿用 §3.5 既有黑名單（不得出現恐怖/暴力/悲傷意象），「魔王」劇情類型的寶貝造型也要遵守 `island-v2/design.md` §6.1 已經定調的「化解心結，不是打倒怪物」基調——寶貝本身不能被畫成需要被擊敗的敵人，牠全程都是玩家這一邊、陪著玩家一起化解課文裡的困境。

## 2. 成長點數：學習行為自動換成點數，零點擊

### 2.1 跟能力指標那一半的介面契約（這是本文件最重要的一張表）

> 這是「能力指標」專家與「遊戲機制」之間唯一需要對齊的介面。雙方各自改動自己那一半的邏輯，
> 只要這張表的欄位不變，兩邊可以獨立開發、獨立上線。

**我方（遊戲機制）需要對方提供的輸入，每次學生完成一個站的學習行為時一筆**：

```
AbilityIndicatorSignal {
  student_id:     int        # 哪個學生
  lesson_uid:     str        # 哪一課（內容樹課程 id，沿用 word_baby_service 既有慣例）
  station:        str        # 哪一站（剝除 "#slug" 後綴的 base id，沿用既有 15 站命名）
  ability_id:     str        # 這一站這一課對應哪個能力指標——沿用 island-v2/design.md §3.1
                              # 已分類好的 14 個能力家族 id 之一（或對方日後調整過的新分類，
                              # 遊戲端不關心分類內容是什麼，只讀這個字串）
  quality_passed: bool       # 這次作答/活動是否達到「值得記一次成長」的門檻
                              # —— 門檻怎麼定（正確率多少、流暢度多少、完整度多少）完全是
                              # 對方的範圍，遊戲端不重新判斷對錯、不重算分數
  quality_score:  float|None # 選填，0-100，給老師端連續型指標用（如沒有就只用 bool）
}
```

**我方（遊戲機制）提供給能力指標那一半的輸出**：每個學生、每個 `ability_id` 的累積「達標次數」與「涉及課程清單」——這是一個**唯讀投影**（projection），對方的老師端儀表板（`island-v2/design.md` §3.4 已經畫過草圖：雷達圖／橫向長條圖，14 個能力各一條）直接讀這份投影，不需要自己重算。遊戲端只負責把「哪些站完成了、品質有沒有過」正確記錄下來並加總，**不負責決定這個數字該怎麼視覺化呈現給老師**（那是呈現層的事，本文件不越界）。

**邊界重申**：`quality_passed` 怎麼判定（例如 `comprehension` 站要 `overall_score >= 多少`、`full-text-annotate` 要標注幾段以上才算「有做」）**完全不是本文件要回答的問題**——這是教學內容專家的範圍（對照 CLAUDE.md「教學內容正確性不歸此學院，轉 course-academy」的既有邊界）。本文件只保證：**只要對方給的是 `quality_passed=true`，遊戲端一定會、而且只會發一次對應的成長；對方給 `false`，遊戲端保證不發任何東西，不會因為「學生好歹做完了」就打折發放**。

**已有的真實資料可以直接支援「品質」判斷的站（依據，已讀程式碼，給對方參考，不是遊戲端自己決定門檻）**：

| 站 | 已存在的量化欄位 | 來源 |
|---|---|---|
| `lesson-intro`／`key-passage-reading`（朗讀相關）| `cpm`、`accuracy`、`match_rate`（`full_reading_attempts` 陣列，每課最多存 4 次嘗試）| `learning_step_progress.py:404-469`、`models/session.py:142-151` |
| `comprehension` | `comprehension_score`／`literal_score`／`inferential_score`／`evaluative_score`（0-100）| `models/session.py:173-176`、`schemas/session.py:126-159` |
| 其餘站（`vocab-*`／`classical-*`／`spotlight`／`keypoints-table`／`full-text-annotate`／`report` 等）| 待查——未逐一核對是否已有對應的量化欄位，需對方（能力指標專家）盤點 | — |

### 2.2 觸發點：複用既有「唯一入口」，不開新端點、不新增前端呼叫

**依據（已讀程式碼）**：`learning_step_progress.py` 的 `save_step_progress` 已經證明「每個 step 完成都會流經這裡」這件事成立——XP 系統掛在這個唯一入口上，文字寶貝 v1 的碎片/遭遇判定（`_award_word_baby_rewards`，第 255-376 行）也曾經掛在同一個入口。**閱讀寶貝的成長判定取代 v1 原本掛的那個位置，不是疊加第三層**——v1 那整段判定邏輯（`_award_word_baby_rewards`／`_try_award`／`_WORD_BABY_EXCLUDED_STEP_IDS`／`_load_word_baby_rewards_for_lesson`）一起刪除，換成一個新的消費者函式（例如 `_award_reading_baby_growth`）掛回同一個觸發點，不新增端點、不要求前端多打一支 API（詳細的檔案級接管清單見 §5）。

**跟 v1 判定邏輯的關鍵差異**（這是「零點擊、做得好才給」的核心落地；v1 這一欄純粹是歷史對照，程式本身已刪除）：

| | v1 碎片判定（已移除，僅供對照） | 閱讀寶貝成長判定（新，取代 v1 原本的位置）|
|---|---|---|
| 觸發條件 | 站完成就判定（不管對錯）| 站完成**且** `quality_passed=true` 才判定 |
| 判定方式 | CSPRNG 擲骰，0.55-0.9 機率掉落 | **決定性，不擲骰**——`quality_passed=true` 保證 100% 發放，不再疊加一層運氣 |
| 學生操作 | 完成站即觸發，零操作 | 完成站即觸發，零操作（跟 v1 一樣零點擊，差別只在多了一道品質門檻）|

**為什麼拿掉 RNG（推論）**：Young 要求「做得好才給」，如果在「做得好」之上還疊一層機率骰子，等於「做得好也可能拿不到」——這違反直覺也會製造挫折（「我明明都答對了為什麼沒拿到」）。拿掉 RNG 之後，`gamification-octalysis` 的 CD7（Unpredictability）這個動機驅動力在閱讀寶貝這條線上刻意調低——這跟該 skill 本身「Black Hat 在教育場景要謹慎使用」的立場一致，**不是忽略它，是刻意不用在這個位置**。v1 曾經保留 CD7（機率掉落），但那套系統已經整套刪除，不存在「兩套各自動機設計不同」的情況了——全站現在只有一套動機設計，就是這份文件寫的這套。

### 2.3 冪等與重做：沿用既有唯一鍵，不設強制次數上限

**冪等（推論，沿用 v1 已證實有效的設計模式，但不沿用 v1 的表本身——v1 整套移除，見 §5）**：成長點數的發放鍵是 `(student_id, lesson_uid, station)`——跟 v1 原本 `StudentStationRewardLog` 的唯一鍵同一個精神，寫進 §7 全新的成長紀錄表，保證**同一站最多記一次成長**，不管學生重做幾次。

**「同一站重做有沒有上限」的設計決策（推論）**：**不設強制次數上限**。理由：
1. 上面的唯一鍵已經保證「最多拿一次成長」，重做再多次也不會多拿——「刷不出來」這個要求已經被冪等機制滿足了，不需要額外的次數鎖
2. 真正需要上限管理的不是「防止多拿」，是「避免學生在同一題卡太久產生挫折」——這是情緒安全的範疇（見 §6），不是防刷的範疇，兩種問題用兩種機制解決，不要混在一起變成一條又防刷又防挫折的複雜規則
3. 連續失敗的軟性引導：**同一站連續 3 次 `quality_passed=false`，顯示鼓勵性提示「要不要先去別的站看看，待會再回來試試這一站？」**（不鎖站、不扣分、純建議），呼應既有 `full_reading_attempts` 上限 4 次「超過背答案」的精神，但改成建議而非強制鎖死——朗讀練習本身已有自己的 4 次上限機制，這裡的「3 次軟性提示」是給其他評量型態的站（`comprehension`／`classical-self-challenge` 等）用的通用規則

**做錯會怎樣（直接回答）**：**沒有懲罰**。`quality_passed=false` 時：不發成長點數、不發碎片、不顯示負面訊息、不影響既有的 XP／站完成紀錄（那些系統有自己的規則，不受這裡影響）、寶貝的外觀與進度**維持原樣，不倒退**。學生可以立刻再試，或照 §2.3 第 3 點的軟性建議先去別站——這是刻意的設計：**閱讀寶貝系統只有「正向強化」一個方向，沒有懲罰分支**，呼應 §6 的情緒安全要求。

### 2.4 文字碎片重新定位：不是第二套貨幣，是成長點數的視覺收藏（Young 2026-10-31 要求明確判斷）

**判斷（定案，不是選項）**：**文字碎片保留，但降級成成長點數的「視覺呈現名稱」，不是獨立的資料或規則。**

v1 原本的碎片是一個**可花用的錢包**（`StudentFragmentWallet.quantity` 可加可減，拿去餵 100 隻通用寶貝）——那是「貨幣」。這個貨幣角色現在失去存在理由：v1 整套移除之後，**沒有任何東西可以拿碎片去餵**，一個不能花的貨幣就不是貨幣，硬要保留等於留著一套空轉的規則。但碎片這個「名字／具體收藏物」的角色值得留著，因為對國小生來說「集滿一片片碎片」比「數字成長點數往上跳」更具體可愛（呼應 Koster 的 Visible Progress、Octalysis CD4 Ownership）。

做法：**碎片不是另一張表、不是另一個事件、不是可以增減的庫存——它就是 §7 成長紀錄表裡同一筆 `quality_passed=true` 列的顯示層換皮**。畫面上，每當這隻閱讀寶貝的成長紀錄裡多一筆通過的站，就在牠的「碎片收藏牆」多貼上一片對應 `ability_id` 顏色的碎片貼圖；碎片數量＝`COUNT(quality_passed=true)`，即時從成長紀錄算，不另外存一個可變動的 quantity。三件事因此同時成立：

1. **沒有兩套重複系統**——碎片跟成長點數是同一筆資料的兩種呈現，不是兩筆資料互相同步
2. **零點擊**——碎片是自動貼上去的展示，沒有任何「領取」「收下」「餵食」的操作
3. **不能當貨幣花**——沒有可花用的 quantity 欄位，沒有「用碎片換什麼」的功能，這點直接回應 Young 的要求

**對 §0.1 第 5 點要求的回應**：「文字碎片仍是收集物的一部分」在這個設計下仍然成立——學生仍然會看到碎片越收越多、仍然會覺得自己在「蒐集」——只是蒐集到的是同一份成長紀錄的視覺切片，不是第二套可操作的資產。

## 3. 三階進化：條件對應「真的學會」，不是時間

### 3.1 為什麼不能沿用 v1 的休眠機制（必須明講的衝突）

**v1 現狀（依據，已讀程式碼）**：`care.json` 定義「完成一個階段的餵食 → 進入休眠（蛋/繭）→ 累積 3-47 天**真實有效天數**（扣掉寒暑假與週末）→ 達到天數才孵化進下一階段」。`word_baby_service.py` 的 `_sync_care_state` 整段邏輯都是圍繞「現在時間減去上次照顧時間」在算。

**這直接違反 Young 這次「不是累積時間」的明確要求**，也間接牽涉 §0.1 第 6 點「不要讓學生覺得寶貝會死」——v1 還有「虛弱/深度沉睡」狀態（5 天沒照顧變虛弱、12 天沒照顧深度沉睡），雖然已經刻意避開死亡用語，但**等真實天數**這件事本身就是一種隱性的時間壓力/登入誘因，跟 Young 這次「不做每日登入懲罰」的新要求性質相近，即使 v1 當初（2026-10-26）是被核准的設計。

**決策（2026-10-31 已由 Young 的「不要兩套」定案強化為確定）**：閱讀寶貝**完全不使用** `_sync_care_state` 的休眠/虛弱/孵化天數邏輯——而且因為 v1 整套被移除（見 §0.2.1／§5），這不再是「兩套系統裡新的那套選擇不繼承舊的機制」，是**這段邏輯本身連同整個 `word_baby_care.py` 一起從程式庫刪除，不存在可以繼承的對象**。三階進化**只看累積的成長點數，不看時間**，進化判定是**立即的**——學生這次送出的學習行為一旦讓累積值跨過門檻，當下（下一次讀取頁面時）就看到進化後的樣子，不需要等待、不會「卡在蛋裡」。

### 3.2 三階門檻：比例制，綁定這一課「真的有幾個可評量的站」

**規則（推論，結構由遊戲端定義，具體比例門檻標為建議值、可由能力指標專家依實測資料調整）**：

每一課的 `step_sequence`（內容樹已有的欄位，`learning_step_progress.py:329-331` 已經在用它驗證站的合法性）天然就是「這一課總共有幾站」的真相來源。進化門檻定義在**這一課裡「會產生 `AbilityIndicatorSignal` 的可評量站」的通過比例**上：

| 階段 | 條件 | 給孩子看的意思 |
|---|---|---|
| **基礎**（遇見）| 進入 `lesson-intro` 即可（見 §1.1），不需要任何 `quality_passed` | 「你開始認識這一課了」|
| **中階** | 這一課可評量站中，`quality_passed=true` 的比例 **≥ 50%**（推論，建議值） | 「你已經學會這一課一半以上的重點了」|
| **進階** | 這一課可評量站中，`quality_passed=true` 的比例 **= 100%**（全部通過）| 「你把這一課真正該學會的東西都學會了」|

**為什麼用比例不用固定次數**：179 課的 `step_sequence` 長度不一致（有些課站少、有些課站多），固定次數（例如「通過 3 站進中階」）對短課太難、對長課太容易，比例制自動適應每一課實際的站數，不需要為每課各自調參數。

**「可評量站」的清單由能力指標那一半定義（介面重申）**：不是這一課 `step_sequence` 裡的每個站都一定會產生 `AbilityIndicatorSignal`（例如 `knowledge-station` 這種延伸資料站，依內容性質可能根本不適合判定「對錯」）——哪些站屬於「可評量」是對方的範圍，遊戲端只是讀這個集合來算分母，不決定這個集合裡該放什麼。

**跟 v1「休眠型態視覺」的差異（v1 已整套移除，這裡講的是機制取捨的理由，不是「保留著不用」）**：v1 用「蛋/繭/冬眠」代表進化前的等待型態——閱讀寶貝因為**沒有等待期**，不需要這層視覺（沒有東西好等）。三階直接是「基礎型態 → 中階型態 → 進階型態」三個固定外觀，切換是瞬間的（進化動畫本身是瞬間事件的呈現，不是等待過程的呈現）。

### 3.3 進化當下的回饋強度

**依據（`game-juice-motion` 的 Milestone Unlock 分級方法論，已驗證來源 Yu-kai Chou）**：「每新增一個互動，先問它屬於哪一級，不要每次都憑感覺做特效」——三階進化對應三種不同重要性的里程碑，回饋強度要分級，不能每次都用最大特效（那樣真正重要的「進階」時刻反而被稀釋）：

| 事件 | 分級 | 回饋通道（依 `game-juice-motion` 分級表）|
|---|---|---|
| 遇見（基礎型態現身）| 小 | 1 個通道（輕柔音效 + 寶貝小幅彈跳一次）|
| 單次 `quality_passed` 成長點數入帳 | 小 | 1 個通道（一個小圖示從學習頁飛向螢幕角落的寶貝縮圖，呼應 PRD §5「不必回島，當頁就跳出提示」）|
| 進化到中階 | 中 | 2-3 個通道（音效 + 粒子 + 外觀切換的小動畫）|
| 進化到進階（這一課全部學會）| 大 | 4-8 個通道疊加（音效 + 發光 + 數字跳動 + 鏡頭或畫面強調），比照「密室破關」等級的規格——這是整堂課的里程碑，值得最大的肯定 |

## 4. 引導：寶貝卡怎麼告訴學生「去哪裡收集」

### 4.1 核心原則：地標優先，寶貝卡只是輔助入口（沿用既有已驗證原則）

**依據（已讀 `ref-zelda-landmark-design`、`island-v2/design.md` §1.4 已經落地的設計）**：喝采島的單課島與群島模式已經確立「地標優先於 UI 箭頭」的原則——下一站建築本身要在畫面構圖上明顯、路徑材質要有已走/未走的視覺差異。**閱讀寶貝的引導不重新發明一套導航機制，是在既有地標系統之上疊加一張「寶貝卡」當作輔助入口**，不是取代它。

### 4.2 寶貝卡的內容與「一鍵直達」

**寶貝卡出現的位置**：單課島畫面的固定角落（跟 §3.3「成長點數入帳」提示同一個視覺區域），學生隨時可以看到自己這一課的閱讀寶貝目前的樣子與進度。

**卡片顯示內容（推論）**：

```
┌─────────────────────────────┐
│  [寶貝縮圖·目前階段]          │
│  寶貝名字（中階階名）          │
│  成長進度：▓▓▓▓▓▓░░░░ 6/10 站 │
│  下一步：去「字源館」看看      │   ← 一鍵直達
└─────────────────────────────┘
```

- **進度條**：用 §3.2 的比例制，分子分母都是這一課真實的可評量站數（不是抽象百分比，直接顯示「6/10」這種可以數得出來的具體數字——呼應 Nielsen Norman 兒童 UX「文字難度要對齊實際識字程度」，具體數字比抽象百分比對國小生更直覺）
- **下一步建議**：從這一課**尚未 `quality_passed`** 的可評量站裡，挑**優先序最高**的一個（見 §4.3 的挑選邏輯），顯示站名 + 建築名稱（沿用 `fragments.json` 的 `station_flavor_map` 既有建築命名，如「字源館」「回音劇場」）
- **一鍵直達按鈕**：按下去直接觸發 `island-v2/design.md` §1.6 已經設計好的 `travelToStop(ctx, stop)` 介面（角色沿路徑自動走到該建築門口，顯示說明卡），**不需要新發明一套傳送邏輯**，是既有 2.5D／上帝視角模式既有函式的直接呼叫

### 4.3 「下一步去哪」怎麼決定：資料從哪裡算出來

**挑選邏輯（推論）**：

1. 篩出這一課 `step_sequence` 裡**屬於可評量站、且尚未 `quality_passed=true`** 的站（§3.2 已定義的集合）
2. 若有多個候選，依**既定站序**（`step_sequence` 的原始順序，也就是老師安排的教學順序）取**最前面**那一個——不額外設計「哪一站比較簡單」這種難度排序（那是能力指標專家的範圍，遊戲端只負責尊重既有的教學順序）
3. 若全部站都已經 `quality_passed=true`（這一課已達進階），寶貝卡改顯示「這一課你都學會了！去群島看看其他課吧」+ 一個連回群島總覽的按鈕（而不是繼續顯示一個找不到目標的空白建議）

**範圍限制（刻意不做的事）**：引導**只在這一課的範圍內**，不做跨課推薦（例如不會說「你這課學完了，去 O 課練同樣的能力」）——這類跨課推薦屬於學習路徑規劃（既有平台已有 `learning_path_service.py` 在做這件事，不是遊戲化學院的範圍，不重複造輪子）。

### 4.4 老師端看到什麼（回應 §0.1 第 6 點）

沿用 `island-v2/design.md` §3.4 已經設計好的「同一份資料，兩種臉」：學生看到寶貝名字跟外觀，老師看到的是 §2.1 介面契約累積出來的 `ability_id` 達標次數投影——呈現形式（雷達圖／長條圖／逐課明細）由老師端儀表板那一側決定，本文件只保證**資料本身是正確、即時、可投影的**（§2.1 的介面契約）。

## 6. 防沉迷與兒童情緒安全

### 6.1 不做每日登入懲罰（直接回應 §0.1 原話）

| 反模式（v1 曾經有，v1 本身現已整套移除，這裡列給下一條防線用）| 閱讀寶貝的做法 |
|---|---|
| 虛弱狀態（5 天沒照顧畫面變半透明）| **不存在**。進度只會累積、不會因為沒上線而退步或變難看 |
| 深度沉睡（12 天沒照顧完全縮回殼裡）| **不存在** |
| 孵化天數倒數（要等真實天數才進化）| **不存在**，見 §3.1 |
| 連續登入獎勵／streak | **不設計**。進步完全由「這次有沒有認真學」決定，不是「連續幾天有沒有打開 App」——呼應 `gamification-octalysis` 明確警告「CD8 Loss & Avoidance 在教育場景要用到最少，焦慮會傷害學習」|

### 6.2 不讓學生覺得寶貝會死

- 沒有任何「死亡」「瀕死」「凋零」字樣或造型（沿用 v1 既有黑名單 + 本文件 §3.1 直接拿掉休眠機制，連「看起來快死掉」的視覺都不會出現——這比 v1 的「縮回殼裡但不講死亡」更進一步，直接**不做任何負面狀態**）
- 進度**單調不減**（monotonic）：這是一個設計不變量，必須在實作驗收時明確測試——沒有任何路徑會讓已經拿到的成長點數、已經進化的階段倒退

### 6.3 失敗零羞恥（回應 §2.3）

- `quality_passed=false` 沒有負面音效、沒有「錯誤」紅色動畫、沒有扣分——只是「這次還沒有」，畫面語言維持中性（例如用「再試試看」取代「答錯了」）
- 連續失敗只給**溫和建議**（去別站看看），不是警告或鎖定

### 6.4 不製造社交壓力（刻意不做的事）

- 閱讀寶貝的進度/圖鑑**預設只有本人看得到**（不像 `island-v2/design.md` §4.2「參觀同學島」那樣開放給同班同學）——因為那套系統管的是「我的島」的裝飾類成就（本來就設計成炫耀型內容），閱讀寶貝管的是**個人學習進度**，兩者性質不同：成就適合公開比較，學習進度不適合（避免後段班學生被同學看到自己哪一課卡在基礎型態而感到難堪）
- 若日後 Young 想加入班級層級的閱讀寶貝圖鑑總覽（例如老師看全班哪幾隻進化最快），那是**老師視角**的彙總資料，不是學生對學生公開——這條邊界沿用 `island-v2/design.md` §4.3 既有的「未成年隱私分層」原則

## 7. 資料草案：單一系統，一張新表就夠（不借殼 v1，因為 v1 整套不保留）

> 初版 §7 原本在討論「借殼 v1 的三張表 or 加兩個欄位」——這兩個選項都建立在「v1 的表還留著」
> 這個現在已經不成立的前提上。2026-10-31 之後，v1 的三張表（`StudentWordBabyState`／
> `StudentFragmentWallet`／`StudentStationRewardLog`）**連同 `word_baby.py` 整個檔案一起
> 刪除**（見 §5.2），所以這裡不是「借殼還是加欄位」的選擇題，是「從零設計一張乾淨的新表」。

### 7.1 逐項檢查 §2-§6 需要存什麼，三張 v1 舊表各自的判決

| v1 舊表 | 判決 | 理由 |
|---|---|---|
| `StudentWordBabyState`（這個學生養到第幾階、休眠狀態等）| ❌ **不沿用，整個刪除** | 欄位裡的 `fed_current_stage`／`fed_by_flavor`／`dormant_type`／`dormant_started_at`／`hatch_progress_days`／`weaken_state`／`duplicate_catch_count` 七個欄位全部是餵食/休眠語意，閱讀寶貝一個都用不到（§3.1／§6）；連「進化到第幾階」這個看起來最像可以借用的欄位也不需要存，因為 §7.3 說明階段永遠即時算，存了反而要擔心跟即時算的結果不同步 |
| `StudentFragmentWallet`（口味／可花用數量）| ❌ **不沿用，不建替代表** | §2.4 已經定案：碎片不是可花用的庫存，是從成長紀錄即時算出來的顯示層，沒有「quantity 要增減」這件事，所以不需要任何一張錢包表 |
| `StudentStationRewardLog`（這格有沒有判定過，含 RNG 結果）| ⚠️ **精神沿用，表本身不沿用** | 「同一格最多判定一次」的唯一鍵設計值得保留，但 `fragment_awarded`／`fragment_flavor`／`encounter_result`／`encounter_baby_id` 四個欄位全部是 v1 的 RNG 遭遇語意，閱讀寶貝沒有 RNG（§2.2），沿用表結構反而要人為忽略四個不會再用的欄位——不如直接設計一張更簡單、沒有歷史負擔的新表（§7.2）|

### 7.2 唯一需要的新表：成長紀錄

```python
class StudentReadingBabyGrowth(Base):
    """閱讀寶貝的成長紀錄——草案，取代 v1 的 StudentStationRewardLog（不是延伸它，
    是用同一個『唯一鍵保證只判定一次』的精神，重新設計一張沒有 RNG/餵食歷史負擔的表）。

    這一張表同時扮演兩個角色，不需要再分表：
    (1) 冪等帳本——`(student_id, lesson_uid, station)` 唯一鍵保證同一格只記一次
    (2) 成長/碎片/老師端能力指標投影的唯一資料來源——三者都是對這張表做不同的聚合查詢
        （§2.4／§3.2／§4.4），不是三份各自要同步的資料
    """
    __tablename__ = "student_reading_baby_growth"
    __table_args__ = (
        UniqueConstraint("student_id", "lesson_uid", "station", name="uq_student_lesson_station_growth"),
    )
    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)
    student_id: Mapped[int] = mapped_column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True)
    lesson_uid: Mapped[str] = mapped_column(String(20), nullable=False, index=True)
    station: Mapped[str] = mapped_column(String(50), nullable=False)
    # 給老師端投影用（§2.1／§4.4），加 index 服務「依能力分組計數」的查詢
    ability_id: Mapped[str] = mapped_column(String(40), nullable=False, index=True)
    quality_passed: Mapped[bool] = mapped_column(Boolean, nullable=False)
    quality_score: Mapped[float | None] = mapped_column(Float, nullable=True)
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), nullable=False)
```

**只有一張表就夠的理由**：拿掉 RNG（§2.2）跟拿掉錢包（§2.4）之後，v1 原本需要三張表才能撐起來的系統（物種進度表＋錢包表＋判定帳本表），閱讀寶貝因為規則單純（決定性、不花用、不休眠），一張表就同時服務成長記錄、碎片顯示、老師端投影三個需求，不需要再問「要不要借殼」。

### 7.3 一張可以省略的小表：遇見時間快取（可選，非必要）

§1.1 的「遇見」需要知道「這個學生第一次看到這隻閱讀寶貝是什麼時候」。這件事理論上可以從
`LearningSession` 本身推算（這個學生對這個 `lesson_uid` 有沒有任何一筆 session），但那樣圖鑑頁
要多一次 join 才能列出 179 格的狀態，效能上不划算。可以選擇性加一張極簡表：

```python
class StudentReadingBabyEncounter(Base):
    """學生第一次遇見某課閱讀寶貝的時間戳——草案，純顯示效能用的快取，不存任何進度/階段。"""
    __tablename__ = "student_reading_baby_encounter"
    __table_args__ = (
        UniqueConstraint("student_id", "lesson_uid", name="uq_student_lesson_encounter"),
    )
    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)
    student_id: Mapped[int] = mapped_column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True)
    lesson_uid: Mapped[str] = mapped_column(String(20), nullable=False, index=True)
    first_seen_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), nullable=False)
```

這張表**可以省略**——沒有它，圖鑑頁改成「對這個學生的全部 `LearningSession` 做一次 `lesson_uid` 去重」就能算出同樣的結果，只是多一次查詢成本；工程落地時依實際效能量測決定要不要加這張表，不是必須。

### 7.4 哪些東西完全不需要存，即時算就好

- **三階進化的判定**（§3.2 的比例）：每次讀取時用 `quality_passed=true` 的筆數 / 可評量站總數即時算，不存一個「目前階段」快取欄位——閱讀寶貝沒有像 v1 那樣的休眠狀態機要追蹤，比例永遠可以從 §7.2 這張表即時重算，簡單到不需要快取，也完全避免「存的階段」跟「算出來的階段」對不上的風險
- **文字碎片的片數**（§2.4）：`COUNT(quality_passed=true)` 依 `ability_id` 分組即時算，沒有可變動的庫存欄位
- **寶貝卡「下一步去哪」**（§4.3）：純粹是對 §7.2 這張表做一次查詢 + 比對 `step_sequence`，不另存一個「建議欄位」
- **老師端的能力指標投影**（§2.1／§4.4）：對 §7.2 這張表依 `ability_id` 分組計數，是一個純讀取的聚合查詢，不另外維護彙總表（除非未來資料量大到查詢變慢才考慮快取，那是效能優化階段的事）

## 8. 驗收（Given / When / Then）

### 批次 1：遇見＋自動成長（核心機制）

1. Given 學生第一次進入某課的 `lesson-intro`，Then 立刻看到該課專屬的閱讀寶貝基礎型態，不需要先完成任何作答
2. Given 學生在某個可評量站的作答被能力指標系統判定 `quality_passed=true`，When 該筆判定送達，Then 當頁（不必回島）跳出「成長點數入帳」的小提示，且該站的成長只記一次——同一站重複送出相同的 `quality_passed=true` 不會重複加成長（冪等）
3. Given 學生在某站 `quality_passed=false`，Then 沒有任何提示跳出、沒有扣分、寶貝外觀與進度維持原樣，學生可以立刻再試或前往別站
4. Given 學生在同一站連續 3 次 `quality_passed=false`，Then 顯示一則鼓勵性建議（去別站看看），不鎖定該站、不計入任何懲罰

### 批次 2：三階進化

5. Given 某課可評量站共 N 站，學生已 `quality_passed` 的站數達到 N 的 50%，Then 該課閱讀寶貝立即（下次讀取時）顯示中階造型，不需要等待任何時間
6. Given 學生把該課可評量站全部 `quality_passed`，Then 該課閱讀寶貝立即顯示進階造型，並播放大分級回饋（§3.3）
7. Given 全部 179 課各自套用 §3.2 規則，Then 每一課都能算出一個明確的進化階段，不存在「算不出來」的課（回歸測試鎖住這個不變量，呼應 `island-v2/design.md` §6.2 批次 2 的驗收精神）

### 批次 3：引導

8. Given 學生打開某課的寶貝卡，When 該課還有未通過的可評量站，Then 卡片顯示「下一步」建議（站名+建築名）與一個「一鍵直達」按鈕
9. When 按下「一鍵直達」，Then 角色沿既有路徑自動走到該建築門口並顯示說明卡（直接呼叫 `island-v2/design.md` §1.6 既有的 `travelToStop`，不是新建一套傳送邏輯）
10. Given 該課已經是進階（全通過），When 打開寶貝卡，Then 顯示「這一課你都學會了」並引導回群島，不顯示一個無效的「下一步」

### 批次 4：單一系統收斂與老師視角（2026-10-31 改寫，取代原本的「共存」批次）

11. Given 開發團隊完成 §5 的接管清單（v1 相關檔案全刪除、呼叫點全改寫），Then **全站只有一個寶貝相關入口、一個圖鑑頁面**——遊戲大廳只看到一張「閱讀寶貝」卡片，不存在第二張寶貝類卡片；`WordBabiesLab` 的路由與 `word_babies.py` 的 API 端點都不存在（直接 404 或編譯期就找不到），圖鑑頁顯示的是 179 格（依課程分組），不是兩套清單疊在一起
12. Given 同一筆 `quality_passed=true` 事件，Then 只寫入 §7.2 這一張成長紀錄表一筆資料；畫面上「成長點數入帳」提示與「碎片收藏牆多一片」同時出現，但兩者是同一筆紀錄的兩種呈現，不是兩筆各自獨立寫入、可能互相不同步的資料
13. Given 老師打開能力指標儀表板，Then 每個 `ability_id` 的數字來自 §7.2 這張表的即時聚合查詢，與學生端看到的寶貝進度、碎片片數來自同一組底層紀錄（不是兩套各自維護、可能對不上的數字）

### 批次 5：防沉迷不變量（回歸鎖）

14. Given 學生超過 30 天沒有任何學習行為，When 回來查看閱讀寶貝，Then 外觀與進度跟 30 天前離開時完全相同（沒有虛弱、沒有倒退、沒有任何時間相關的狀態變化）
15. Given 任意一筆學習紀錄，Then 系統中不存在任何會讓已達成的成長點數或進化階段**減少**的程式路徑（單元測試覆蓋：故意建構一個會扣減的 mutation，測試必須抓到）
