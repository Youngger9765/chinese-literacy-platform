# 文字寶貝養成系統 — 資料表欄位設計（提案，非 migration）

> ⛔ 這份只是「設計給 Young 看」，**不建表、不動 `backend/app/models/`、不跑 `alembic revision`**。
> Young 已原則同意「可以新增一張伺服器資料表」（見 `design.md` §0）——這份把欄位攤開來，
> 等 Young 看過同意，才由實作那邊照 `sqlalchemy-model-safety` 的流程真的建。

## 為什麼需要新資料表（哪些東西不能只靠既有資料算出來）

PRD §5.6 已經確定：**碎片有沒有掉、有沒有遇到寶貝**這兩件事，都可以從既有的學習紀錄
（`steps_completed`／`has_session`）＋這次新增的決定性雜湊規則（`fragments.json`／`encounters.json`）
**即時算出來，不用存**——同一個學生、同一個站，答案永遠一樣，算一次跟算一百次結果相同。

但有三件事**沒辦法只靠即時計算**，因為它們會隨時間累積、因人而異，而且「算出來」這件事只能
發生一次（不能每次問都重新判定一次，不然同一個站的碎片會被無限次領取）：

1. 「這個學生到底有沒有抓過這隻寶貝、現在養到第幾階段第幾級」——這是**狀態**，不是算出來的
2. 「這個學生手上還剩幾片碎片沒餵」——背包庫存，會隨餵食消耗
3. 「這個『課×站』格子的碎片/遭遇，這個學生到底有沒有已經領過」——如果不記這筆，學生每次重整
   頁面重新呼叫進度 API，同一個站的碎片會被重複加進背包

這三件事分別對應下面三張表。

---

## 表一：`student_word_baby_state` — 這個學生擁有的每一隻寶貝，現在養到哪

**白話**：這張表的一列 = 「某個學生」+「某一隻寶貝」+「牠現在的養成狀態」。沒抓過的寶貝不會
有列（不用 100 隻都先建空列，抓到才新增一列）。

| 欄位 | 型別 | 存什麼、為什麼需要 |
|---|---|---|
| `id` | 流水號 PK | 這一列本身的識別碼 |
| `student_id` | 外鍵→既有學生表 | 誰的寶貝——沒有這欄就不知道這隻是誰養的 |
| `baby_id` | 字串，如 `wb-037` | 對應 `babies.json` 裡的物種 id——物種的名字/稀有度/進化階段規則**不存在這張表**，
  那些是不會變的內容設定，放在 JSON 檔裡版控，這張表只記「這個學生」跟這個物種的**關係** |
| `caught_at` | 時間戳 | 第一次抓到的時間，給「我的寶貝」頁排序/炫耀用（最早抓到的放前面之類） |
| `stage_index` | 整數 | 目前第幾個進化階段（1=小寶、2=中寶…）——決定畫面上顯示哪一張圖、叫什麼名字 |
| `fed_current_stage` | 整數 | 本階段已經餵了幾片正確口味的碎片——用來算「還差幾片升級/進入休眠」，畫成進度條 |
| `dormant_type` | 列舉：`none`／`egg`／`cocoon`／`hibernation` | 目前是不是在休眠、是哪一種型態（蛋/繭/冬眠）——決定畫面顯示縮起來的樣子 |
| `dormant_started_at` | 時間戳，可空 | 幾時開始休眠的——配合下面 `hatch_progress_days` 算還差幾天孵化 |
| `hatch_progress_days` | 整數 | 休眠期間已經累積的「有效照顧天數」（已經扣掉虛弱/深眠/寒暑假的天數）——
  孵化判定用這個數字，不是用「現在日期 − 開始休眠日期」直接算，因為中間可能有虛弱/長假要扣掉 |
| `weaken_state` | 列舉：`healthy`／`weak`／`deep_sleep` | 目前虛弱狀態——決定畫面上是正常待機還是縮起來探頭還是完全看不到本體 |
| `last_cared_at` | 時間戳 | 最後一次「照顧動作」發生的時間——每次這個學生完成任何站，或主動餵食這隻，就更新；
  下次要判斷「虛弱了沒」只要拿現在時間跟這個比，不用去掃整個學習紀錄 |
| `duplicate_catch_count` | 整數，預設 0 | 重複遇到同一隻的次數，純紀錄用（可以拿來做「這隻你遇過 N 次」的小彩蛋文案），
  不影響任何判定邏輯 |
| `created_at` / `updated_at` | 時間戳 | 一般稽核欄位 |

**唯一鍵**：`(student_id, baby_id)`——同一個學生同一隻寶貝只會有一列，重複捕捉是更新這列
（累加 `duplicate_catch_count`、發補償碎片），不是新增一列。

## 表二：`student_fragment_wallet` — 這個學生手上還有幾片碎片沒餵

**白話**：背包。一列 = 一個學生的某一種口味碎片目前還剩幾片。

| 欄位 | 型別 | 存什麼、為什麼需要 |
|---|---|---|
| `id` | 流水號 PK | |
| `student_id` | 外鍵→既有學生表 | 誰的背包 |
| `flavor` | 列舉：語文基礎／閱讀理解／朗讀表達／書寫紀錄／文言文 | 哪一種口味——5 種口味各自獨立庫存，
  餵食時只能消耗對的口味（見 `design.md` §6） |
| `quantity` | 整數，不可為負 | 目前還有幾片沒餵出去——掉落時 +1，餵食時 -N |
| `updated_at` | 時間戳 | 最後異動時間 |

**唯一鍵**：`(student_id, flavor)`——5 種口味，一個學生最多 5 列。

---

## 表三：`student_station_reward_log` — 這個「課×站」格子，這個學生到底領過沒

**白話**：收據存根。沒有這張表，同一個站的碎片/遭遇判定結果沒辦法記住「已經給過了」，
學生每次重新整理頁面、重新打進度 API，都會被當成「第一次完成這一站」再算一次，碎片會無限增生。

| 欄位 | 型別 | 存什麼、為什麼需要 |
|---|---|---|
| `id` | 流水號 PK | |
| `student_id` | 外鍵→既有學生表 | 誰 |
| `lesson_uid` | 字串 | 哪一課 |
| `station` | 字串 | 哪一站（PRD §5.1 的 15 種站 id 之一） |
| `fragment_awarded` | 布林 | 這一站當時判定的結果：有沒有掉碎片——**存起來**而不是每次重算，
  是因為 `fragments.json` 的機率規則未來可能調整；如果不存，規則改了舊的判定結果會跟著變，
  等於學生已經領過的東西突然消失或突然多出來 |
| `fragment_flavor` | 字串，可空 | 如果有掉，是哪一種口味（已經加進表二的背包了，這裡只是留紀錄可查） |
| `encounter_result` | 列舉：`none`／`caught`／`duplicate` | 這一站的遭遇判定結果 |
| `encounter_baby_id` | 字串，可空 | 如果遭遇了，是哪一隻 |
| `created_at` | 時間戳 | 這筆判定發生的時間 |

**唯一鍵**：`(student_id, lesson_uid, station)`——同一個學生同一個站只會判定一次，
之後查詢只讀這張表，不再重算。

## 要不要併成一張表（給 Young 的選擇題，design.md §13 第 3 點）

上面是**3 張正規化小表**，各自只管一件事，好處是語意清楚、以後要查「這個學生所有碎片庫存」
或「這隻寶貝的養成紀錄」都只查一張表不用篩欄位。

如果想要真的只開「一張」（照 Young 原話字面意思），可以把表一跟表二合併成一張寬表
（`student_word_baby_state` 多幾個 `fragment_語文基礎_qty`...`fragment_文言文_qty` 欄位），
代價是：以後每個學生不管有沒有抓到任何寶貝都要有這幾個庫存欄位放在某個地方（可能要掛在
學生主檔而不是每隻寶貝各自一列，否則 5 種庫存量會在每一列寶貝狀態上重複存一樣的值）。
**工頭建議維持 3 張**——表三（收據存根）無論如何都需要獨立存在（它管的是「課×站」而不是
「學生×寶貝」或「學生×口味」，天生就是第三種粒度），所以最多只能從 3 張併成 2 張，
併不回 1 張；拆 3 張的額外成本很低（都是小表、沒有複雜 join），語意卻乾淨很多。
