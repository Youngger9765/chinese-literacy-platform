## 0. 這份文件要解決什麼

實際入班使用的老師回饋（原文見 epic #3357）濃縮成一句話：**教師面板的導覽把「天天要看的」跟「分析用的」混在一起，而分析頁的數字跟老師在教室裡看到的狀況對不上**。這份文件不是美化版面，是先把資訊架構和資料正確性一起修。

## 1. 老師一天的使用流程（任務導向，不是功能導向）

重設計的導覽樹要讓這三個情境各自有清楚、不必跳頁的路徑：

| 時機 | 老師想問的問題 | 現在要跳幾頁才看得到 | 重設計後 |
|---|---|---|---|
| **上課前** | 這次我指派的作業，誰還沒交？ | 進班級 → 學習分析 tab → 自己心算扣掉自學紀錄（矩陣沒分）| 「今日總覽」tab 的「待交作業」卡片直接列未交名單 |
| **下課後** | 剛剛那堂課，哪一題全班都錯？ | 課堂即時 tab（即時但不留存）或錯字熱力圖 tab（只到字，不到題）| 「作業」tab 點進單一作業 → 矩陣「全班平均」列直接排序顯示最低正確率的大題 |
| **週末 / 月底** | 這班有誰需要我介入？為什麼？ | 早期介入 tab，但卡片預設收合、常常展開後是空的 | 早期介入卡片預設展開風險因子＋建議行動，且先解決「為什麼是空的」的資料問題（見 §5）|

## 2. 資訊架構：新舊對照

### 2.1 現況（9 個分頁 + 1 個獨立頁，兩層分組名稱跟實際內容對不上）

```
/teacher（班級列表）
└─ /teacher/classroom/:id
   ├─ 日常管理：學生進度｜課堂即時｜學生名單｜課文管理｜協同教師
   └─ 進階分析：學習分析（矩陣）｜跨課文分析｜早期介入｜錯字熱力圖
/teacher/assignments（獨立於班級頁之外的作業管理）
```

另外 `/teacher-home`、`/teacher/my-texts` 兩條路由存在但**沒有任何導覽入口連得到**（讀 `TeacherSidebar.tsx`／`getTeacherNavItems()` 確認目前只有「班級管理／作業管理／使用說明」三個入口）——這兩條是孤兒路由，**最終保留/合併/刪除以 teacher-code-inventory 的分類為準**，本文件只標記存在。

問題：① 學生名單跟「管班級」這件事綁更緊，卻用跟分析頁一樣的 tab 平起平坐，而且多班級的老師每次進班級頁都要重新確認「我現在看的是哪一班」② 課文管理（指派課文）跟作業管理是兩個互不相干的資料模型，但 UI 語言都叫「指派」，老師以為是同一件事 ③ 學習分析/跨課文分析/早期介入/錯字熱力圖四個 tab 其實都在問「這個學生/這題/這班 怎麼樣」，但彼此不能互相跳轉（矩陣看到異常分數，點不進去看錯在哪）④ 學生進度 tab 跟跨課文分析 tab 都有「單一學生的學習曲線」，是重工的兩套元件（`StudentExpandedPanel.tsx` 的 `buildCurveChartData` vs `CrossTextChartGrid` 的 `StudentDetailPanel`）

### 2.2 重設計（扁平化、任務分組，不是資料來源分組）

```
/teacher（班級列表 + 快速狀態：待批作業數／高風險學生數）
└─ /teacher/classroom/:id
   ├─ 班級頁首（header，常駐不隨 tab 切換，見 §2.3）
   │    └─ 班級資訊／加入代碼（既有）＋ 班級切換器（新）＋ 學生名單（新併入，手風琴收合，預設收合）
   ├─ Tab 1　今日總覽（新）—— 待交作業／課堂即時／需要關注的學生，三張卡片，取代老師「登入後到底先看哪」的空白（課堂即時的去向見 §9）
   ├─ Tab 2　作業（合併「作業管理」與「課文管理」—— 見 §3）
   │    └─ 預設畫面：班級作業總表（學生 × 全部作業的格狀總表，見 §4.1）
   │    └─ 點作業名 → 單一作業矩陣（只看這份作業，含逐大題全班統計 + 橫向展開）（見 §4.3）
   │    └─ 跨作業趨勢（取代原「跨課文分析」的班級角度，見 §4.4）
   ├─ Tab 3　學生自學總覽（新，從矩陣移出的自學紀錄 —— 見 §7）
   ├─ Tab 4　早期介入（維持，但修資料管線 —— 見 §5）
   ├─ Tab 5　錯字總表（原「錯字熱力圖」，更名避免跟班級表現矩陣的顏色編碼混淆；內容不變，見 §2.4）
   └─ Tab 6　協同教師（維持不動）

（非導覽節點，下鑽頁）學生個人頁 —— 吸收原「學生進度」tab 的內容 + 跨課文分析的個人視角，見 §8
```

這個分組不是砍功能——9 個舊 tab 的內容全部保留，只是：合併 2 個（課文管理 → 作業、跨課文分析的個人視角 → 學生個人頁）、重新定位 2 個（課堂即時 → 今日總覽卡片、學生進度 → 學生個人頁）、新增 1 個入口頁（今日總覽，純粹是既有 API 的組合視圖不需新資料）、把學生名單移位、其餘 2 個（早期介入、協同教師）內容維持只動資料管線或完全不動。

### 2.3 班級切換器（新，對應現場回饋「多班級時比較不會混淆」）

班級頁首最上方新增一個常駐的切換器：顯示目前班級名稱＋年級徽章，點擊展開同一老師底下所有班級的下拉清單（> 8 班加搜尋框）。切換後整頁資料重載，URL 帶 `?classroom={id}` 以便重新整理後維持在同一班。

**為什麼要做在頁首而不是沿用現有的「回班級列表再點別班」**：現有 `/teacher` 班級列表已經能切換，但代價是離開當前頁面的所有 tab 狀態（例如矩陣已選的作業、早期介入的篩選）。回饋說「多班級時比較不會混淆」講的是**當下在看哪一班**的確認感，不是切換路徑本身缺失——所以解法是在頁首加一個隨時可見、不離開當前 tab 脈絡的切換器，而不是新建一條切換路徑。

### 2.4 錯字總表（Tab 5）：維持內容，只搬位置

現場回饋沒有針對「錯字熱力圖」本身的具體抱怨，所以這次**只重新命名＋搬進扁平化後的 Tab 5，內容與既有 `ErrorHeatmapTab` 不變**。重新命名理由：原本「學習分析」tab 內的班級表現矩陣跟這支都用「熱力圖／色階」的視覺語言，老師容易把兩者的顏色編碼搞混（兩者色階代表的意義不同：矩陣是分數高低，這支是錯誤次數高低）——改名「錯字總表」降低第一眼的概念混淆成本。**是否要把「學習分析」tab 裡原本的常見錯誤 Top 10 清單合併進這裡，待 teacher-code-inventory 判斷是否為重複功能**（兩者內容確實有重疊，見 §11）。因為內容本體不變，本文件不另外產出這一頁的線框圖。

## 3. 「指派課文」併入「作業管理」

> ⚠️ 本節 v1 原本寫「這是兩個互不相干的資料模型，merge 不需要改資料層」——**這個前提不完全正確，已依交叉查核的 code 證據修正如下**。

**現況資料模型**（`backend/app/models/school.py:128 ClassroomText` vs `backend/app/models/assignment.py:18 Assignment`）：兩個 table 之間沒有外鍵，但**在寫入路徑上已經有兩層隱性連結，不是互不相干**：

1. **建立作業時會自動同步寫入 `ClassroomText`**（`backend/app/services/assignment_lifecycle_service.py:307-324`，註解明寫 `# Sync story_id to classroom_texts so the library page shows it (#997)`）——已實地核對，這段 code 確實存在且邏輯如此。
2. **`ClassroomText` 同時是學生端自學圖書館的資料來源**（`frontend/src/pages/student/StoryLibrary.tsx:128`），而且**只有一個班級的學生會被自動導向這個圖書館頁**（`StudentHome.tsx:71`）。換句話說，`ClassroomText` 不是「只給老師自己試作用」的孤兒資料——它同時餵給學生自學功能，刪掉或改錯這條資料路徑會影響學生看到的自學書單。
3. `classroom_texts.py:179-211`（列表 API）本身也已經把「由 Assignment 衍生出來的課文」合併進清單回傳，顯示後端已經把兩者視為同一份「這個班可讀的課文」清單在維護。

**對現場回饋「唯一的用途是讓老師『我來試作』」的修正**：讀 code 顯示這個前提不成立——`ClassroomText` 真正被學生自學頁消費，不是只有老師自己用。老師感覺「指派完只出現在這一頁」，更可能是**教師端沒有把「這份課文現在在自學圖書館裡」這件事顯示出來**，造成老師以為它石沉大海，而不是後端真的沒有下文。

**設計決定（修正版）**：
- 拿掉獨立的「課文管理」tab（UI 層面的合併仍然成立，只是理由要改）。
- 「作業」tab 的清單上方放一個篩選：**正式作業**（有到期日、進矩陣計分的 `Assignment`）／**自學課文庫**（`ClassroomText`，標籤改成「學生可在自學區看到的課文」，並且**明確顯示「已在自學圖書館上架」**，解決回饋裡「指派完只出現在這一頁」的信任問題，而不是把這份資料改成單純的老師試讀）。
- 「建立作業」表單的課文挑選器優先顯示已在自學課文庫的課文（體感更快、符合現有 `#997` 的同步邏輯），但仍可搜尋全部課文。
- 加入作業時既有的自動同步（#997）維持不變——這是本來就在跑且被學生端依賴的行為，不可移除。

## 4. 作業：班級總表、單一作業矩陣、跨作業趨勢

> ⚠️ 本節 v3 曾經把「班級表現矩陣」直接拆成「今日總覽的作業清單」+「單一作業的學生列表」，少做了一件事：老師原話要的矩陣是**一張全班學生 × 老師出的所有作業的格狀總表**（「矩陣那裡只看他出的作業……看懂每次上課的作業完成度」），不是要老師一份一份作業點進去看。§4.1 補回這張總表，§4.3 也補回「逐大題」在**全班層級**的統計（原本只做到個別學生展開）。

### 4.1 班級作業總表（學生 × 全部作業，新補回）

「作業」tab 的預設畫面（而不是直接看作業清單）：**一張格狀表，第一欄固定學生姓名、第一列固定作業名稱**，每一格是「這位學生對這份作業」的狀態，共 4 種：

| 狀態 | 顯示 | 意義 |
|---|---|---|
| 已完成 | 分數（依分數上色）| 這份作業已交且已算分 |
| 進行中 | 黃框，顯示卡在第幾步 | 已開始但尚未送出 |
| 未開始 | 灰色「—」 | 已指派但這位學生還沒動手 |
| 未指派 | 淡灰斜線 | 這位學生不在這份作業的指派名單內（例如作業建立後才加入班級的學生——`assignment_lifecycle_service.py` 的 `AssignmentSubmission` 是在建立作業當下對「當時」的在班學生批次建立，之後才加入的學生不會回溯補上） |

點作業名稱（第一列表頭）即可切換到 §4.3 的「單一作業矩陣」看這份作業的完整細節（逐大題統計＋橫向展開）；點學生名稱可切換到 §8 學生個人頁。這張總表本身**只顯示總分**，不做逐大題展開——逐大題統計是進到單一作業後才看的量（§4.3），兩層資訊密度分開，避免一次塞進 28×6×5 個數字（Tufte data-ink：總表只回答「誰還沒交、誰考差了」，不需要在總表層級就攤開大題）。

**資料面**：跟 §4.3 單一作業矩陣同一支查詢邏輯，只是維度反過來——這裡是「這個班所有 `Assignment` × 這個班所有學生」的交叉表，§4.3 是「固定一份 `Assignment`」之後的學生列表。沒有新 schema 需求，差別只在後端查詢要跨多份 `Assignment` 聚合。

**競品依據**：這張總表的形狀直接對應 research.md 裡 **Google Classroom 的 Gradebook**——rows=學生、cols=作業、cell=分數，紅/綠/黑三色一眼辨識缺交/已交/已退回（research.md §1）。我們多做的是「未指派」第四態與分數以外的三態顯示（§4.2 根因之後不能再讓「沒分數」跟「0 分」同色）。

### 4.2 單一作業矩陣的現況根因（已用程式碼直接核對，非猜測）

`backend/app/routes/teacher/teacher_analytics.py:159-260`（`get_classroom_heatmap`，前端叫它「矩陣」其實是 `/heatmap` API）：

1. **沒有過濾 session 來源**——查詢只篩 `student_id` 在班上 + `story_slug` 不是 null，**完全沒有濾 `session_mode`**（`backend/app/models/session.py:120`：`session_mode` 欄位已存在，值是 `"self_study"` 或 `"assignment"`，是 #1762 就加好的）。自學紀錄跟作業紀錄現在混在同一張矩陣裡。
2. **`None` 分數顯示成 `0.0`**（teacher_analytics.py:250：`score = round(...) if sess.overall_score is not None else 0.0`）——任何還沒跑到計分步驟、中途放棄、或只是還在練習中的 session，矩陣上一律顯示跟「考了零分」一模一樣的 `0`。這極可能就是老師看到「其他同學都是 0 分」的主因：不是學生真的考零分，是他們的紀錄被這個 fallback 吃掉了。
3. **沒有大題分解**——`HeatmapScoreEntry` 只有 `score` + `status` 兩個欄位，没有任何辦法知道「朗讀對/錯、理解答對幾題、生字錯幾個」。

以上三點已直接讀原始碼核對（本 agent 親自讀過 `teacher_analytics.py:140-260`），**邏輯存在是確定的**。

✅ **已用 staging 真資料驗證，不再是推論**——見 [#3359](https://github.com/Youngger9765/chinese-literacy-platform/issues/3359)：測試班級（id=9，10 位學生）54 格矩陣裡有 **10 格（18.5%）顯示紅色 0 分，但實際上是 6 筆 `abandoned`／1 筆 `in_progress`／3 筆 `completed` 但 `overall_score` 為 null** ——沒有一筆是真的考 0 分。**6/9 位有練習紀錄的學生**至少命中一次假 0，其中 6/10 筆集中在同一篇課文（story 20011「贏得喝采的輸家」），代表除了這個顯示邏輯，這篇課文的評分管線本身可能也有獨立問題。

### 4.3 單一作業矩陣：逐大題全班統計 + 只看作業 + 可橫向展開

- **過濾**：矩陣預設只吃 `session_mode == "assignment"`（且進一步限定在該份 `Assignment` 的 `AssignmentSubmission.session_id`，精準對到「這份作業」而非「這個學生對這篇課文做過的任何一次」）。自學紀錄完全移出矩陣，改在 Tab 3「學生自學總覽」單獨呈現（同樣的 heatmap 元件，資料源換成 `session_mode == "self_study"`，色階用不同底色避免老師搞混兩張表在講不同的事——Tufte 的 graphical integrity：同一視覺語言代表不同語意會誤導判讀，顏色要變但座標軸結構保持一致，方便老師用同一套讀圖習慣）。
- **未完成 ≠ 0 分**：三態顯示——`未開始`（灰，無底色）／`進行中`（黃框，顯示目前卡在第幾步，不給分數）／`已完成`（照分數上色）。沒有 `None → 0` 的靜默轉換。
- **頁面頂部：逐大題全班統計（新補回，對應 F3c）**——在學生列表**之前**先放一塊「這份作業、全班、每個大題」的統計：朗讀／理解-字面／理解-推論／理解-評鑑／生字，各自列**完成率**（這個大題有多少人做到）／**正確率**／**錯誤率**，**依正確率由低到高排序**，正確率最低的那項用紅色/醒目樣式標出。這是回應 §1 表格裡「作業詳情頁『逐大題』卡片直接排序顯示最低正確率的大題」的具體實作——之前只做到「個別學生展開」的大題卡片，沒有「全班」這一層聚合，等於老師要自己一個個學生點開再心算平均，這次補上系統直接算好的全班聚合，省掉老師心算。
- **橫向展開（點 cell 展開列）**：資料大部分現成，不用建新表——`backend/app/routes/teacher/teacher_student_reports.py:58-78`（`TeacherSessionReportResponse`）已經回傳 `reading_result` / `comprehension_result`（含 `literal_score`／`inferential_score`／`evaluative_score`）/ `vocab_result` / `step_progress`。展開列顯示這些大題（朗讀／理解-字面／理解-推論／理解-評鑑／生字）各自的完成與正確率小卡，並附「查看完整報告」連到既有的 `TeacherSessionReportPage`（`/teacher/students/:id/sessions/:id/report`）。
  - ⚠️ **這不等於「每一題」的逐題對錯清單**。目前對外的作業提交 schema（`backend/schemas/assignment.py:80-92`）只到分數/朗讀正確率/cpm/錯字數這個粒度；真正逐題（例如某一題選錯哪個選項）要靠 `mcq_attempt` 表（見 §6），但它目前**沒有** FK 連回 `AssignmentSubmission` 或 `LearningSession`，所以「逐大題」展開做得到，「逐題」清單目前做不到——本文件的矩陣展開列只到大題粒度，逐題是另一個待補的資料缺口（§6）。
- **大題子欄集合依作業動態產生，不寫死**：依 `backend/app/models/assignment.py` 與 `session.py` 的 step 設計，不同課文/作業可能配置不同步驟組合（參 `frontend/src/config/stepConfig.ts` 的 step 清單遠多於後端目前算分用的 6 類），寫死欄位會在某些作業上顯示假的「未完成」。全班統計的「大題清單」要跟這份作業實際配置的 step 一致，不是寫死固定 5 項。

### 4.4 跨作業趨勢（取代原「跨課文分析」的班級角度）

**現況根因**（經 competitor-research 與 teacher-code-inventory 兩次獨立核對一致）：`backend/app/services/cross_text_analysis_service.py` 的 `analyze_class_cross_text_patterns` 只保留「`status == 'completed'` 且 `overall_score` 非 null」的 session（跟 §4.2 是同一種資料缺口的另一個症狀）；前端對應元件在資料點少於 2 筆時也會隱藏趨勢線。老師回饋「只採計三筆高分紀錄」的現象，根因推論是**符合雙重篩選條件的 session 本來就只剩極少數**，不是程式寫死只取 3 筆。

✅ **已用 staging 真資料驗證**——見 [#3360](https://github.com/Youngger9765/chinese-literacy-platform/issues/3360)：除了上述的「無分數 session 被丟棄」，還找到第二個獨立機制——趨勢分組用的是 `started_at`（練習**建立**時間）而非 `completed_at`（練習**完成**時間），且前端用物件 key 覆蓋同一天的多筆資料。實測學生 id=1312 有 **10 筆真實分數橫跨 10 個不同完成日**（67.6→93.0，是一條完整的進步曲線），但這 10 筆的 `started_at` **全部是同一天**，分組後折線圖只剩 **1 個點**。這正是「只採計三筆高分紀錄」字面現象背後的具體機制——不是刻意只取 3 筆，是分組欄位選錯＋資料被悄悄丟棄兩個問題疊加。

**設計方案**：不另開一個「跨課文分析」導覽節點，而是在「作業」tab 內提供一個檢視切換：**單一作業矩陣／跨作業趨勢**。跨作業趨勢用 Tufte 的 small multiples 概念——同一份小圖表（例如「全班平均正確率」）針對這學期每一份作業並排顯示，而不是把所有作業的分數塞進同一條折線（那正是現在的 bug：折線圖對篩選後的稀疏資料點特別敏感，少數幾個高分點會讓趨勢線失真）。小倍數排列對資料稀疏更誠實：某份作業完成的人少，圖就老實顯示「樣本數：3」，而不是硬畫一條看起來像完整趨勢的線。

## 5. 早期介入：兩套系統＋一個被摺起來的答案

### 5.1 現況（程式碼直接核對）

這個 repo **同時有兩套早期介入邏輯**，都在 `backend/app/routes/teacher/teacher_alerts.py`：

| | `/alerts`（`get_classroom_alerts`，teacher_alerts.py:25-141）| `/at-risk-students`（`get_at_risk_students`，teacher_alerts.py:143-198）|
|---|---|---|
| 呼叫方 | `ClassroomAnalytics.tsx` 用（「學習分析」tab 內一小段）| `AtRiskStudents.tsx` 用（「早期介入」獨立 tab，實際這個）|
| 邏輯 | 3 條簡單門檻：連續 N 天未練習／平均分<50／連續 3 次下滑 | `prediction_service.predict_learning_difficulty`（5 訊號規則引擎：前期正確率／生字錯誤率／下滑趨勢／練習間隔／卡關次數）|
| 建議文字 | 有（`detail` 欄位一句話）| 有，且更完整（`risk_factors[]` + `recommended_actions[]`，各訊號對應具體建議，見 `prediction_service.py:81-111`）|

老師反映的「早期介入沒有任何建議或標籤」，對照的是右邊這套（`AtRiskStudents.tsx` 正是「早期介入」tab）。程式碼顯示它**不是沒有建議文字**——`risk_factors` / `recommended_actions` 就是為了回答「為什麼」而設計的。但有兩層因素共同造成老師看到的空白：

1. `AtRiskStudents.tsx:63-66` 把這些內容收在「詳情」按鈕後面、**預設收合**，摘要行只顯示截斷的第一條風險因子。
2. **`AtRiskStudents.tsx:186-187` 預設完全隱藏 `risk_level === 'low'` 的學生**（`const atRisk = students.filter((s) => s.risk_level !== 'low')`，`displayed = showAll ? students : atRisk`）——如果資料缺口（下面第 3 點）讓本該是 medium/high 的學生被系統性誤判成 low，這些學生會連卡片都不會出現，不只是建議文字被收合。

**更精確的根因假說**（經 teacher-code-inventory 獨立核對）：`predict_learning_difficulty` 5 個訊號裡有 3 個讀 `LearningSession.accuracy` 欄位。追到 `backend/app/routes/learning/sessions_progress.py:73-121`（`update_session` PATCH handler）後確認：這支 handler **完全沒有伺服端自動計算 `accuracy`／`overall_score` 的邏輯**——`update_data = payload.model_dump(exclude_unset=True)` 之後單純 `setattr`，只有前端這次 PATCH 的 payload 裡有帶的欄位才會被寫入。也就是說 `completeSelfPracticeSession`（`session.ts:281-300`）這個「標記完成」的呼叫只送 `{status: 'completed'}`，並不會順便把 `accuracy` 補上——如果一個 session 在流程中從來沒有一次 PATCH 帶過 `accuracy`，它就會完成得乾乾淨淨卻永遠是 `null`。

✅ **已用 staging 真資料驗證，確認是同一個資料漏斗的第三個症狀**——見 [#3364](https://github.com/Youngger9765/chinese-literacy-platform/issues/3364)：測試班級 10 位學生裡有 **3 位**（正確率 42.9%～55.3%）的後端回應其實帶著真實的 `risk_factors` + `recommended_actions`，但 `_compute_risk_level`（`prediction_service.py:245` 起）把「只命中 1 個風險因子」一律判成 `"low"`——這 3 位全部被判 `low`，畫面因此顯示「目前所有學生均為低風險」，老師一個建議都看不到。同一張票也確認這個 repo 有 **兩套互不相通的早期介入系統**（`/alerts` 判「23 天未練習」9/10、`/at-risk-students` 判「0/10 風險」），兩邊對同一批學生給出互相矛盾的結論。

### 5.2 設計方案

- **合併成一套**：保留 `/at-risk-students`（規則引擎，建議更完整），`/alerts` 的「連續 N 天未練習」訊號併入前者的 `Signal 4`（已經有近似邏輯，直接比對兩邊門檻值是否一致，統一成一個）。`ClassroomAnalytics.tsx` 裡那段改呼叫同一支 API，不要兩套。
- **預設展開風險因子**，不要收在「詳情」後面——這是老師最需要的那句話，不是次要資訊。徽章（高/中/低風險）留著當掃視用的顏色編碼，但建議文字跟它同時可見。
- **空結果要分「真的低風險」跟「資料不足」兩種狀態**，不要都顯示成「低風險」綠燈、也不要整張卡片直接消失。`supporting_data`（`prediction_service.py` 已回傳）裡已經有 `early_accuracy` / `max_inactivity_days` 等欄位是不是 `None`，可以直接拿來判斷「資料不足以下判斷」，UI 顯示成第三種灰色「資料不足，尚無法判斷」，**並且這一類學生預設仍要顯示**（不能沿用現在把 low risk 整批隱藏的邏輯，否則資料不足的學生會跟真正低風險的學生一起消失，老師永遠不知道他們存在）。

## 6. 猜題 / 作答時間等行為訊號

> ⚠️ 本節 v1 原本寫「完全沒有埋點」——**不準確，已修正**：有部分訊號存在，缺的是更精細的兩個欄位與一條連結。

**現況**（`backend/app/models/session.py` 全欄位核對 + `backend/app/models/mcq_attempt.py` 核對）：

- **已存在、可用的部分**：`mcq_attempt` 表（`backend/app/models/mcq_attempt.py`）每一次學生的選擇題作答都會留一筆紀錄（`user_id` / `lesson_id` / `question_id` / `choice` / `is_correct` / `created_at`）。這張表的設計註解明寫是為了「找出沒用 AI 救援家教就一直答錯的學生」（Issue #1507），不是為了這次的「猜題偵測」而建，但資料本身可以拿來推算「同一題被改答案幾次」。
- **不存在、真正的缺口**：
  1. 沒有「題目出現時間」欄位——只有 `created_at`（送出答案的時間），算不出「作答花了多久」，只能算出「兩次送出動作之間」的間隔，不是真正的 response time。
  2. **沒有 FK 連回 `AssignmentSubmission` 或 `LearningSession`**——只能用 `user_id` + `lesson_id` + `question_id` 這組合，加上時間窗做推測性比對，無法乾淨地回答「這個猜題行為發生在哪一份作業提交裡」。
- 另外兩個既有欄位，精細度都不夠：session 層級的 `started_at` / `completed_at`（算得出整堂課花多久，算不出某一題花多久）；`full_reading_attempts` jsonb 裡每次朗讀嘗試的 `duration_ms`（只有朗讀這一關有時間，理解/生字題沒有）；`AssignmentSubmission.attempt_number`（整份作業重做幾次，不是單題重答次數）。

**這不是「資料收集或判定的問題」能馬上修好的，是資料模型缺口**——要可靠偵測猜題，至少需要：① `mcq_attempt` 補 `shown_at` 時間戳或等效欄位 ② `mcq_attempt` 加 `submission_id`／`session_id` FK，把單題作答精準掛回某一次作業提交。

**設計方案（分兩階段）**：
- 第一階段（這次重設計範圍內可做）：§4 的矩陣展開列先把「現有能看到的」都攤開——正確率、完成度、大題分解——讓老師至少看得到「這題（大題層級）錯」，不是只有一個總分。這解決老師講的「看不到他們錯在哪」的大部分（大題層級對得到，逐題層級跟行為訊號對不到）。
- 第二階段（資料缺口，需要 schema 改動＋前端把 `shown_at` 埋進既有作答流程，另開 issue、需人審）：`mcq_attempt` 補上時間戳與 FK 連結後，才能算「作答時間顯著短於該題平均、或同一題在極短時間內改了答案 → 疑似猜題」這類訊號。**這份文件只負責標出缺口與可行的下一步，不在這次範圍內建 migration。**

## 7. 自學紀錄的位置

新 Tab 3「學生自學總覽」。資料源跟矩陣同一支 API（`getClassroomHeatmap` 的查詢邏輯），差別只在 `session_mode` 篩選反過來（`self_study` 而非 `assignment`）。呈現上刻意跟作業矩陣用不同底色（例如作業矩陣用藍色系分數深淺、自學總覽用綠色系），標題旁加一行說明文字「學生自己選的練習，不是老師出的作業，僅供參考」——避免老師又把這兩種數字混在一起判斷。

這個 tab 跟 §3 的「自學課文庫」是同一份 `ClassroomText` 資料的兩個呈現面——**作業 tab 的「自學課文庫」篩選回答「學生可以讀什麼」，這裡的「學生自學總覽」回答「學生實際讀了什麼、讀得怎樣」**，兩者不合併成一個畫面，因為一個是書單（設定/選書），一個是成果（事後回顧），操作時機不同。

## 8. 學生個人頁

**不是獨立導覽節點，是下鑽頁**——從班級頁首的名單、矩陣的學生列、早期介入的卡片點進去。

這一頁**吸收原「學生進度」tab 的內容**（`StudentProgressTab.tsx`／`StudentExpandedPanel.tsx`／`StudentTagManager.tsx`／`TeacherInstructionPanel.tsx`），不是從零新建：
- 學生頭卡：姓名、所屬班級（可切換）、整體正確率
- 標籤管理（既有 `StudentTagManager`：需要關注／閱讀困難／進步中／資優，手動標記不變）
- 個人指導紀錄（既有 `TeacherInstructionPanel`：老師寫給這個學生的一般性提醒，跟 `AssignmentSubmission.teacher_feedback`——針對單次提交的評語——是兩層不同粒度的回饋，不合併）
- **本學期作業表現**：每筆作業一列，可展開看每個大題（同 §4.3 矩陣展開列的元件，重用不重做）——這是修「看不到他們錯在哪」的核心，展開後連到既有 `TeacherSessionReportPage` 看完整報告
- **長期趨勢**：吸收原「跨課文分析」的個人視角（`CrossTextChartGrid` 的 `StudentDetailPanel`）跟原「學生進度」tab 既有的學習曲線圖（`StudentExpandedPanel.tsx` 的 `buildCurveChartData`）——這兩支目前是重工的兩套元件，做同一件事（單一學生跨課文/跨時間的分數曲線），合併成一個圖表，避免兩套邏輯各自維護、對不上的風險
- 自學紀錄（獨立分區，同矩陣頁的視覺分隔邏輯，見 §7）
- 早期介入狀態（若此生被標記，直接在此顯示訊號+建議，與早期介入頁同步，不是兩套文案——對應問題陳述「分數和入班觀察有落差，不確定是資料收集還是判定問題」的信任缺口：同一件事只能有一個答案）
- 資料缺口佔位：作答時間軸／猜題標記（見 §6，明確顯示「尚無此資料」而非留白或偽造）

## 9. 課堂即時的去向

原「課堂即時」tab（`LiveMonitorTab.tsx`）在新 IA 裡**不再是獨立導覽節點，摺進「今日總覽」的一張卡片**。

**理由**：課堂即時是「現在這堂課，學生正在做什麼」的即時快照，時間範圍被「今天／現在」緊緊綁住，這跟「今日總覽」要回答的問題（今天該看什麼）是同一個時間尺度，不需要另開一個節點。卡片本身顯示精簡摘要（例如「3 位學生目前正在作答」），點擊展開才載入完整的即時監控內容（原 `LiveMonitorTab` 的畫面原封不動搬進展開區，不重做）。這同時也呼應 Sweller 的 split-attention 顧慮——把「今天該看什麼」拆成兩個分頁（今日總覽 + 課堂即時）反而要老師自己記得兩邊都要看，合併成一頁內的卡片降低這個協調成本。

## 10. 跨段落的設計依據（issue 明確要求對照的兩套理論）

這一節不重複各節已經寫過的理由，只列出**貫穿多個決策、值得單獨點名**的依據：

- **Tufte — data-ink ratio / graphical integrity / small multiples**：§4.1 班級作業總表只顯示總分、不在總表層級塞大題明細（資訊密度分層）、§4.3 矩陣三態顯示（不用 `0` 吃掉「未完成」）＋逐大題全班統計、§4.4 跨作業趨勢改用 small multiples 而非單一折線、§7 自學紀錄與作業矩陣用不同色階但相同座標結構——共同原則是「視覺上的差異必須對應資料上真實存在的差異，資訊密度要分層不要一次攤平」，混用或省略都是對老師判讀的誤導。
- **Sweller — cognitive load theory / split-attention effect**：§2.2 把 9 個 tab 收斂成 6 個（外在負荷）、§4.1 班級總表讓老師不用一份一份作業點進去才拼湊出完成度全貌（避免跨頁記憶負荷）、§4.3 大題展開做在同一列而非另開頁面（避免要老師同時記住兩處畫面）、§9 課堂即時併入今日總覽（同一時間尺度的資訊不拆兩頁）——共同原則是「同一個判斷需要的資訊，不該分散在要求老師自己切換記憶的不同畫面」。
- 兩套理論在這份文件裡**互相印證但管的是不同層次**：Tufte 管「畫出來的東西有沒有說謊／有沒有浪費」，Sweller 管「要老師同時處理幾件事會不會超出負荷」。
- **競品依據（`research.md`，12 個產品，詳細引用見該檔）**：(a) §2.2「今日總覽」是刻意反業界慣例——12 家裡沒有一家把「老師今天該看什麼」做成第一個畫面，多數停在報表目錄層級（research.md §13-1）；(b) **§4.1 班級作業總表直接對應 Google Classroom 的 Gradebook**（rows=學生、cols=作業、cell=分數，紅/綠/黑三色一眼辨識，research.md §1）——這不是新發明，是業界最基本的教師報表形狀；(c) §4.3 矩陣三態顯示＋大題展開呼應 Edpuzzle／Wayground 的 item-analysis 下鑽與 Seesaw 的「未開始/進行中/已完成」三態完成狀態（研究證明這是業界已驗證的必要狀態機，不是自創）；(d) §4.4 跨作業趨勢圖可仿 ReadTheory 疊一條「班級平均」參考線，低成本高價值的小改動；(e) §5.2 早期介入的建議呈現可以往 Lexia 的 Action Plan 四分類（需用量提醒／需介入教學／可離線／可嘉獎）靠，比純列風險因子句子更有行動指引（列為本次可選、非必做的下一輪迭代方向）；(f) §6 的猜題/作答時間缺口有 PaGamO 當業界先例佐證，支持列為「值得投資」而非「邊緣需求」。
