## 1. #3024 — 學習過程中沒有即時回饋

### 教師回饋原文（第幾場 demo 未逐場標記，issue 只寫「2026-08~09 三場 demo」，兩則回饋指向同一缺口）

> 「答題答對時可以有即時增強或視覺進度條，讓學生覺得更有動機」
> 「徽章系統怎麼運作？是達成目標的當下就跑出來嗎？」

### 現況（已在程式碼驗證）

- 徽章判定唯一入口 `check_and_award_badges()`（`backend/app/services/gamification_service.py:152-215`），只被 `process_session_completion()`（同檔 `:216`）呼叫一次
- `process_session_completion()` 唯一呼叫方是 `POST /api/gamification/session-complete`（`backend/app/routes/gamification.py:216-238`）
- 前端唯一呼叫點在 `ReportPage.tsx:93`，`useEffect` 只在頁面掛載時跑一次（依賴 `dbSessionId`）——**確認：徽章與 XP 是整課走完到報告頁才一次結算，教師的猜測是對的**
- `process_session_completion()` 開頭有一個 idempotency 檢查（`gamification_service.py` ~232-247）：只要該 `session_id` 已經有任何一筆 `StudentXPLog`，整段函式立刻回傳「已處理」的快照，**不會**執行 session_complete XP、首篇獎勵、正確率獎勵、理解測驗獎勵、連續登入獎勵，也**不會**呼叫 `check_and_award_badges()`。這代表：如果之後要在課程進行中途插入任何一次 XP 寫入（例如每個大題完成給一點 XP），現在的報告頁結算會被這個 idempotency 檢查直接短路、整個報告頁的正式結算永遠不會發生。**這是任何「即時給 XP/徽章」方案動工前都必須先解決的架構衝突，不是實作細節。**
- `XPAwardToast`（`ReportPage.tsx:225`）與 `CelebrationOverlay`（`AssessmentReport.tsx:242`）都是純展示元件，只吃 props（`XPAwardResult` / `score: number | null`），本身沒有跟後端耦合——**如果只是要「換個時機顯示」，這兩個元件本身不需要改**
- `XP_REWARDS` 字典（`backend/app/models/gamification.py:21-33`）裡已經定義了 `vocab_practice`（5xp）、`step_complete`（3xp）、`strategy_exercise_complete`（10xp）、`all_steps_complete`（25xp）、`daily_first_login`（3xp）五種「顆粒度更細」的事件類型——**但全庫搜尋（backend + frontend）找不到任何一處真的呼叫 `award_xp()` 觸發這五種事件**（唯一命中是 `test_seed_service.py:44` 拿字串做假資料 seed，不是正式呼叫）。這代表資料模型已經預留了細顆粒度獎勵的位置，只是從來沒接線——比從零設計新事件類型省一步，但接線本身仍要做
- 學習流程中已經存在「大題完成」等級的事件，只是沒接遊戲化：`saveStepProgressPatch({ stepId, markCompleted: true, ... })`（例：`ReportPage.tsx` 對 `report` 這個 step 呼叫），這是給教師後台看學生走到哪一步用的，目前跟 XP/徽章完全無關
- 個別答題元件本身在「這一題答對了」的當下就已經知道結果，且完全在前端——例：`MultipleChoiceExercise.tsx` 的 `handleSelect()` 有 `if (correct) {...}` 分支，這個時間點比任何後端事件都早，**加一個純前端的視覺回饋（不涉及後端呼叫）在技術上現在就能做**

### 未驗證（標「假設」，未讀程式碼證實）
- `step_progress` 後端表格的完整 schema 與查詢成本——只讀了前端呼叫點，沒讀 `learning_progress.py` 的持久化邏輯全文
- 教師是否期待「每一題答對」還是「每個大題完成」才給回饋——issue 原文的三條範圍建議把兩種顆粒度混在一起（見下方 open questions）

### BDD 驗收準則

```gherkin
### Scenario: 答對當下有正向視覺回饋

### Scenario: 課程中已顯示過的徽章，報告頁結算時不重複計算
  Given 某徽章已在課程進行中被解鎖並顯示給學生
  When 學生的 session 之後在報告頁做最終結算
  Then 報告頁的徽章總覽不會重複顯示同一個徽章
  And 該徽章的 XP 只被計算一次
```

### 給 Young 的 open questions（每題可一句話回答）

1. **顆粒度**：即時回饋要做到「每題答對」還是「每個大題完成」？（issue 原文兩種都提，範圍不同）
2. **徽章即時解鎖要不要做**：現在的「一次結算」架構要改成「多次結算」需要重寫 idempotency 邏輯（見上方程式碼證據）——這是要做，還是先只做「答對當下的視覺回饋 + 大題進度條」（純前端、不動後端），徽章維持整課結算？
3. 如果徽章要即時解鎖，`step_progress` 的完成事件夠不夠當觸發點，還是要在答對當下就觸發（顆粒度更細、呼叫更頻繁）？

### 大小估計（依上方驗證，非拍腦袋）

| 子項 | 大小 | 依據 |
|---|---|---|
| 答對當下視覺回饋 | **S**（1-2 檔起步，逐元件加） | 純前端，可重用 `CelebrationOverlay` 的既有 pattern（純 props 驅動），不需新 API |
| 大題進度條 | **S–M** | 部分元件（`MultipleChoiceExercise`）已有「第 K 題/共 N 題」計數，只是沒有 issue 要的視覺樣式；其餘元件要各自補 |

### 建議

**答對當下視覺回饋 + 大題進度條：現在就做**（不依賴任何 open question，純前端，風險低，直接回應教師「即時回饋」的核心訴求）。

## 2. #3028 — 各大題增加正確率獎勵（鼓勵用最少次數完成）

### 教師回饋原文

> 「各大題增加正確率獎勵，鼓勵學生盡量用最少次數完成」（issue 原文摘要，非逐字引號）

### 現況（已在程式碼驗證）

- `mcq_attempt` 資料表（`backend/app/models/mcq_attempt.py`）**已經存在**，每一次答題點擊都會寫一筆（`user_id, lesson_id, question_id, choice, is_correct, created_at`），由 `POST /api/learning/mcq-attempt`（`backend/app/routes/learning/mcq_attempt.py`）寫入。這是 #1507 為了讓教師看到「一直答錯又不求助 AI 助教的學生」而建的 telemetry，**目前沒有任何地方讀取這張表做計分或遊戲化**（全庫搜尋 `McqAttempt`/`mcq_attempt` 除了寫入路徑與型別匯出，零下游消費者）
- 這個紀錄只接在 3 個答題元件：`MultipleChoiceExercise.tsx`（閱讀理解選擇題）、`GuidedStepsExercise.tsx`（引導式步驟）、`TraitInferenceExercise.tsx`（人物特質推論），加上共用區塊渲染器 `ExerciseBlockView.tsx`。**其餘所有題型完全沒有嘗試次數紀錄**——`VocabDefinitionMatch*`、`FillInBlankExercise`、`OrderingExercise`、`ClassicalWordMatching`、`ClassicalSentenceMatching`、`DictationPractice`、`SentencePractice`、`ComprehensionChat`（蘇格拉底對話）等都沒有
- `mcq_attempt` **沒有 `session_id` 欄位**，只有 `user_id + lesson_id + question_id`。同一個學生同一課文不同天重做，這張表分不出是哪一次的嘗試——要拿它做「這次大題用了幾次嘗試」的獎勵，要嘛加欄位（DB migration），要嘛用時間窗口去猜（不可靠）
- **關鍵發現**：在唯一真的接了 attempt 紀錄且有計分邏輯的元件（`MultipleChoiceExercise.tsx`）裡，讀完整支元件邏輯確認：`score`（`onComplete(score, questions.length)`）**在數學上恆等於 `total`**。原因是 `handleSelect()` 答錯只顯示「再選一次」並清空選擇，`handleNext()` 沒有任何「放棄/跳過」路徑——學生不答對就無法前進到下一題，也沒有嘗試次數上限。這代表：現有唯一有計分能力的題型，目前的 UI 規則下**永遠拿滿分**，「答對 N / total，繼續加油」這個分支目前是打不到的死路徑（`ComprehensionMcqPage.tsx:361-363`）
- 上面這個「不鎖、不揭曉、可無限重試」的設計不是意外，是刻意的：程式碼註解記載 #2199 把「答錯鎖住並揭曉正解」改成「答錯不揭曉、可再選」，且 #1094 決定「學生端不顯示答對題數」。**#3028 想加的『按嘗試次數給獎勵』，方向上正好與這兩次刻意的產品決策相反**

### 未驗證（標「假設」）
- issue 原文「各大題」具體指哪些題型（是全部 12 步驟的每一種練習，還是只有選擇題類）
- 教師實際想要的獎勵強度（多一次獎勵消失，還是漸進式）

### BDD 驗收準則

> ⚠️ 以下場景假設某個最終方向已定案；哪個方向要做，取決於下方 open question 1 的答案。

```gherkin
### Scenario: 第一次就答對整個大題可獲得額外獎勵
  Given 學生開始一個大題，在這次嘗試中還沒有任何一題答錯過
  When 學生把大題裡的每一題都在第一次選擇就答對
  Then 學生除了基本完成獎勵外，額外獲得這個大題的正確率獎勵

### Scenario: 需要多次嘗試仍能正常完成大題，且不受懲罰
  Given 學生在某幾題答錯後才答對
  When 學生完成整個大題
  Then 學生仍然獲得該大題的基本完成獎勵
  And 畫面上不出現任何暗示「你答錯了/表現不好」的訊息
  And 正確率獎勵單純不觸發（不會被講成「扣分」或「失去」）

### Scenario: 重新作答不會被鎖住或倒數提示
  Given 學生剛答錯一題
  When 學生選擇新的答案
  Then 不出現「已達嘗試上限」之類的訊息，也不會被鎖住
  And 這與現行行為一致（不得比 #2199 之前更嚴格）

### Scenario: 正確率獎勵與 #3024 即時回饋不會同時彈出互相矛盾的訊息
  Given #3028 的正確率獎勵與 #3024 的即時回饋同時因同一個學生動作被觸發
  When 系統要顯示獎勵/徽章/加分訊息
  Then 同一時間只顯示一則連貫的訊息（多個事件要排隊，不能兩個 toast 疊在一起互相矛盾）

### Scenario: [待 Young 決定方向後才能定案] 正確率獎勵的呈現方式不能讓人讀出「你表現差」
  Given 目前鎖定使用族群是學習扶助學生
  When 系統顯示任何跟正確率有關的訊息
  Then 一律用「加碼機會」的正面語氣（例：「再接再厲，下次有機會拿到⭐加分」）
  And 絕不出現「你錯了 N 次」「只拿到低分」這類語氣
```

### 給 Young 的 open questions（每題可一句話回答）

1. **這張票本身寫的風險你怎麼處理**：完全不做／只做「正面加碼」版本（絕不顯示嘗試次數、絕不暗示扣分）／其他做法？
2. **涵蓋範圍**：先只做已經有 attempt 紀錄的 3 種元件（閱讀理解選擇題／引導式步驟／人物特質推論），還是要求全部大題類型都要有（那多數題型要從零建 attempt 紀錄）？
3. `mcq_attempt` 沒有 `session_id`，要不要為此開一個 DB migration（依規則我不能未經同意就建 migration，這裡只是先問）？

### 大小估計

**Large。** 理由：(a) 現有唯一可用的資料（`mcq_attempt`）覆蓋率只有 3 個元件，且缺 `session_id`；(b) 多數題型要從零建 attempt 紀錄；(c) 唯一有計分的題型目前用的 UI 規則讓「正確率」這個維度根本不存在（永遠滿分）；(d) 這張票自己承認的風險，經程式碼驗證是真實存在的產品衝突，不是過度謹慎。

### 建議

**先別做原始範圍。** 建議走「正面加碼」版（open question 1 的第二個選項）：只針對「第一次就全對」給一個額外的、絕不與失敗掛鉤的加碼獎勵，且併入 #3024 的即時回饋一起設計（沿用同一套獎勵語彙，符合 issue #3028 原文自己寫的「與即時回饋那張票合併設計，避免兩套獎勵語彙打架」）。若 Young 想要更貼近「鼓勵用最少次數」的原意，需要先回答 open question 1，且要接受這是本次三張票裡風險最高的一項。

## 3. #3024 × #3028 設計衝突（程式碼證據小結）

| | #2199／#1094 現行設計 | #3028 想加的 |
|---|---|---|
| 答錯後 | 不揭曉正解、可無限次再選、無鎖定 | 用嘗試次數決定要不要給獎勵 |
| 學生端可見的分數 | 刻意隱藏「答對 N 題」 | 需要某種形式的正確率/次數可被感知，獎勵才有意義 |
| 設計目的（程式碼註解） | 溫和、不製造壓力 | 「鼓勵用最少次數」隱含次數多=不夠好 |

**結論**：這不是「兩張票剛好都是遊戲化」的巧合式合併，是同一個 UI（`MultipleChoiceExercise.tsx` 等）裡兩種互斥的產品哲學。任一方案動工前，這張表要先讓 Young 看過並選邊。

## 4. #3026 — 讀全文-做記號：重點生詞可預先標示，標示來源可切換

### 教師回饋原文（完整教學分析，issue 要求原文保留）

> **不先標** → 增加師生互動（由老師下指令讓全班手動標）
> **老師標** → 讓學生能統整注意力、並且能有學習團體的感覺
> **編者標** → 達到預先提醒，因為學習落後的孩子甚至無法獨立做到理解監控
> **學生自己標** → 反而需要一定程度

### ⛔ 對任務前提的更正（未驗證前提 → 已查證更正）

交辦時給的前提是「`backend/data/lessons/L*/v3/lesson.yml` 有一個 `vocabulary` 陣列，147/179 課非空」。**這個前提不成立，已查證**：

```
$ grep -rl "^vocabulary:" backend/data/lessons/  →  0 個檔案
$ lesson.yml 的頂層欄位只有：lesson_uid, version_id, title, catalog_slot, sections_present, source
```

`lesson.yml` 只是輕量索引檔，不含任何詞彙資料。真正的候選資料源是**另一個檔案**：`vocab_definitions.<slug>.yml`（每個大題一個模組檔，符合 CLAUDE.md 記載的 v3 架構「一個大題一個模組」）。以下是重新查證後的真實數字。

### 現況（已在程式碼與資料實測驗證）

- `FullTextAnnotate.tsx` + `annotationOffsets.ts`：標記的位置完全來自瀏覽器即時 `Selection`/`Range` API（`getSelectionInfo()`），用 `TreeWalker` 走過 DOM text node 換算成原始字元 offset，並剝除注音 PUA variation-selector 代理對（`stripPUASelectors`）。**目前沒有任何路徑能從「使用者即時選取」以外的來源產生一筆標記**——這是 issue 原文寫的「目前無任何預標邏輯」的具體程式碼證據
- `Annotation` 型別（`annotationReducer.ts:12-18`）只有 `{ id, paragraphIndex, charStart, charEnd, type: 'unknown'|'important' }`，**沒有「來源」欄位**分辨這筆標記是學生／老師／編者做的
- 後端持久化（`learning_annotations.py` + `annotation.py` model）：標記是綁在 `session_id`（一個學生的一次學習 session）上，PUT 整批覆蓋語意，`annotation_type` 前後端都寫死驗證只接受 2 個值。**目前完全沒有「班級層級」或「課文層級」的標記概念**——每一筆標記都只屬於一個學生的一次 session
- **實測（真的跑過資料，非猜測）**：
  - `vocab_definitions.<slug>.yml` 存在且 `items` 非空的課文：**154 / 179**（85.7%）。其餘 25 課是文言文課文，改用 `word_matching` / `classical_text` / `sentence_matching` 等模組，**沒有對應的詞彙庫概念**
  - `full_text_annotate.<slug>.yml` 另外帶一個 `inline_marked_terms` 欄位——同一批關鍵詞的純字串清單（無釋義、無位置），與 `vocab_definitions` 明顯出自同一次抽取
  - **兩者都沒有位置資訊**（沒有段落編號、沒有字元起訖）。把 157 課、共 1,648 個詞，實際拿去跟同一份 `full_text_annotate` 模組自己的 `paragraphs[].text`（就是 `FullTextAnnotate.tsx` 實際渲染的同一份原文）做子字串比對，結果：
    - **1,486 個（90.2%）在原文中剛好出現 1 次** → 可以直接定位
    - **146 個（8.9%）出現 2 次以上** → 定位時要決定「標第一個」還是「全部標」
    - **16 個（1.0%）完全找不到逐字相符**（例：千里迢迢、星光滿布、複製、雜草叢生、歉意、好感、略表、與…為伍）→ 這幾個詞無法用子字串比對自動定位，需要決定要跳過還是走別的比對方式
- 結論：`vocab_definitions`／`inline_marked_terms` 可以當「編者標」的資料源，**但必須先新建一個「詞→原文位置」的解析步驟**——這個步驟現在完全不存在（後端沒有、前端也沒有）
