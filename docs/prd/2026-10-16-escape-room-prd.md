## 1. 內容中立原則（governs everything below — 違反本節的設計一律打回）

**這是 PRD 的第一節，不是附錄**：§3 以後的所有玩法、文案、StoryPack 章節規劃，寫之前都要先通過這一節。

1. **世界觀＝書本裡的世界，不是「古代中國」**。迷城＝一座由被遺忘的故事書頁堆疊而成的城；玩家角色是「拾字人」，任務是在文字被遺忘之前把故事搶救回來。玩家是在**造訪一則一則的故事**，不是「穿越回某個朝代」——不用「穿越時空」「回到大唐／大宋」這類詞，章節轉換的敘事動詞是「翻開」「走進」「進入下一則故事」。
2. **反派是抽象的「迷霧」，不是人、不是國家、不是族群**。迷霧＝文字漸漸被遺忘而產生的現象，視覺上是一片會吞噬字跡的霧，裡面飄著破碎的字——不給它臉、不給它國籍、不給它軍隊，台詞由「迷霧」本身發出（低語感），不是某個擬人化的「守衛」角色去扮演誰的守軍。
3. **禁用詞清單**（用詞與框架雙重管制，後述 §8.4 做成與 `league_theme.py` 共用的同一道程式化檢查，不是只靠人工抓）：
   - 禁止字面詞：`中華`、`中國`、`祖國`、`民族`、`我國`、`統一`、`收復`、`大一統`
   - 禁止框架：任何「國與國」「朝代興衰／征戰」「誰的天下」式的對立敘事；章節之間沒有勝負或優劣，只有「這一則故事」換成「下一則故事」
4. **台灣原住民族神話與中國古典神話並列、不是陪襯**。章節內容規劃（§8.3）必須同時包含古典神話（山海經／淮南子／大禹治水／盤古）與台灣原住民族神話，且**每則原住民族神話都要點名是哪一族的故事並附來源**，不可用「原住民」籠統帶過。本 PRD 查證可用的素材見 §8.3 與附錄引用來源（取自維基百科「彩虹橋」「百步蛇傳說」條目、國家文化記憶庫、原住民族委員會「臺灣原住民族事典」——這些是**公開、可查證**的版本，實際寫進遊戲文案前仍需請教育內容team／文化顧問覆核用詞是否得體，本 PRD 不代為做最終文化審定）。
5. **機關的出題內容只能來自平台既有課文**（現行 175 課served lessons 或未來新增課文），**不得為了配合某則神話臨時編造或引入課外文本**。神話只出現在章節開場白／迷霧台詞等 StoryPack 裝飾文字裡，**不是出題來源**——一個「盤古」章節裡的機關題目，正常情況下可能跟盤古毫無關係（只是依年級/範圍抽到的任何一課），這是刻意的設計，不是疏漏（§5、§8 再次說明）。
6. **沿用既有底線**（#3599 原始內容＋平台既有原則）：不恐怖、不暴力、不嘲笑、不比較班級／個人輸贏排名、落敗/被迷霧碰到只是「被定住」（暫停狀態，不是死亡或受傷，需要隊友救援，§3）。

## 2. 要解決的問題與成功指標

**問題**：平台現有的「練習」介面（圖書館、課文清單）對學生而言像在寫作業（會議紀錄 2026-10-16 §5 已指出同一個問題）。PK 解決「想跟人切磋」，跨班賽季解決「長期投入」，兩者都還是「一個人面對題目」。迷城密室要解決的是**用敘事與合作感包裝練習**，讓做題目這件事本身變成「正在闖關」而不是「正在寫評量」。

**成功指標（學習優先，不是遊戲留存優先）**：
- 機關完成率：進入第 1 座機關後，完整打完 4 座機關的比例 ≥ 70%（低於代表節奏/難度有問題）
- 逃脫率不是刻意設計成很難：以年級對應難度抽題為前提，應有 ≥ 60% 的 run 能在時間內逃出（這不是一個刻意製造挫折的遊戲，見 §1.6）
- 不退化既有系統：PK／跨班賽季／課堂搶答／一般學習頁面的既有效能基準不因本功能上線而變差
- 不產生新的機關題目「硬記答案」誘因：同一位學生短時間內重複同一課的 run，正確率不應該異常飆高到接近 100%（代表學生在背答案而非理解課文）——上線後追蹤，不訂死數字（沒有基線）

## 3. 核心玩法與規則（v1：單人＋AI 隊友，一張地圖）

**一局結構**：1 位真人學生＋**固定 3 位 AI 隊友**（非真人、非可選角色，純粹是遊戲內的夥伴 NPC，由 StoryPack 提供造型與台詞，§8）組成 4 人隊伍，進入**一座迷城**（1 個 StoryPack 章節）：

1. **4 座機關**：依序開啟（不可跳關），每座機關＝1 小段課文＋2–3 題選擇題（§5）。答對累計「解鎖進度」；全部機關的題目答對一定比例（建議：每座機關至少答對半數）才算解鎖。
2. **迷霧逼近／推遠**：機關進行中，每答錯一題，迷霧向隊伍逼近一格；每答對一題，迷霧後退一格。迷霧碰到隊伍 = 一位隊友（AI）被定住（§1.2 的抽象反派機制，不是「被抓走」或「受傷」的敘事）。
3. **救援題**：任一隊友被定住時，畫面出現一題「解救題」（同樣來自課文題庫），答對立刻救回該隊友、迷霧退開一段距離；答錯不處罰（只是沒救到，可以等下一次機會再救，不卡關、不扣分）。
4. **逃出大門**：4 座機關全部解鎖後，進入「大門」——**整篇課文理解題**（重用既有 `comprehension` 題庫，888 題跨約 150 課，已經是單選 A–D 題型，§7），過關＝逃出迷城；全部隊友都要在身邊（已被救回）才能一起逃出。
5. **結局**：逃出＝成功（顯示過關動畫＋這次解鎖的外觀，§8.2）；時間到或所有隊友同時被定住且無法再救援＝這次沒逃出，**沒有懲罰性敘事**（迷霧只是暫時籠罩，下次再挑戰即可，不寫「失敗」「你輸了」這類字眼，用「這次沒來得及，再試一次？」）。
6. **一局時長**：5–10 分鐘（對齊 #3599 原始草案），對齊平台既有「20 分鐘一堂課」的現場節奏（會議紀錄 2026-10-16 §4）。

**能力卡**（角色能力，§1 原始草案「文學家當角色」→ MVP 簡化為不綁定特定人物的能力卡，理由見 §6）：每局固定提供 3 張能力卡，各限用 1 次——**提示卡**（排除一個錯誤選項）、**延時卡**（本題倒數+5 秒）、**護字符**（下一次被迷霧碰到不會被定住）。能力卡用完即沒有，不可購買、不可囤積（§4 守則）。

## 5. 題型、難度與選材

- **v1 只有選擇題（MCQ）**。連連看、圈詞是 Phase 2（§12）；**朗讀永遠排除**——會議紀錄 2026-10-16 §1 已明確定調「朗讀的正確率不適合拿來比賽」，這條同樣適用於需要即時判定對錯的闖關機制。
- **難度依年級**：沿用 PK §7.1 的 `scope_type: enum('lesson', 'grade_pool')` / `scope_ref` 設計，不另外發明一套——同一個 run 的 4 座機關＋大門全部用同一個 `scope_ref`（同一課或同一年級題庫），維持難度一致，不在一局裡忽難忽易。
- **選材來源**：現行 **175 課**served lessons（`GET /api/stories?page_size=300` 現況，實測 `total=179`，以 API 回傳的 `total` 為準，不是任何靜態檔案快照——同 `CLAUDE.md` 既有教訓，見 chinese-literacy-platform 專案記憶）。機關題目與大門理解題的課文選擇**跟章節主題無關**（§1.5 已說明），只跟 `scope_ref` 有關。

## 6. 角色與能力（小決定：不做「文學家當角色」）

**小決定（Claude 判斷，Young 可推翻）**：#3599 原始草案提議「文學家當角色」，MVP 階段**不採用**——理由：(1) PK 已經用 7 位文學家做對戰對手，迷城密室若再用同一批人物當「可操作角色」容易讓學生混淆兩個模式在玩同一套人物 (2) 角色挑選/解鎖是額外的一層系統複雜度，MVP 要精簡（Young §0 決定 5）。改為§3 的**能力卡**機制：固定 3 張、跟人物無關、规则寫死在程式碼裡，不經 StoryPack（StoryPack 只提供外觀皮膚，不提供能力數值，同 `league_theme.py` 的「數值永遠寫死在程式碼，内容才是資料」設計哲學）。
**外觀皮膚**（cosmetics）：解鎖條件＝「某個 `story_pack_key` + `chapter_key` 底下至少成功逃出一次」，用查詢算出（`SELECT DISTINCT story_pack_key, chapter_key FROM escape_room_runs WHERE student_id = :id AND result = 'escaped'`），**不另開解鎖紀錄表**（同 PK §7.2「贏過的人物是查詢，不是新表」的作法）。皮膚圖像資產本身由 StoryPack 提供（§8.1）。

## 7. 架構：重用既有出題基礎設施，不重寫一套

```
既有題目來源 adapter（live_quiz/sources/*，完全不改）
  comprehension.py（閱讀理解，888 題／~150 課，單選 A-D）──→ 大門（整篇課文理解）
  vocab_definitions.py / vocab_application.py / zhuyin.py ──→ 4 座機關（依 scope_ref 抽題）
                             │
                             ▼
                live_quiz/round_types/choice.py::generate_rounds()
         （PK 已驗證可重用的 pure function，迷城密室直接呼叫，不重寫出題邏輯；
          per-game seeded shuffle 防正解外洩機制原樣沿用，同 PK §6／§8.1）
                             │
                             ▼
                  迷城密室引擎（新模組 escape_room）
            run 狀態機／迷霧距離／救援判定／能力卡／StoryPack adapter（§8）
```

**獨立性**（沿用 `live_quiz`／`league`／`pk` 已驗證的規則）：依賴只往一個方向（迷城密室讀 `live_quiz` 的出題 adapter，後者不知道迷城密室存在）；自己的表、自己的 `/api/escape-room/*` 路徑；開局就把題目快照存進 `escape_room_runs.chambers_snapshot`（課文之後改版不影響進行中或已結束的 run）；**不寫進 `league` 的任何表、不算進「完成一課」的學習紀錄**（同 PK §8.3 的理由：迷城密室是「臨場反應＋合作」機制，不是「長期投入」，混進 `league` 會把兩種訊號搞混）。

**v1 不需要配對引擎**：因為沒有真人對真人（§0 決定 5），學生選定範圍後**立即**建立一局 run，沒有排隊、沒有輪詢等待——這是 MVP 比 PK／跨班賽季都更簡單的地方，不是偷懶漏做。

## 8. StoryPack 整合（不自建故事儲存）

**原則**：迷城密室**不定義自己的主題/故事 schema**。遊戲規則（迷霧距離怎麼算、救援怎麼判定、機關怎麼解鎖）寫死在 `escape_room` 模組的程式碼裡；**會變的只有故事內容**（章節背景、迷霧的台詞、救援/逃脫時的過場台詞、皮膚美術），這些一律向共用的 **StoryPack** 模組要。

> ⚠️ 撰寫本文件時，StoryPack 尚未定案——目前存在的是它的前身：`league_theme.py` 的 `LeagueTheme` schema（`schema_version`/`scenes` 擴充點已預留）＋ `docs/prd/2026-10-16-story-mode-design.md` §3.5／§4 提出的 `LeagueThemeScenes`／`DialogueLine` 共用對話格式（PK 與跨班賽季已經共用同一套 `speaker`/`scene`/`variant`/`expression`/`lines` 慣例）。本節**只列出迷城密室需要 StoryPack 提供的介面需求**，不假設 StoryPack 最終定案的確切型別名稱——實作時由 StoryPack 的設計者／CTO review 決定怎麼落地，迷城密室這邊只透過一層 adapter（`services/escape_room/story_adapter.py`，概念性命名）去讀，不直接耦合到 StoryPack 內部結構。

### 8.1 迷城密室需要的槽位（slots）— 全部透過 adapter 讀取，一個都不自己存

| 槽位 | 對應既有機制 | 說明 |
|---|---|---|
| **章節地圖背景美術** | 等同 `LeagueTheme.background_art` | 1 張背景（v1 一張地圖只要 1 份）|
| **迷霧台詞** | `DialogueLine`，`scene` 新增 `"escape-room-mist"` | 變體（`variant`）：`advance`（逼近）／`retreat`（後退）／`freeze`（定住某隊友）／`breakthrough`（逃脫成功）——語氣統一是抽象低語，不給迷霧任何人稱代名詞指向特定群體（§1.2）|
| **救援／逃脫對話** | `DialogueLine`，`scene` 新增 `"escape-room-rescue"` / `"escape-room-escape"` | 變體：`call_for_help`（隊友呼救）／`rescued`（救回歡呼）／`escaped`（全員逃出過場白）／`not_this_time`（沒逃出，鼓勵語氣，§3.5）|
| **章節開場白** | 等同既有 `LeagueTheme.intro`／跨班賽季 2 位導覽角色模式 | v1 只需要 1 個章節的開場白（1–4 句），不需要新建「導覽角色」這個新概念——直接沿用 StoryPack 已有的 intro 欄位 |
| **外觀皮膚美術** | 等同 `LeagueThemeChest`/`LeagueThemeBadge` 的 `art` 欄位（emoji 或 allow-list SVG）| 每個 `chapter_key` 至少 1 款，解鎖條件見 §6 |

**刻意不跟 StoryPack 要的東西**（對齊 Young「不跟 StoryPack 要新功能」的 MVP 指示）：不要求 StoryPack 新增任何目前還沒有的欄位型別或驗證邏輯——上面 5 個槽位全部可以用 `DialogueLine`（擴充 `scene` 這個 `Literal` 的允許值，屬於**新增列舉值**，不是新機制）＋既有 `LeagueThemeArt` 容納，不需要 StoryPack 團隊為了迷城密室另外設計一套新的內容型別。

### 8.2 綁定方式（概念層，不是實作規格）

- `escape_room_runs` 只存 `story_pack_key` + `chapter_key`（兩個字串），**不存任何故事文字或美術**——跟 `league_seasons.theme_key` 的做法一致（參照既有欄位，不複製內容）
- 哪個 `story_pack_key`/`chapter_key` 是目前的預設值，由 StoryPack 自己的解析規則決定（比照 `league_theme_store.resolve_theme_for_season` 的 fallback chain：個別指定 → 平台預設 → 內建最小文案）；迷城密室**不自己維護一份「目前啟用哪個主題包」的設定**
- StoryPack 暫時不可用／尚未定案時，迷城密室要有一份**最小內建預設文案**（純白話、不涉及任何神話，例如「濃霧漸漸籠罩，快想辦法推開它！」），保證遊戲規則可以先上線測試，不被故事內容卡住——同 league 的 `DEFAULT_THEME_FALLBACK` precedent

## 9. 資料表需求（只列清單，不建 migration — 需 Young 核准）

### 9.1 v1：新增 1 張表 `escape_room_runs`

```
id                  PK
student_id          FK -> users
scope_type          enum('lesson', 'grade_pool')   -- 同 PK §7.1
scope_ref           string
story_pack_key      string                          -- §8.2，不存內容本身
chapter_key         string
chambers_snapshot   JSONB   -- 4 座機關的題目快照 + 作答進度（每座：lesson_ref、题目、是否解鎖、答對數）
gate_snapshot       JSONB   -- 大門（comprehension 題）快照 + 作答進度
mist_distance       int, default 50                 -- 0 = 全員被定住，100 = 逃出
teammates_state     JSONB   -- 3 位 AI 隊友的狀態（slug、是否被定住、被定住時間），非真人，無 FK
abilities_used      JSONB   -- 哪幾張能力卡已經用掉（§3）
result              enum('in_progress', 'escaped', 'not_this_time', 'abandoned')
started_at
completed_at
```
索引：`student_id`（自己的闖關紀錄／皮膚解鎖查詢，§6）。

**為什麼只要 1 張表**：v1 沒有真人對真人、沒有配對佇列，所有狀態都附屬在同一個 run 上，比 PK（3 表）跟跨班賽季 arena（3 表）都精簡——這是 MVP 範圍小帶來的自然結果，不是為了省表硬塞欄位。

### 9.2 既有欄位重用，零新增（Phase 2 才會用到）

`classrooms.feature_settings`（PK §7.4 已核准、已上線的 JSONB 欄位）未來只需要在 `FEATURE_DEFAULTS` 字典多加一個 key **`escape_room_team`**（boolean，預設 `false`）——**v1 不需要**，因為 v1 無真人組隊；留在這裡是讓 Phase 2 實作者知道不用再申請一次 migration。

## 11. CTO 架構審查（2026-10-16）

| # | 發現 | 修正/回應 |
|---|---|---|
| 1 | v1 把「4 人合作」做成「1 真人 + 3 AI」，會不會讓實作者誤以為要做即時多人連線？ | 不需要——AI 隊友狀態完全是 server-side 計算、單一真人客戶端驅動，沒有任何跨使用者的即時同步需求，§10 API 清單裡沒有任何「等待另一方」的端點，跟 PK／Phase 2 組隊模式（需要配對/輪詢）性質不同，這點在 §7「v1 不需要配對引擎」已說明，CTO 審查確認這個簡化是對的，不是漏做 |
| 2 | §8 的 StoryPack 綁定，在 StoryPack 尚未定案時會不會讓本功能卡住無法開工？ | 不會——§8.2 已經要求迷城密室自備一份「最小內建預設文案」，遊戲規則可以先用這份文案上線測試；StoryPack 定案後只是把 `story_pack_key`/`chapter_key` 指向真正的內容來源，不需要改動 `escape_room` 模組本身的任何程式碼（跟 §8.2 的 adapter 分層精神一致）|
| 3 | `chambers_snapshot`／`gate_snapshot`／`teammates_state`／`abilities_used` 四個 JSONB 欄位會不會讓這張表將來難以查詢（例如要統計「哪個年級最常用延時卡」）？ | 跟 PK §7.2 的技術債記錄方式一樣：這是 MVP 階段對「只需要 1 張新表」這個限制下的合理取捨，**不是沒想到**。真的需要跨 run 的能力卡/機關統計分析時，再把對應欄位遷移成獨立表，現在不需要為了假設性的未來分析預先拆表（同 PK CTO 審查 #6 的「複雜度預算」原則）|
| 4 | §1.3 的禁用詞清單只有 8 個詞，會不會不夠全面？ | 誠實標註為起點而非終點：這份清單是本 PRD 根據協調者給的具體指示整理，**不是一份完整的政治敏感詞庫**。建議 StoryPack／`DialogueLine` 驗證器上線後，由實際審稿／QA 過程持續補充（同任何 `_BANNED_TERMS` 清單的既有維護模式，§8.4），本 PRD 不假裝一次列完 |

## 12. UIUX 審查（2026-10-16）

| # | 發現 | 修正 |
|---|---|---|
| 1 | 迷霧是抽象反派（§1.2），畫面上要怎麼呈現才不會變成「有臉的怪物」或「嚇人的東西」？ | 用環境特效（半透明灰藍色霧氣＋裡面漂浮的破碎字跡/筆畫殘影），**不設計成有眼睛/嘴巴/肢體的生物**；逼近時用「霧氣擴大、邊緣文字殘影變多」表現，不用任何尖牙/利爪/紅光一類會讓低年級學生感到威脅的視覺語言 |
| 2 | 隊友「被定住」要怎麼呈現才不會像是受傷或死亡（§1.6）？ | 被定住的 AI 隊友角色改成**半透明＋靜止姿勢**（像被按了暫停鍵），周圍一圈淡淡的霧氣光環；救回時播放「光環消散、角色恢復原色」的簡短動畫，不使用倒下/變灰黑/碎裂等負面視覺 |
| 3 | 「沒逃出」的結局畫面要怎麼避免像「你輸了」？ | 沿用 PK/league 既有的「不用紅色、不用懲罰性字眼」規則（`DESIGN.md` `error` 紅色保留系統錯誤）：改用溫暖鼓勵文案（「這次沒來得及，再試一次？」）＋中性色（沿用既有 `accent-bg` 淺紫背景），不顯示「失敗」「GAME OVER」字樣 |
| 4 | 三個斷點（390/768/1280）下，迷霧距離條、隊友狀態、能力卡按鈕會不會擠在一起？ | 390px 手機版採垂直堆疊（迷霧距離條在最上方常駐、能力卡列在底部固定工具列、隊友頭像縮成一排小圖示）；768/1280 可以併排顯示，比照 PK §18 UIUX 審查「位置固定不重新映射」原則，三個寬度的相對位置一致，不為了「好看」在不同寬度換位置 |

## 13. QA 計畫（實作完成後執行，每項附可驗證的 pass 條件）

| 項目 | 驗證方法 | Pass 條件 |
|---|---|---|
| 機關依序解鎖 | 跑 10 局 run，檢查機關 2 能不能在機關 1 未解鎖時被存取 | 100% 無法跳關（直接呼叫 API 也要回 403/409，不只是前端擋）|
| 迷霧距離計算 | 構造「連續答對 5 題」與「連續答錯 5 題」兩種情境 | 答對全程迷霧距離單調遞增（後退）、答錯全程單調遞減（逼近），不出現方向錯誤 |
| 隊友救援 | 讓迷霧碰到隊伍，觸發救援題，分別測「答對」與「答錯」 | 答對：該隊友立即恢復、迷霧退開；答錯：隊友維持定住、無額外處罰、可以再次嘗試救援 |
| 大門理解題 | 4 座機關全解鎖後，確認大門題目來自 `comprehension` 題庫（§7），且無法在機關未全解鎖時提前觸發 | 大門題目格式為既有 A-D 單選；提前呼叫大門 API 回 409 |
| StoryPack fallback | 模擬 StoryPack 回應缺失/逾時 | 遊戲改用 §8.2 的最小內建預設文案繼續運作，不整局卡住或白屏 |
| 中立性驗證器 | 對 `DialogueLine` 送入含 §1.3 禁用詞的文字 | 一律被拒絕（422），同 `league_theme.py` 既有驗證器的 fail-closed 行為 |
| 能力卡用量限制 | 同一局嘗試使用同一張能力卡兩次 | 第二次呼叫回 409，不生效 |
| 無障礙 | `prefers-reduced-motion` 開啟前後截圖比對 | 迷霧逼近動畫與過場特效全部替換為靜態呈現，功能不受影響 |
| 效能 | 模擬 30 位學生同時開局 | 0 次因 per-IP 限流被擋（429）；不讓同時段既有系統（PK/live_quiz/league）效能基準劣化 |
| 鍵盤/螢幕閱讀器 | 走一次完整 run（開局→機關→救援→大門→結局）| 所有互動元素可用鍵盤操作，字幕完整呈現（§4 無語音旁白）|
