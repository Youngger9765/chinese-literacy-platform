# PRD｜國文競技場（跨班／跨校／全國中文學習競賽，工作代號 `arena`）

> 狀態：規劃中｜2026-10-14｜對應 issue：見本文件所在 PR

## 1. 要解決什麼

老師看到均一教育平台「星空探險隊」（年度全國性團隊學習競賽）帶動的學習動機，希望中文閱讀這邊也有類似機制：
學生可以跨校、跨班比賽，也可以有個人排行榜，但**不能洩漏未成年學生的個資**。

目前平台已有「課堂挑戰」（issue #3551，contest 引擎，Kahoot 式即時搶答）與「遊戲化」（XP／等級／徽章／連續登入／單班排行榜）兩套機制，但：
- 沒有**跨時間持續**的排行榜（課堂挑戰是單場次，結束即清空畫面）
- 沒有**跨班／跨校**的比賽機制
- 沒有官方可以主辦的**全國性賽季活動**
- 既有的單班排行榜（`GET /api/gamification/leaderboard/{classroom_id}`）直接顯示學生真實姓名（`User.name`）—— 這在「老師看自己班」的情境下沒問題（老師本來就認識班上學生），但**不能原樣搬到跨班／跨校／全國的情境**，否則等於把全國各地陌生人看得到的榜單上放真實姓名

**成功指標**
- 老師 3 步內可以發出一場跨班邀請賽邀請（選對象班級 → 設定時間窗 → 送出）
- 個人日常排行榜：任何學生都能在「只看得到暱稱」的榜單上看到自己進步
- 隱私：跨班／跨校／全國範圍的任何 API 回應，**0 筆**出現其他班級學生的真實姓名、email、學校全名、使用者 id
- MVP 範圍：個人日常排行榜（校內）＋跨班邀請賽，建立在既有「課堂挑戰」引擎之上，不重寫出題系統

## 3. 賽制設計

四種賽制共用同一套「參賽者」概念（個人／班級／學校），差異在**誰能建立、誰能加入、怎麼計分**。

| 賽制 | 誰能建立 | 誰能加入 | 計分單位 | 排行榜範圍 |
|---|---|---|---|---|
| **(a) 個人日常排行榜** | 系統自動（常態開啟，無需建立）| 所有學生自動參與（見 §5 可否退出） | 個人 | 校內同年級（MVP）；全平台留待 Phase 3 |
| **(b) 跨班邀請賽** | 任一班級的老師 | 被邀請的班級老師接受 | 班級（team） | 僅參與的兩班 + 雙方老師學生 |
| **(c) 跨校邀請賽** | 學校管理員或老師（代表本校）| 被邀請的學校接受 | 學校（聚合各班）| 僅參與的兩校 |
| **(d) 官方全國賽** | 平台管理員（`system_admin`）| 任何班級／學校於報名期自願加入 | 個人＋班級＋學校三層 | 全平台（分層顯示，見 §6）|

### 3.1 個人日常排行榜（MVP）

- **賽季**：每週一 00:00 重置（對齊學校作息），**非賽季限定**、永久常態運作；歷史賽季分數保留供「歷史最佳」展示
- **分數來源**：每日「自主挑戰」（學生自己開課堂挑戰題目作答，答對＋速度計分，沿用 #3551 的計分公式：答對 500＋速度加分最多 500）累加
- **防刷量**：每日只計**前 N 題**（如 50 題）的分數，避免靠長時間刷題堆量而非正確率取勝（對齊均一「年級減 2」的公平精神：拚效率不拚時數）
- **排行榜範圍**：MVP 先做「校內同年級」；顯示 Top 20 ＋「你目前的名次區間」
- **tie-break**：總分相同 → 正確率高者優先 → 仍相同則較早達到者優先

### 3.2 跨班邀請賽（MVP）

- **建立**：任一班級老師選擇目標班級（用班級 `join_code` 或同校班級清單）發出邀請，設定比賽時間窗（如「這週五 1 天」）與課文範圍（沿用 #3551 的選題介面）
- **接受／婉拒**：對方老師在時間窗開始前接受或婉拒；逾時未回應視為過期
- **比賽形式（MVP 預設：非同步視窗期，而非強制同時上線）**：兩班**各自**在時間窗內用「課堂挑戰」（即時課堂或自主挑戰皆可）完成，分數在時間窗結束時彙總比較。
  > 為什麼不做「兩班同時連線 PK」：兩校／兩班實際排課時段不同，強制同步會變成老師要喬課表；而且#3551 的即時課堂設計本來就是單班規模（60 人上限／每秒輪詢），同步橋接兩班需要另一層跨班廣播機制，MVP 不做。
- **計分：人數不同的公平性公式**
  ```
  班級比賽分數 = 該班所有參賽者得分總和 ÷ max(該班實際參賽人數, 最低門檻)
  ```
  例：最低門檻設 5 人 —— 8 人班只有 8 人參賽，用 8 當分母；3 人參賽的班，仍用 5 當分母（避免小樣本靠少數高手衝高平均）。門檻值留在 §9 待 Young 決定具體數字。
- **tie-break**：平均分數相同 → 參賽人數佔全班比例（參與率）高者優先

### 3.3 跨校邀請賽（Phase 2，非 MVP）

- 架構同 §3.2，聚合層級從「班級」換成「學校」（該校所有參賽班級的平均分數之平均）
- 需要先有「學校目錄」機制讓老師找到對方學校（不能讓任何老師隨意對任何學校發邀請，否則變成騷擾管道）——建議比照均一「選填學校或選其他」的作法，由學校管理員（`org_admin`／`school admin`）決定是否加入公開可邀請清單（opt-in directory）

### 3.4 官方全國賽（Phase 3，非 MVP）

- 僅 `system_admin` 可建立；比照均一兩階段時間窗（報名期／算分期）
- 題目：比照 #3551「開場就把題目快照存起來」的規則，全國賽開賽時鎖定題目快照，過程中課文資料更新不影響比賽公平性
- 三層排行榜：個人／班級／學校，顯示規則見 §6

## 5. 個資保護（具體規則）

| 情境 | 顯示什�么 | 不顯示什麼 |
|---|---|---|
| 老師看自己班的排行榜（既有 `/api/gamification/leaderboard/{classroom_id}`）| 真實姓名（現狀維持——老師本來就認識班上學生）| — |
| **個人日常排行榜（跨班可見）** | 系統產生的**暱稱**（固定詞庫組合，如「勇敢的向日葵」）＋系統給的**代表圖示**（沿用既有 `BADGE_CATALOGUE` 的 icon／color 系統，不做大頭貼上傳）| 真實姓名、email、學校全名、班級名稱、`user_id`、`student_id` |
| **跨班邀請賽排行榜** | 對方班級顯示「X 年Y班」或老師自訂的**對外暱稱**（如「飛鷹隊」），學生顯示暱稱 | 對方班級學生的真實姓名／座號／個人帳號資訊 |
| **跨校邀請賽／全國賽**（Phase 2–3）| 學校顯示**縣市＋學校自訂暱稱**（opt-in，預設匿名「神秘學校 A」）| 學校全名（除非該校管理員主動 opt-in 公開校名）|
| 家長（`ParentStudentLink`）查看 | 自己小孩的真實分數與排名 | 其他學生的任何可識別資訊（不因為是家長就解除暱稱保護）|

**k-anonymity 最小人數門檻**：任何聚合排行榜只在該群組（班級／學校／縣市）**人數 ≥ 5** 時才顯示精確名次；低於門檻顯示「人數不足，暫不顯示排名」或併入上一層聚合單位。

**名次區間而非精確名次**：給個別學生看自己的排名時，小樣本（如全年級 < 30 人）顯示「你在前 20%」而非「你是第 6 名」，降低反推身分的風險。

**預設不開放跨校查找**：跨班／跨校功能的「對象清單」只顯示**已 opt-in** 的班級／學校，不是任何人可任意搜尋全平台名單去發邀請——這對齊既有 `backend/app/auth/policies.py` 的個資法 §20 原則（cross-org 預設拒絕，例外只在雙方明確同意後開一個有限欄位的視圖）。

**資料保留**：排行榜聚合資料（已去識別化的分數／名次）可長期保留供教學分析；MVP 不新增刪除流程，留待 Phase 2 與既有個資保留政策一併檢視。

**未成年考量**：延續既有「合成 email」（`@student.lingoleap.local`）與無需真實聯絡資訊的帳號模型——`arena` 模組**不需要、也不會**額外蒐集學生的真實姓名以外的任何新個資欄位。

## 6. 防作弊與公平

- **伺服器端計時與計分**：沿用 #3551「時間與分數由伺服器判定」原則，`arena` 不自己重算分數，只讀 contest 引擎回傳的結果
- **一人一帳號**：沿用既有 `User`／`UserRole` 唯一帳號模型，不開放訪客／匿名作答
- **題目隨機化**：沿用 #3551 adapter 既有的隨機抽題能力
- **限流**：比照 #3551 CTO 審查結論（finding #1）——`arena` 的狀態查詢 API 不計入「同一來源 IP 每分鐘」的全域限流（全班共用一個對外 IP 時會互相誤傷），改用「每場次、每參賽者」自己的獨立上限
- **異常偵測（MVP 範圍外，Phase 2 再做）**：同一帳號短時間內作答量或正確率出現統計異常 → 標記供老師人工複核，**不自動扣分**（扣分需要人判斷，誤判成本太高）
- **人數造假防範**：§3.2 的「每人平均分」公式本身就讓「硬拉人頭灌水」沒有效益（分母設最低門檻，衝人數不會拉高平均分）

## 7. 架構

### 7.1 模組獨立性（沿用 #3551 的四條規則）

```
既有模組（完全不改）
  org/school/classroom/user（既有租戶與角色模型）
  gamification（XP／等級／徽章，既有）
  contest（#3551 課堂挑戰引擎：QuizItem adapter + session/participant/answer）
        │ arena 只讀 contest 算出的「這次作答結果」
        ▼
  ┌─────────────────── arena（新模組）───────────────────┐
  │  Season（賽季期間）                                    │
  │  Nickname（暱稱／圖示指派，隱私層）                     │
  │  Invitation（跨班／跨校邀請：建立／接受／婉拒／過期）    │
  │  LeaderboardSnapshot（去識別化後的聚合排名，快取用）    │
  └────────────────────────────────────────────────────┘
        │
        ▼
  老師端：邀請管理頁／學生端：個人排行榜頁、邀請賽頁（新前端頁面）
```

**獨立性規則**：
1. **依賴只往一個方向**：`arena` 可以讀 `contest`／`org`／`school`／`classroom`／`user` 的資料，這些模組完全不知道 `arena` 的存在；拿掉 `arena`，其他功能照常運作
2. **自己的資料表、自己的 API 路徑**：`/api/arena/*`，不寫入 `contest` 或 `gamification` 的表
3. **讀 `contest` 結果走抽象介面**：`arena` 的計分服務透過一個「分數提供者」介面讀取作答結果，不直接 import `contest` 的 ORM model——`contest` 仍在開發中（另一分支），等它併入 `staging` 後再接上實作，介面先用假資料／既有 `gamification` XP 當暫代資料源讓測試先行
4. **暱稱與可見性是 `arena` 自己的一層**：不修改 `User.name`，不在既有 `gamification` 排行榜 API 動刀（那支維持現狀給「老師看自己班」用）

### 7.2 實體

| 實體 | 說明 |
|---|---|
| `ArenaSeason` | 賽季期間設定（開始/結束時間、是否常態輪替） |
| `ArenaNickname` | 學生 ↔ 系統產生暱稱＋圖示的對應（穩定不隨機變動，可由學生申請重roll） |
| `ArenaInvitation` | 跨班邀請：發起班級、對象班級、狀態（pending/accepted/declined/expired）、時間窗、建立者 |
| `ArenaMatch` | 一場邀請賽的比賽紀錄（連結到一個已接受的 `ArenaInvitation`，記錄雙方彙總分數與結果） |
| （Phase 2+）`ArenaSchoolDirectoryOptIn` | 學校是否開放被跨校邀請 |

### 7.3 API 草案

| Method | Path | 說明 |
|---|---|---|
| GET | `/api/arena/leaderboard/personal` | 個人日常排行榜（同年級校內，暱稱顯示） |
| GET | `/api/arena/nickname/me` | 取得自己的暱稱／圖示，可要求重新產生 |
| POST | `/api/arena/invitations` | 老師發出跨班邀請 |
| GET | `/api/arena/invitations` | 查詢本班收到／送出的邀請 |
| POST | `/api/arena/invitations/{id}/respond` | 接受／婉拒邀請 |
| GET | `/api/arena/matches/{id}` | 查詢一場邀請賽結果（班級彙總分數＋暱稱化個人名次） |

### 7.4 彙總策略

個人日常排行榜（校內同年級，MVP 規模：數十到數百人）用**即時彙總**即可（沿用 `gamification_service.get_classroom_leaderboard` 的查詢模式，換成校內同年級範圍）；全國賽（Phase 3，規模未知）才需要改成定期（如每 5 分鐘）刷新的快取表，避免尖峰時段對 DB 造成 N+1 查詢負擔。

### 7.5 規模假設（誠實標註）

目前 repo 看不到實際註冊使用者規模的資料，**本 PRD 無法給出真實數字，以下是假設**：均一第三季單一活動達 17,339 人／500+ 校，但那是營運多年、有縣市合作的成熟活動；本平台是新產品，MVP 應先以「單校／跨班」規模（數十到數百人）驗證機制可用，全國賽等流量與營運量能（縣市合作、公告管道）到位後再評估開放。

## 8. 分期

| 期別 | 範圍 | 備註 |
|---|---|---|
| **MVP**（本次實作範圍）| 個人日常排行榜（校內同年級，暱稱顯示）＋跨班邀請賽（非同步視窗期，每人平均分公平性公式）| 建立在既有 contest／gamification 之上，新增 `arena` 獨立模組 |
| Phase 2 | 跨校邀請賽（需要學校目錄 opt-in 機制）＋異常偵測（統計異常標記供人工複核）| |
| Phase 3 | 官方全國賽（`system_admin` 主辦，兩階段時間窗，三層排行榜，快取彙總）| 需先確認流量與 Cloud Run 常駐成本（§9）|
| Phase 4 | 賽季週期性重置＋榮譽牆／徽章擴充＋「夜幕低垂」畫面凍結（如採用）| |

## 9. 風險與待決定（需要 Young 定案）

1. **分數來源**：個人日常排行榜要用獨立的「競賽積分」，還是直接重用既有 XP？（本 PRD 預設獨立積分，因為 XP 反映整體學習動機、不適合當競技排名量尺）
2. **跨班邀請賽的最低參賽人數門檻**：§3.2 公平性公式裡的分母門檻數字（建議 5，待定案）
3. **跨校邀請賽的學校目錄**：要不要做 opt-in 機制？由誰審核學校加入公開清單？（Phase 2 問題，先列入風險）
4. **官方全國賽是否要做縣市／政府合作加碼**（均一有宜蘭／新北加碼）——我們目前沒有這類合作關係，是否要仿效
5. **是否開放自學生／非正式學校單位報名**（均一有此機制，本平台目前帳號模型以「學校—班級」為主幹，開放需另外設計）
6. **排行榜「畫面凍結」（夜幕低垂）**：是否要做類似機制防止熬夜刷題？MVP 不做，Phase 4 再評估
7. **資料保留與刪除政策**：排行榜歷史資料要保留多久？（MVP 暫不處理，需與既有個資保留政策一併訂）
8. **全國賽尖峰流量的 Cloud Run 常駐成本**：是否要在賽事時段保留 warm instance（需要先有 Phase 3 的流量規模才能估）
