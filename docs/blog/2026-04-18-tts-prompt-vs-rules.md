# 為了讓 AI 念對「垃圾」，我一天內搞了三套方案，最後發現一句 prompt 就夠了

你有過那種「做完才發現根本不用做」的經驗嗎

我這天是

---

## 事情是這樣開始的

我們做一個國小國語文閱讀平台，學生會聽 AI 念課文學讀音

有天方大哥（product owner）傳訊息來：「垃圾被念成 `lā jī` 了，這是中國發音，我們要台灣發音 `lè sè`」

國小國語文平台 AI 念錯音 = 教育事故，這不是能「再觀察」的小 bug

我打開 Gemini TTS 聽一次，確實是中國腔，就這樣，故事開始

---

## 方大哥的四個要求

做之前先釐清需求，方大哥的要求很清楚：

- **台灣腔**（攻擊念 `gōng jí`，不是 `gōng jī`）
- **自然不機械**
- **多音字要對**（喝采的喝念 `hè` 不是 `hē`）
- **人名地名要對**（戴資穎、陳彥博、214 周、2021 年）

---

## 問題的廣度 — 不是只有「垃圾」

你先別以為「台灣腔差別」只是幾個特例，我隨手整理一下就一堆：

| 詞 | 台灣 | 中國 | 差在哪 |
|----|-----|------|--------|
| 垃圾 | lè sè | lā jī | 兩個字都不一樣 |
| 企業 | qì yè | qǐ yè | 「企」聲調 |
| 研究 | yán jiù | yán jiū | 「究」韻母 |
| 危險 | wéi xiǎn | wēi xiǎn | 「危」聲調 |
| 攻擊 | gōng jí | gōng jī | 「擊」韻母 |
| 微笑 | wéi xiào | wēi xiào | 「微」聲調 |
| 星期 | xīng qí | xīng qī | 「期」聲調 |
| 盡量 | jìn liàng | jǐn liàng | 「盡」聲調 |
| 質量 | zhí liàng | zhì liàng | 「質」聲調 |
| 認識 | rèn shì | rèn shí | 「識」韻母 |
| 知識 | zhī shì | zhī shí | 「識」韻母 |
| 包括 | bāo guā | bāo kuò | 「括」整個不同 |

這些字在兩岸都是一樣的繁體字（或同樣的簡繁對應），但發音硬是不一樣

國小學生是在**建立國語發音基礎**的階段，念錯一次就是種一個錯的聲調在腦袋裡，未來要改回來很痛

所以這不是「口音偏好」問題，是「學理正確性」問題

還有一個更玄妙的細節 — 即使念對聲調，**韻尾的捲舌感**也是台灣腔和中國腔的分水嶺：

- 「摸」在中國腔會有一點點 ㄇㄨㄛ，ㄨ 的尾音藏在裡面
- 台灣腔就是乾淨的 ㄇㄛ

這種差別不在字典裡，但學生一聽就知道「怪怪的」

---

## 市面上三個 TTS 選項

市面上 TTS 我能拿到的，大概三個選擇：

| Provider | 台灣腔 | 成本 | 品質 |
|----------|-------|------|------|
| Azure Speech（zh-TW HsiaoChen）| ✅ 原生 | 貴 | 好，略僵 |
| Google Chirp3-HD Sulafat | ❌ 中國腔 | 中 | 非常好 |
| Gemini 3.1 Flash TTS（preview）| 🟡 可 prompt 指示 | 便宜 | 好 |

三個都試過的人應該知道，每個都有自己的遺憾

---

## 第一版：Azure + SSML `<phoneme>`

最早的生產版本是 Azure，搭 SSML 的 `<phoneme>` 標籤手工修多音字：

```xml
<phoneme alphabet="x-microsoft-zhuyin" ph="ㄏㄜˋ">喝</phoneme>采
```

你看這段 XML 應該就懂了，每個多音字都要手編一次注音標記

Azure 的好處是台灣腔原生正確，壞處是

1. 貴，bill 每月一直累積
2. 每個新多音字都要工程手動加規則
3. 音質略僵，不像真人

這個模式跑了一段時間，我一直在想有沒有更便宜更自然的做法

---

## 第二版：Gemini 3.1 + 37 條同音字替換表

Google 推出 Gemini 3.1 Flash TTS preview 的時候我眼睛一亮

成本超低（2036 句音檔跑完只要 $0.30 美金），音質又好，就是

**它預設念中國腔**

那怎麼辦？我就想出一個我現在回頭看覺得很奇葩的方法

**TTS 只看發音不看字義，那我把字換成同音的台灣字不就好了？**

```python
_TAIWAN_TTS_REPLACEMENTS = [
    ("垃圾", "樂色"),     # TW lè sè vs CN lā jī
    ("研究", "研舊"),     # 究 TW jiù vs CN jiū
    ("危險", "圍險"),     # 危 TW wéi vs CN wēi
    ("攻擊", "攻急"),     # 擊 TW jí vs CN jī — 方大哥指名
    # ... 37 條規則
]
```

我還順便做了阿拉伯數字轉中文：`214` → `兩百一十四`，免得 Gemini 用英文念

做完、跑完 batch、重生 2036 句音檔、上 staging 給方大哥驗收

**然後就踩坑了**

---

## 踩坑：一個沒 call 的 function

方大哥聽完回：「攻擊還是中國音」

啥

我打開 log 看，batch script 只 call `_clean_for_tts()`（去符號），漏 call `_clean_for_gemini()`（套我那 37 條替換）

送進 Gemini 的還是原文，等於我的 37 條規則全部白工，batch 白跑一次

修一行 code、重跑 batch、$0.30 又丟出去，總算對了

花了半天做 37 條表 + 修 bug + 重 batch 兩次

---

## 為了「相信 AI 念對了」，我做了一套稽核系統

方大哥這時候又提了一個我後來覺得非常有洞察的要求：

**「我要能驗收每一句音檔」**

他的擔心很合理 — 規則可能套錯、Gemini 可能念錯、我可能 push 了一個沒檢查的版本

於是我做了：

1. **Append-only JSONL log**（29 個欄位/筆）：記下每一句送進 Gemini 的原文、替換後字串、哪些規則觸發、音檔 SHA、GCS 路徑、生成時間、誰生的、取代了哪個舊版本
2. **後台稽核頁**：方大哥可以用瀏覽器翻 2036 句、filter「有套替換」「有數字」「台灣特有詞」、點進去看完整 metadata、直接播音檔抽聽

後來我才發現，**這套東西最大的價值不是除錯，是信任**

工程師 debug 用 log，其實可以寫粗一點；但產品 owner 要驗收 AI 生成的東西時，需要的是一種「責任可追」的安全感

這一層我之前都低估了

---

## 第三版：一句 prompt 就夠了

下午我坐下來，盯著那 37 條替換表看了一下

我自己問自己一個問題：

**「如果我不做替換，只告訴 Gemini『請用台灣腔念』，會不會就夠了？」**

其實我不知道答案，但 batch 只要 20 分鐘 + $0.30，試一次的成本低到不試白不試

於是我建了個 variant 系統：

- **Variant A**：不替換，只加 prompt prefix
- **Variant C**：做替換（原本的版本）

```
prompt prefix = "請使用台灣用語的繁體中文，以親切且自然的語氣朗讀以下內容："
```

跑完 A 版 batch，2036 句 / ~20 分鐘 / ~$0.30

---

## A/B 盲聽：44 個樣本、6 個類別、方大哥拍板

要讓「感覺比較好」變成可驗收的結論，我做了一個 A/B 盲聽網頁

44 個樣本，涵蓋：

- 台灣發音-高頻（垃圾 / 研究 / 危險 / 攻擊 / 企業 / 成績）
- 台灣發音-其他（微笑 / 盡量 / 休息 / 質量 / 認識 / 知識）
- 人名-難字（陳彥博 / 楊俊瀚 / 戴資穎 / 陳雨菲）
- 地名（東京 / 台灣）
- 數字（214 / 2021 / 100）
- 中英混讀（NASA / Hemsworth / PEACE / Frankenstein）

左邊綠色是 A（純 prompt），右邊橘色是 C（替換表），每筆並排放 audio element

方大哥和我並肩坐著聽完一輪，結果很清楚：

- **A 更自然**：整句連貫、語氣親切
- **C 略僵硬**：替換字會擾動語意節奏，斷句怪怪的
- **難字**：A 靠 prompt 竟然也能念對陳彥博、楊俊瀚這種不常見人名
- **數字**：A 直接讓 Gemini 自己把 `214 周` 念成「兩百一十四周」，我的數字轉中文規則根本可以刪

拍板：**以後就用 A**

---

## 彩蛋：啟翔獨立盲測也選 A

當天稍晚，我把三個音檔（A = prompt + 原字「攻擊」、B = 無 prompt + 原字、C = prompt + 「攻急」替換）丟到實習生啟翔的 Slack：

> 你聽聽看，你喜歡哪一個？盲測一下 — 啊！標題不要看

啟翔（完全不知道前因）的回覆：

> 我喜歡 A prompt，第三個，比較有台灣腔的感覺，也比較沒有捲舌的感覺

**三個不同的人，盲測都選 A**，這下差異是可聽辨的客觀差別，不是個人品味了

---

## 為什麼「攻擊 → 攻急」反而更糟？一個讓我重新想像 TTS 的 hypothesis

這一段是整件事最有趣的部分

原本我以為 TTS 的邏輯是：**字 → 發音**，既然「攻急」和「攻擊」的「擊 / 急」同音（jí），念出來應該一樣

但 C 版明顯更僵硬，啟翔的觀察一針見血：

> 他的語境沒有判別到才聽起來比較不舒服

我一邊聽一邊抓出另一個細節 — **「摸」字**：
- 中國腔會有一點點 ㄇㄨㄛ（ㄨ 的尾音藏在裡面）
- 台灣腔就是乾淨的 ㄇㄛ

這類聲調/尾音細節，用耳朵能辨，但 prompt 一句「台灣用語」就能影響

然後我想通了

**Gemini 3.1 Flash TTS 不是單純的 grapheme-to-phoneme，它帶語意理解**

- 看到「攻擊」→ 認識這個詞 → 用完整的語意節奏念
- 看到「攻急」→ 不認識這個組合 → 產生微妙的停頓和斷裂

我的 37 條替換表，其實是在**破壞它的語意 prior**

這個認知對我是一個 paradigm shift — 我以為我在「幫 Gemini 繞過」它的發音 bug，其實我在「把它會的部分拆掉」

---

## 一個反直覺的結論

> LLM 時代，工程的價值不是用規則補 AI 的不足，而是不要擋到它原本會的事

你讓它看原字 + 給它上下文（prompt），它的表現比你精心替換過的版本更好

這跟我過去做系統的直覺完全相反 — 以前系統能力不夠，工程的價值就是補規則、寫 workaround、打補丁；現在 AI 已經理解語意了，你加的每一條規則都可能在**削弱**它

## 三個我會記到下一次的教訓

### 一、Prompt 先試，規則後做

37 條規則我做了半天，prompt 十分鐘

LLM 時代 code infrastructure 的邏輯跟以前不一樣了 — 以前做系統，規則是主角、prompt 是配角；現在反過來

**先試 prompt，不夠再做規則**

這個順序如果我一開始就遵守，半天可以省下來

### 二、Audit trail 的價值是「信任」不是「除錯」

我原本以為 provenance log 是為了自己 debug，做完才發現

它真正的用戶是方大哥，他需要的是**逐句驗收的權力**

你想想，工程師被 bug 咬是家常便飯，但產品 owner 對 AI 生成物有一種「我沒親眼確認過的不敢簽」的焦慮，這個心情合理

做 AI 產品，audit trail 其實是讓非工程師睡得著覺的機制，不是 debug tool

### 三、Variant system 的長期價值

`tts-variants.yaml` + `--variant A|C` 這個設計本來是為了一次 A/B 做的，但做完我發現它可以長期存在

未來 Gemini 推出 voice 選項，可以加 Variant D 測試
未來要做低年級專用腔調，可以加 Variant E
GCS 分 folder 儲存，cache 不會污染

**一次實驗如果設計得好，會自己變成 infra**

這是我比較常忽略的一個原則 — 當下花 30 分鐘多寫一層抽象，未來少掉一次架構重構

## 成本對比（最後的帳單）

| 方案 | 人工維護 | API 月費 | 音質 | 台灣腔 |
|------|---------|---------|------|--------|
| Azure + SSML phoneme | 高（手編每字） | 貴 | 好，略僵 | ✅ 原生 |
| Chirp3-HD（中國腔）| 0 | 中 | 非常好 | ❌ |
| Gemini 3.1 Variant C（替換表）| 中（37 條 + 維護）| ~$0.30/2036 句 | 略僵 | ✅ 靠規則 |
| **Gemini 3.1 Variant A（prompt-only）**| **零** | **~$0.30/2036 句** | **好** | **✅ 靠 prompt** |

A 和 C 都是 Gemini 3.1 Flash TTS，差別只在 prompt 和替換表，所以 API 成本一樣

A 全贏，零維護、音質最好、成本最低

## 留一個問題給你

看到這裡你可能會想：「所以 LLM 把 TTS 工程師的飯碗搶走了嗎？」

我的答案是不會，但**工作內容變了**

以前 TTS 工程師在優化：音素標記、斷句規則、多音字字典、同音替換、SSML tag

現在工作變成：prompt 設計、audit trail、variant system、成本監控、信任機制

你在你自己的領域，有沒有也發生這種「工作不見、但工作內容換了」的事？
