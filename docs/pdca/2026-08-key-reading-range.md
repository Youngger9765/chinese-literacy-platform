## 一、Hans 回報的前因後果（含 QR code）

**時間點很關鍵：老師是在做 QR code 移植的時候發現的。**

```
2026-08-25  PR #2920   QR 改印代號 /q/{slug}（一課多篇，每一節有自己的代號）
2026-08-29  明珠老師照著把 QR code 移植到學習單上
            → 掃進去看到念順順，發現「這不是我要學生讀的範圍」
18:58 Hans  「他們在測段落閱讀流暢度時，有一個前提，是需要至少 300 字，
             因此講義上的手指箭頭是開始，但其實學生要閱讀的內容是
             講義右方有標字數的全部段落，這個部分我們是能調整的嗎？」
19:03 Hans  「我先請明珠老師一樣先進行 QR CODE 移植…建議可以不急著 31 日完成，
```

⚠️ **QR 本身沒有問題** —— `/q/{slug}` 指到的是「那個大題現在的頁面」，
slug 是節的身分，跟 passage 內容無關。**QR 移植不必等這個修**，Hans 的判斷是對的。

但那次移植是**第一次有老師真的從紙本走進線上**，所以也是第一次有人發現內容不對。
換句話說：**這個 bug 已經在線上活了 14 天，是 QR 把它照出來的。**

### 二之二 · 根因 B 我自己也搞錯了（2026-08-31 更正）

**「13 課錨點錯」這個結論，是拿一版人工掃描當裁判量出來的 —— 也就是根因 C 本身。**
用二修學習單的累計欄重量那 13 課：

| 課 | 指定段→end | 我們的字數 | 學習單 | 差 |
|---|---|---|---|---|
| L0004 · L0062 · L0067 · L0072 · L0076 · L0167 · L0017 | | | | **0** |
| L0012 · L0022 · L0038 · L0071 · L0149 | | | | ±1~9 |
| **L0007** | 5→10 | 367 | 399 | **−32** |

**12/13 對得上，其中 8 課差 0。** 真正還對不上的只有 L0007。

⚠️ 我原本寫的機制「印刷段號被當成陣列索引」**在 code 裡查不到證據**：
`find_anchor()` 從指示句解印刷段號，而 `by_idx` 也是用印刷段號當 key
（`out["by_idx"] = {idx: texts[i] for idx, i in pos_of.items()}`，`idx` 來自
`full_text_annotate` 的段號欄）—— 兩邊同一套口徑，不存在我描述的那個錯位。
**我把一個沒讀過 code 的因果寫成了結論**，這裡撤回。

⭐ 這是根因 C 第三次咬人，而這次咬的是**寫這份 PDCA 的我自己** ——
可見「換掉錯的裁判」不只是修抽取器，凡是引用過那份一版資料的**結論**都要重量一次。

**C 是 A 反覆復發的原因。** 每一次改回「只取一段」，引用的都是同一份一版資料：

```
backend/data/key_reading_passages.yml   134 筆人工掃描，中位數 147 字，只有 7 筆 ≥300 字
```

**一版的念順順本來就是一段，二修改成跨段。** 拿它當正解，就是在測錯的版本 ——
而且會得到「36/38 命中」這種看起來很硬的數字。

## 四、skill 當時是怎麼抽的

| 時期 | skill | 抽法 |
|---|---|---|
| ~8/16 | `build-key-reading` | `extent = max(累計字數)` —— 湊滿那個字數為止。**這是 #2712 的成因** |
| 8/21–8/24 | `lesson-reading-pipeline`（Raymond v3 初版）| ☞ → 累計欄末筆落在的那一段 ✅ |
| 8/24–8/30 | 同上（被改寫）| **只取 ☞ 那一段**，`end = start` 寫死，並把累計欄從 yml 剝除 |
| 8/30 起 | 同上（現行）| ☞ → 累計欄末筆落在的那一段，**取離末筆最近的停點** |

⚠️ **「湊滿 max」與「末筆落在哪一段」是兩件不同的事**，先前被當成同一件否決掉：

- 湊滿 max → 會越過數字實際落在的段落（`build-key-reading` 的病）
- 末筆落在哪一段 → 累計欄常常**提早停**（實測 115/138 課），停在哪就到哪

`apply()` 當時還把 `approx_chars_from_start`（＝累計欄末筆）列進 `RANGE_ERA_FIELDS`
**從 yml 剝掉**，理由是「留著會讓下一個人重建範圍規則」。
結果是：**判斷範圍的唯一紙上依據被刪了**，實測活的 yml 0/160 份還有那個數字。

## 五、現在定下來的規則（v3 抽取）

> **☞ 那一段 → 學習單右緣累計字數欄末筆落在的那一段，兩端之間全包。**

三步（`scripts/extract_key_reading_v3.py`）：

1. 讀 `printed_counter_last`（累計欄末筆，已逐課轉錄進 yml）
2. 從 ☞ 往後累加，取**離末筆最近**的停點當 `end_paragraph`
3. 差距 > `SPAN_TOLERANCE`（20 字）就標記讓人看，⛔ 不硬湊

⛔ 不是「累加到 ≥ 末筆才停」（會多吃一段，實測 32 課差在這裡）
⛔ 不是「☞ → 文末」（8/24 否決得對，累計欄常常提早停）

**因為末筆在 yml 裡，這支不需要 DOCX** —— 原設計性質保住，CI 也跑得動。

### 決定性證據

Owner 拍的《大自然的氣象小幫手》(L0003) 實體學習單：
**☞ 在第七段，而第七段第一行的數字就是 28** —— 若累計欄從文章開頭算不可能是 28。
第七段結束 259（＝被改壞期間服務的字數），第八段結束 392。

三個**互相獨立**的來源同時指向範圍：現場老師回報 · 實體學習單照片 ·
2026-07-20 專家審查自己定的「約 300–400 字」（`docs/PRD.md:1602`）。

## 七、可複用的教訓（公版 PDCA 用）

### 1. 規則翻面時，**把否決的理由連同數字寫進 code**

這條規則翻了四次，每一次翻的人手上都有前一版的**結論**，沒有前一版的**證據**。
現在 `test_key_reading_passages_2562.py` 的 docstring 逐次記著四次的理由與數字，
最後一段寫著「要再改（第四次）請先看那張照片，並解釋 ①②③ 三條各自為什麼不算數」。

### 2. **黃金集要註明是哪個版本的真值**

`key_reading_passages.yml` 是**一版**的人工掃描，但檔名與用法都沒說。
於是「36/38 命中」被當成規則正確的證明，實際上只證明「跟一版一樣」。
⛔ 任何 golden set 都要寫清楚：**它是誰、什麼時候、對哪個版本量的**。

### 3. **不要在同一個 commit 裡「改規則」＋「刪掉舊版本」**

`5c94728f1` 兩件一起做，之後想問「上一版怎麼抽的」只能翻 git。
規則改動與版本清理要分開，中間留一段可比對的時間。

### 4. **刪證據 ≠ 消除矛盾**

累計欄被剝掉的理由是「留著會讓下一個人重建範圍規則」。
但那是**判斷範圍的唯一紙上依據** —— 刪掉之後不但沒有防住重建，還讓修復要重新去翻原稿。
正確做法是鎖「**不准與 passage 矛盾**」，不是鎖「**不准存在**」。

### 5. **兩個版本並存時，全庫統計必先分版本**

我第一版時間軸得到「8/24 有 269 課」（全庫只有 175 課），就是 v2+v3 混算。
數字看起來像真的，結論整個是錯的。

### 6. **mutation 之後要先量「被測系統的輸出真的變了嗎」**

第一次驗服務端的鎖時，我 mutate 的是 `lesson_indexes._key_reading()` ——
**那根本不在服務路徑上**，改了它服務端輸出完全沒變（375 → 375），
而測試「4 passed」看起來像鎖是劇場。真正的路徑在 `lesson_uid_loader.py`。
**只確認「檔案改到了」不夠。**
