# 注音這件事的六個月 —— 目標、做法、對錯、釐清、下一步

> 2026-09-15 · 起因是 Young 問「那本來的『難』有搞定嗎」，追下去發現這條線從 2026-03-20 就開始
> 給外部 LLM 偵錯用的完整脈絡。全部數字都附產生方式，可複驗。

---

## 1. 目標

**學生在畫面上看到的每一個注音都是台灣讀音，而且同一個字在不同畫面上一致。**

拆成可驗的三條：

| | 條件 | 今天的狀態 |
|---|---|---|
| A | 讀音是台灣的，不是大陸的 | 單音字軸已修（#3202）；破音字軸部分修（#3215） |
| B | 同一句話在課文頁與朗讀診斷頁標同一個音 | 63,115 個可比位置，**93.77% 一致、3,934 不一致** |
| C | 某個字的注音悄悄變錯時，測試會紅 | 今天才做到（#3215 的全語料基準）；在那之前只守 7 個字 |

⚠️ **B 不等於正確。** 抽 32 個爭議案例送教育部辭典判：
**課文頁對 18 個詞（618 個位置）、後端對 11 個詞（185 個位置）、兩讀皆可 4 個。**
→ 「把後端對齊課文頁」會**新製造 185 個錯**。產品裡沒有任何一個畫面是真值。

## 2. How：現在到底有幾條路徑在產生注音

```
                   BpmfZihiSerif-Regular.ttf（出貨字型）
                   cmap format 14：基字 + U+E01Ex → uniXXXX.ssNN
                   glyph 第一個元件 = z_<拼音><聲調>   ← 讀音的庫存
                            │
        ┌───────────────────┼───────────────────┬──────────────────┐
        ▼                   ▼                   ▼                  ▼
   課文頁 ruby         朗讀診斷 ruby          語音（TTS）        字典頁
 polyphonicProcessor  _build_zhuyin_map   tts/normalization  dictionary_service
 + poyin_db.json      + 4 層查詢          + 教育部生成表      + 萌典（不看語境）
 + toneSandhi.ts                          + he_exceptions
 → (字, styleSet)     → 注音字串           → SSML <sub alias>  → 注音字串
```

**朗讀診斷那條的四層查詢**（`learning_reading.py::_build_zhuyin_map`，依序）：

1. `polyphone_words.py` —— 詞表 3,167 個詞（#3215，從 poyin_db 詞樣式展開）
2. `he_conjunction.py` —— 「和」當連接詞讀 ㄏㄢˋ（#3204，jieba + 380 筆教育部例外）
3. `zhuyin_readings.py` —— 單音字表 11,050 字（#3202，抽自字型）
4. 都沒命中 → `pypinyin` 的上下文判讀

**逐位置記帳**（213,449 個中文字，`_build_zhuyin_map` 真的跑）：

| 決定讀音的是誰 | 全部位置 | 只看破音字位置 |
|---|---|---|
| 字型單音表 | 145,132 (68.0%) | — |
| pypinyin 提議、**且該讀音在字型候選集內** | 54,984 (25.8%) | **80.5%** |
| 詞表 | 12,338 (5.8%) | 18.1% |
| 和 規則 | 656 (0.3%) | 1.0% |
| 字型聲調吸附 / 退預設 | 335 | 0.5% |
| **pypinyin 原始輸出、字型完全沒意見** | **4** | **0.006%** |

⭐ **所以風險不是「大陸音滲進來」（21 萬字裡只有 4 個），是「在台灣的合法讀音之間挑錯」。**

## 3. 過程：對的、錯的，分開看

### 3a. 做對的

| | 為什麼算對 |
|---|---|
| **真值選出貨字型** | 它就是畫面上實際會畫出來的讀音；已經在出貨；不受教育部辭典 CC BY-ND 限制。repo 09-12 就用 `test_font_is_taiwan_reading_authority_3173.py` 宣告過（12 個兩岸差異字由 Young 逐字確認）|
| **不移植前端的 matcher** | 改用 esbuild 把出貨 TS 打包在 node 跑當 oracle。移植版漏掉一/不變調與 `skipPrev`，吐出 `不 → ㄈㄨ`（看起來合理的錯答案）|
| **詞樣式展開成資料，不寫演算法** | 3,167 個具體的詞 + 最長詞優先比對。沒有判讀邏輯 = 沒有可以移植錯的東西 |
| **把「和」的判斷抽成共用模組** | 三道門（jieba + 380 筆教育部例外 + 自我指稱）整套早就在，只住在語音模組裡。抽出來兩邊共用，並**突變驗證 TTS 真的吃抽出去的那份**（回空集合 → TTS 7 條紅）|
| **每個「知情地改壞」都記成可見的帳** | `欸` 三處、`削鉛筆`（後來證明是我判斷錯，見 3b）|
| **棘輪只 commit「相異的決策」** | 10 KB，不是 1.32 MB 的全量產物。大小隨決策數長，不隨語料長度長 |

### 3b. 做錯的（分兩類）

**類型一：量具壞了，而答案看起來很正常**

| 錯 | 症狀 | 怎麼被抓到 |
|---|---|---|
| 「放寬裁判後 154/154 仍咬得住」 | 判定式有個 `is None` 恆真 → **跟裁判是誰無關**。把裁判換成「什麼都放行」照樣綠 | 對抗式複審 |
| 「21/21 與教育部一致」 | 那一層的缺陷密度 0.16%，抽 21 個看到 0 個的機率 **96.7%** —— **檢定力約等於零** | 對抗式複審 |
| 萌典解析器 | 教育部把輕聲點放在音節**前面**（`˙ㄉㄜ`），我的正則寫成放後面 → 解析出的讀音是錯的**而數量對得上** | 自己回頭查 |
| 對照表打錯字 | 注音 `ㄧ`(U+3127) 打成漢字 `一`(U+4E00)，把兩個正確的字標成錯 | 自己回頭查 |
| 影響面清單 | 只走單音字分支，**漏掉整條破音字分支** —— 而語料裡改最多的三個字（期 594、識 505、差 427）全在漏掉的那邊 | 對抗式複審 |
| 「`triples` 是棘輪」 | docstring 寫了三次，**沒有任何一條斷言讀它**。換成「宣稱 63,115 個位置全部一致」的假基準 → 40 passed | 對抗式複審 |

**共通形狀：數量對得上、格式合法、每一筆都像真的答案。沒有任何東西會壞掉或報錯。**

**類型二：判斷錯了**

| 錯 | 真相 |
|---|---|
| 把 `褐` 列成「知情地改壞」 | repo 裡的教育部資料說台灣讀 **ㄏㄜˊ**，正是字型說的；pypinyin 的 ㄏㄜˋ 是 `china` 欄。它是**改善**。我驗了機制、沒驗前提，而前提來自我的記憶 |
| 排除 `一`/`不` 出詞表 | 它們走變調不走詞樣式，看起來明顯正確 —— 實測從 **2 紅變 5 紅**（`第一`／`買一` 本來就是真的詞）|
| 濾掉空變體 | `[v for v in variants if v]` 讓**索引整串位移**（變體索引 = 字型 slot 編號），`了解` 給了 ㄌㄜ˙ |
| 「82.2% 落回 pypinyin」 | 這個框架誇大了 pypinyin 的權威。那 80.5% 每一筆都是**字型認可的台灣讀音之一** |
| 把「棘輪從 19 收到 2」說成快好了 | 它綠是因為**世界只有 31 句**。全語料 3,934 個不一致 |

### 釐清的結論

**1. 根因不是「缺一本字典」，是後端建了第二套破音字選擇器。**
#611 的研究報告 2026-03-20 就寫明後端不參與；10 週後後端有了自己的一套，
而 #3175 / #3202 / #3204 / #3215 全都是那一套的 bug。

**2. 而我今天一整天在把那第二套做得更精緻**（加詞表、加基準、加指紋門），
**沒有問過它該不該存在**。這正是 CLAUDE.md 自己的規則在講的事：
> 「十輪以上沒進展、或連續 3 個假設失敗 → 停下來問『我的框架是不是從第一輪就錯了』」

**3. 09-12 Young 已經問過「有四份、哪一份是對的、要不要整合」，也明講過「把難跟了處理好」。**
我三天後才盤清楚四份來源，而且是他再問一次「難有搞定嗎」我才去查。

**4. 一個沒人問過的問題**：`DiffDisplay` 是**前端**元件，它為什麼從後端拿 `token.zhuyin`，
而不直接叫前端那個已經存在的 `PolyphonicProcessor`？
（查證：`DiffDisplay.tsx` 沒有 import 它；全前端只有 `ZhuyinContext.tsx` 與 `toneData.ts` 在用。）
⚠️ 這不是零成本 —— diff token 含 `extra`/`missing`，位置要對回原文，而**那正是 #3175 的 bug 所在**。
但它是唯一能讓「第二套」消失的方向，而六個月來沒有任何一張票問過它。

### 5b. 該做、順序有理由

1. **`和` 兩個方向都會錯**（53 個漏判 + 23 個誤判）。⚠️ **必須一起修** ——
   放寬 jieba 判定讓一邊好、另一邊壞；`he_exceptions.json` 的 `_dropped_rare_two_char`
   那段是前人踩過同一個蹺蹺板的紀錄，動之前先讀
2. **那 83 組逐條判決**，按語料次數：`長(249) 為(190) 著(165) 質(72) 挑(45) 處(40)`。
   修法是**改 `poyin_db.json` 的詞樣式** —— 同一個槓桿同時修兩個畫面。實測：
   `「質」變體 0 加 `蛋白*` → 富含蛋白質 從 ㄓˋ 變 ㄓˊ`（課文頁本來就對，不受影響）
3. **萌典當一次性判官**，判決記成 `tts/taiwan_pronunciation.json` 那個形狀的小檔
   （我方語料驅動、附出處）。⚠️ 判決表要有 `authority` 欄（`moe` / `moe-overridden`
   + 誰、哪天、為什麼），否則下一輪有人重跑萌典會把 `姊姊` 「修」回 ㄗˇ 而且全綠

### 5c. ⛔ 明確不要做

| | 為什麼 |
|---|---|
| 把萌典詞條**批次匯入**當最長比對 | `中的` 是真的教育部詞條（ㄓㄨㄥˋ ㄉㄧˋ，射中靶心），而語料裡「…中的…」出現 137 次 → **會在最高頻位置憑空製造新錯誤** |
| 把後端**對齊課文頁** | 教育部判給後端的 185 個位置（`相反 ×109` 最大）抄過去就是製造新錯 |
| 整批修那 1,273 個詞彙破音不一致 | 要逐字判斷（教育部兩讀皆可的就有 4/32）。**資料補上去不會自己變對** |
| 萌典放進**執行期** | 現在的讀音路徑是純本地 fail-open，加網路相依 = 拿授權問題換可用性 bug |
| 移植 `polyphonicPatternMatcher.ts` | 移植過，漏規則，吐 `不 → ㄈㄨ` |
| 指望「音節聽 pypinyin、聲調聽字型」救簡體缺項 | **對這類永遠無效**：`乾` 的 ㄑㄧㄢˊ 與 ㄍㄢ 是不同音節；而且 `乾`×22 全部走「pypinyin 的讀音在字型候選內」那條（ㄑㄧㄢˊ 本來就是合法台灣讀音，乾坤）→ 字型候選比對完全攔不住 |

### 5d. 授權：事實 / 判讀 / 推測，分開講

**事實**
- CC BY-ND 3.0 TW：可重製散布**原樣的**著作，**不得散布改作物**
- 這個 repo 是 **PUBLIC**
- repo 裡**已有三處**萌典衍生物：`data/tts/taiwan_pronunciation.json`（198 筆，出處欄寫明）、
  `data/tts/he_exceptions.json`（380 筆）、`frontend/src/data/radical-meanings.json`（227 個部件，**帶釋義原文**）
- 而注音子系統寫著相反立場：`zhuyin_readings.py:16`、`test_font_is_taiwan_reading_authority_3173.py:21`
  —— 「教育部辭典是 CC BY-ND，不進這個 repo」

→ ⭐ **repo 內部政策是分裂的，不是「有先例所以可以」**

**實務判讀**（不是法律意見）
- 讀音本身是事實，事實不受著作權保護；但**選擇與編排**可構成編輯著作
- 既有那份 198 筆站得住的理由是**選擇標準是我方語料的詞頻**，不是照抄辭典編排，且附出處
- 曝險最尖銳的是 `radical-meanings.json`（出貨的是釋義原文），不是讀音表
- **「只在 build 時當判官」這條路不需要判這題** —— 萌典的東西一個字都不出貨

**推測（未查證）**
- 台灣著作權法第 7 條編輯著作在「小量事實抽取」上的實際判準，未查判決
- g0v moedict-data 專案頁對衍生使用有無額外聲明，未讀

## 附：可複驗的產生方式

```bash
# 前端 oracle（不移植，跑出貨的 TS）
git archive origin/staging frontend/src/components/zhuyin \
  frontend/public/data/poyin_db.json | tar -x -C "$W"
# runner.ts 見 backend/scripts/generate_cross_surface_baseline.py 檔頭
esbuild runner.ts --bundle --platform=node --format=cjs --loader:.json=json --outfile=runner.cjs
node runner.cjs corpus.json fe_readings.json

# 基準
python3 backend/scripts/generate_cross_surface_baseline.py --fe fe_readings.json
python3 backend/scripts/generate_cross_surface_baseline.py --check

# 詞表
python3 backend/scripts/generate_polyphone_words.py
python3 backend/scripts/generate_polyphone_words.py --check
```

**三個會咬人的地方**：繞 `fetch()` 要抄 `polyphonicReadings.test.ts` 的 `beforeAll`；
**長度守衛不可省**（錯位 = 一整份看起來合理的位移答案，#3175 的形狀）；
fixture 存的是**拼音**不是注音 —— ⭐ **一個「100% 全錯」的結果通常是單位沒對齊，不是東西真的全錯**。

## 6. 兩個外部 LLM 的獨立判決（2026-09-15）

問同一題：**後端該不該有第二套破音字選擇器？** 兩位都答「不該」，而且各補了對方漏的。

### 收斂的目標形狀（cursor 的一句話最準）

> **要一個原文座標契約、一份 `poyin_db`、一個顯示引擎、一個獨立的 TTS 資料表。**

```
 ① 原文座標契約          每個 token 帶 source_index（extra 為 null）
    後端的責任            ⛔ 禁止「數 non-extra 去猜原文下標」 ← #3175 的 bug
                             ⚠️ 換到前端寫一樣會再犯 —— 這層跟「誰選音」無關

 ② 一份資料              poyin_db.json（詞 → 選哪個變體）
                          字型 = 讀音庫存（一個字有哪些音）

 ③ 一個顯示引擎          PolyphonicProcessor，對「原文」跑
    前端                  後端不再回 token.zhuyin

 ④ 一份語音資料          taiwan_pronunciation.json → SSML <sub alias>
    後端留著              聽覺 ≠ ruby，這不是第二套選擇器
```

### 兩位的分歧，以及誰對

| | GPT-5.6（kiro） | cursor | 我的判讀 |
|---|---|---|---|
| 後端加詞表 | 加深債 | 同意，且「這套甚至還沒 merge，不要再做」 | 一致 |
